# 포트폴리오 트러블슈팅 — 추억피드 확장 (약속 연결 + 여권 상세)

> Clov 추억피드에 "약속 연결 + MEMORY PASSPORT 상세 + 사진 갤러리"를 구현하며 만난 두 가지 비자명한 버그의 **문제 발견 → 원인 → 솔루션** 기록.
> 스택: 프레임워크 없는 순수 HTML/CSS/JavaScript, 데이터는 `localStorage`에 저장.

---

## 트러블슈팅 1 — 전체화면 사진 갤러리가 "페이지 안에 박히는" 문제

### 문제 발견
추억 상세(여권)에서 대표사진을 클릭하면 **전체화면 슬라이드 갤러리**가 떠야 하는데, 오버레이가 화면을 덮지 않고 페이지 본문 사이에 그냥 끼어서 렌더됐다. 기능(다음/이전, 카운터)은 동작하는데 시각적으로만 깨진, 잡기 까다로운 형태였다.

### 원인 분석 (디버깅 과정)
1. 갤러리는 `document.createElement('div')`로 만들어 `overlay.className = 'mp-gallery'`(= `position:fixed` 전체화면 오버레이) 지정 후 `document.body.appendChild()` 하는 방식이었다.
2. 그런데 런타임에 계산된 스타일을 찍어 보니 `display: block`, `position: static` — **`.mp-gallery` 클래스가 실제로는 안 붙어 있었다.**
3. DOM 트리를 역추적하니 오버레이가 `document.body`의 직속 자식이 아니라, **클래스 없는 `<div>` 컨테이너(모바일 미러 영역) 안**으로 옮겨져 있었고, **`className`이 빈 문자열로 지워져** 있었다.
4. 생성 직후를 단독으로 검사(`ensureMemoryGalleryEl()` 호출 → 즉시 `className` 확인)한 결과: **append하는 순간** 클래스가 사라지고 다른 컨테이너로 이동. → `document.body`에 동적으로 추가된 노드를 **모바일 뷰로 복제/이동하면서 class를 제거하는 앱 자체 로직(MutationObserver 계열)** 이 원인이었다.

즉, 내 갤러리 코드의 버그가 아니라 **"body에 동적으로 노드를 붙인다"는 전제가 이 앱에서 성립하지 않는다**는 게 핵심이었다.

### 솔루션
동적 생성(append)을 버리고, **다른 모달들과 동일하게 오버레이 컨테이너를 `index.html`에 정적으로 배치**했다. (`memory-detail-sheet`, `wm-backdrop` 등 기존 모달이 전부 정적 body 자식으로 잘 살아 있는 것을 근거로 삼음.)
- `index.html`: `<div class="mp-gallery" id="memory-gallery-overlay">` 정적 추가
- JS: `ensureMemoryGalleryEl()`을 "정적 요소를 찾아 이벤트를 **최초 1회만** 바인딩"으로 변경 (append 제거)

### 결과
`display:flex · position:fixed · z-index:260`으로 정상 전체화면 렌더. 화살표·썸네일 점프·드래그 스와이프·ESC 닫기, 갤러리에서 넘긴 위치가 상세 대표사진에 역동기화까지 확인.

### 배운 점
- "내 코드가 안 되네"보다 **런타임 DOM/computed style을 직접 찍어 전제를 의심**하는 게 빨랐다. `className`이 빈 문자열이라는 단서 하나가 범인을 특정했다.
- 공용 코드베이스에선 `document.body.appendChild`조차 안전하지 않을 수 있다. **기존에 이미 잘 동작하는 패턴(정적 모달)을 따르는 것**이 가장 견고했다.

## 트러블슈팅 2 — "저장 공간이 부족해요" 모달이 뜨는 문제

### 문제 발견
추억에 사진을 몇 장 올리면 **"저장 공간이 부족해요 / 이미지를 더 작은 파일로 다시 올려주세요"** 모달이 떴다. "디스크 용량"처럼 보이지만 실제로는 그렇지 않았다.

### 원인 분석
1. 이 모달은 `localStorage.setItem(...)`이 `try/catch`에서 **예외를 던질 때만** 표시된다(코드 추적으로 확인).
2. 서버가 없는 프로토타입이라 **사진을 포함한 모든 데이터를 `localStorage`에 저장**하는데, 사진이 파일이 아니라 **base64 데이터URL 문자열**로 통째로 들어간다. base64는 원본 대비 약 1.35배로 커지고, `localStorage`는 **도메인당 약 5MB** 한도다 → 초과 시 `QuotaExceededError`.
3. 악화 요인 3가지:
   - 이번 확장에서 **추억 사진 상한을 6 → 30장**으로 올림.
   - 추억 사진은 **압축 없이 원본 그대로 저장**하고 있었다. (반면 인생4컷 사진은 이미 `compressStagePhoto`로 520px·품질 0.64로 줄여 저장 → 상대적으로 안전) → 스마트폰 사진(장당 3~4MB)이면 **2~3장만으로 5MB 한도에 도달.**
   - 기존에 누적된 데이터도 한도 근처였을 수 있음.

즉 "디스크 부족"이 아니라 **브라우저 도메인당 localStorage 5MB 한도 초과**였다.

### 솔루션 (1차 — 유입 차단)
추억 사진도 업로드 시 **자동 압축**하도록 공용 함수 `compressMemoryPhoto`를 추가했다. 갤러리에서 전체화면으로 보므로 4컷(520px)보다 큰 **1080px·JPEG 품질 0.7**로 설정(캔버스 리사이즈 → `toDataURL('image/jpeg', 0.7)`, 디코드 실패 시 원본 폴백). 글쓰기 모달과 상세 수정 양쪽의 업로드 경로에 동일 적용.

**실측:**
- 6.4MB 원본 PNG → **26KB** JPEG(1080×720), 약 99.6% 감소.
- 실제 업로드 경로: 2400×1600 PNG → **7KB** JPEG 저장 확인.
- 장당 수십 KB → 30장이어도 ~780KB로 한도 안에 여유롭게 수용.

### 솔루션 (2차 — 이미 쌓인 부채 회수) ★ 한 단계 더 깊은 대응
1차 압축 적용 후에도 **여전히 같은 모달이 떴다.** 압축은 **앞으로 올릴 사진(유입분)** 만 줄일 뿐, **압축 도입 이전에 이미 원본으로 저장돼 한도를 꽉 채운 데이터(재고분)** 는 그대로 남아, 새 사진(압축본)조차 들어갈 자리가 없었던 것이다. 즉 "수도꼭지는 잠갔지만 이미 넘친 물은 그대로"인 상태.

→ 데이터를 **삭제하지 않고**, 저장돼 있던 원본 사진들을 **한 번에 재압축해 공간을 회수하는 마이그레이션**(`compactStoredPhotos`)을 추가했다.
- 로드 시 **1회만 자동 실행**(`clov_photo_compacted_v1` 가드 플래그) — 사용자는 새로고침 한 번으로 자동 복구, 확보 용량을 토스트로 안내.
- 4컷 사진 저장이 실패하면 **그 자리에서 재압축 후 1회 재시도** → 그래도 부족할 때만 안내 모달 표시(자기 치유).
- 이미 충분히 작은(≈60KB 미만) 사진은 건너뛰고, 재압축 결과가 더 커지면 원본을 유지하는 안전장치 포함.

**실측:** 14MB로 포화된 저장소 → 새로고침 1회 → **256KB로 회수(약 98%)**, 사진 장수·연결·대표사진 모두 보존.

### 배운 점 (보강)
- 버그 수정이 "유입"만 막고 "재고"를 놓치면 증상이 그대로다. **문제를 시간축(과거에 쌓인 것 vs 앞으로 생길 것)으로 나눠** 양쪽을 다 처리해야 진짜 해결이었다.
- 되돌릴 수 없어 보이는 저장 포화 상태도, **손실 없이 회수(재압축 마이그레이션)** 하는 자기 치유 경로를 두면 사용자가 데이터를 잃지 않는다.

### 배운 점
- 에러 문구("저장 공간 부족")를 **문자 그대로 믿지 말 것.** `setItem` 예외 하나가 곧 문구였고, 진짜 원인은 base64 인코딩 + 한도였다.
- 서버 없는 클라이언트 저장(localStorage) 설계에서 **바이너리를 base64로 넣는 순간 용량이 핵심 제약**이 된다. 한도(≈5MB)와 인코딩 오버헤드(≈1.35×)를 먼저 계산했어야 했다.
- 상한(30장)을 올리는 결정과 저장 비용은 **함께 설계**해야 한다. 기능 상한만 올리고 저장 전략(압축)을 안 바꾼 게 화근이었다.
