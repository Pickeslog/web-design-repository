# 🐛 일정 삭제가 "안 되는" 버그 트러블슈팅

> **한 줄 요약**: "삭제 버튼이 작동하지 않는다"는 제보를 받았지만, 실제 원인은 버튼이 아니라 **변경 사항이 영구 저장되지 않는 데이터 지속성(persistence) 누락**이었다. 증상과 진짜 원인이 다른 케이스를 체계적 디버깅으로 규명하고, 미러링된 두 코드베이스에 일관되게 수정을 적용했다.

| 항목 | 내용 |
|---|---|
| **화면** | Clov 우정공간 — 일정계획(약속 메모) 탭 |
| **스택** | Vanilla JS · localStorage · 컴포넌트 없는 프로토타입 |
| **증상** | "일정 삭제 버튼이 작동하지 않음" |
| **실제 원인** | 삭제 로직은 정상. `groupsData` 변경 후 localStorage 미저장 → 새로고침 시 데이터 부활 |
| **영향 범위** | 삭제뿐 아니라 추가·수정·메모 편집까지 동일 결함 |

---

## 1. 문제 발견

사용자로부터 **"일정계획의 삭제 기능이 작동하지 않는다"** 는 제보를 받았다.

첫 가설은 흔한 UI 이벤트 문제였다.
- 클릭 핸들러 미바인딩?
- 다른 요소가 버튼을 덮고 있는(overlay) 히트테스트 문제?
- 확인 다이얼로그가 안 뜨는 문제?

**"버튼이 안 눌린다"는 제보를 그대로 믿지 않고**, 실제 브라우저에서 이벤트 흐름을 단계별로 계측하며 재현부터 했다.

---

## 2. 원인 분석 (디버깅 과정)

### ① 이벤트 체인 계측 — 버튼은 정상이었다

브라우저에서 삭제 버튼의 실제 동작을 단계별로 확인했다.

```
✓ 삭제 버튼 존재 & onclick="deleteSchedule(1)" 정상 바인딩
✓ elementFromPoint(버튼 중심) === 버튼  → 덮는 요소 없음(히트테스트 통과)
✓ mousedown→mouseup→click 이벤트 디스패치 → 확인 다이얼로그 정상 오픈
✓ "삭제" 확정 클릭 → 메모리상 배열에서 해당 일정 제거됨
✓ 토스트 "🗑️ 일정이 삭제되었어요." 정상 노출
```

**버튼도, 핸들러도, 확인창도 전부 정상이었다.** 삭제 직후 화면에서도 일정이 사라졌다. 그렇다면 왜 "작동하지 않는다"고 느꼈을까?

### ② 진짜 증상 재현 — 새로고침하면 되살아난다

핵심 단서는 **"삭제한 일정이 다시 나타난다"** 였다. 새로고침 후 상태를 확인하자:

```
삭제 실행 → 화면에서 사라짐 ✓
새로고침  → 삭제했던 "제주도 여름 우정 여행"이 부활 ✗
```

사용자 관점에서는 "삭제했는데 또 있다 = 삭제가 안 된다"로 보였던 것이다.

### ③ 데이터 흐름 추적 — 지속성 계층의 단절

데이터 로딩 지점을 역추적했다.

```js
// data.js — 부팅 시 localStorage에서 일정 데이터 복원
let groupsData = JSON.parse(localStorage.getItem('clov_groupsData'));
if (!groupsData || ...) { groupsData = defaultGroupsData; ... }
```

```js
// schedule.js — 삭제 로직 (수정 전)
function deleteSchedule(scheduleId) {
    clovConfirm('정말 이 약속을 삭제하시겠습니까?', () => {
        const schedules = groupsData[activeGroup].schedules || [];
        groupsData[activeGroup].schedules =
            schedules.filter(s => s.id !== scheduleId);   // ← 메모리만 수정
        updateScheduleUI();                                // ← 화면만 갱신
        clovToast('🗑️ 일정이 삭제되었어요.', 'info');
        // ⚠️ localStorage.setItem(...) 없음 → 새로고침 시 원복
    });
}
```

**근본 원인**: 앱은 부팅 시 `clov_groupsData`(localStorage)에서 일정을 복원하는데, 삭제 로직은 **런타임 메모리(`groupsData`)만 변경**하고 저장소에 다시 기록(persist)하지 않았다. 화면은 즉시 갱신되므로 순간적으로는 삭제된 듯 보이지만, 다음 로드 때 저장소의 옛 데이터가 그대로 복원됐다.

### ④ 결함 확산 확인 — 삭제만의 문제가 아니었다

동일한 패턴을 검색하자 **추가(`saveSchedule`)·수정·메모 편집(`saveScheduleContent`)** 도 똑같이 저장 호출이 빠져 있었다. (이쪽은 반대로 "만든 일정이 새로고침하면 사라지는" 잠재 버그.) 즉 **일정 데이터의 모든 변이(mutation) 지점에서 지속성이 누락**된 구조적 결함이었다.

## 3. 솔루션

### 설계 원칙
개별 함수마다 `localStorage.setItem`을 흩뿌리는 대신, **저장 책임을 단일 헬퍼로 캡슐화**하고 모든 변이 지점에서 호출하도록 통일했다.

```js
// 일정 변경(추가/수정/삭제/메모)을 localStorage에 반영 — groupsData는 부팅 시
// clov_groupsData에서 복원되므로, 저장하지 않으면 새로고침 때 변경 전 상태로 되돌아간다
function persistGroupsData() {
    try {
        localStorage.setItem('clov_groupsData', JSON.stringify(groupsData));
    } catch (error) {
        clovToast('⚠️ 변경사항 저장에 실패했어요. 저장 공간을 확인해주세요.', 'warn');
    }
}
```

**적용 지점 (3곳)**
| 함수 | 시점 | 효과 |
|---|---|---|
| `deleteSchedule` | 삭제 확정 시 | 삭제가 영구 반영 |
| `saveSchedule` | 추가/수정 저장 시 | 새 일정·변경이 영구 반영 |
| `saveScheduleContent` | 메모 blur 저장 시 | 메모 편집이 영구 반영 |

**미러 코드베이스 동기화**
이 프로토타입은 `index.html`용 `js/schedule.js`와 `feed.html` 등이 쓰는 `js/desktop.js`에 **동일 로직이 이중으로 존재**했다. 한쪽만 고치면 화면에 따라 동작이 갈리므로, **양쪽 파일에 일관되게** 적용했다.

**견고성 보강**
- `try/catch`로 localStorage 용량 초과(QuotaExceeded)를 잡아 조용한 실패 대신 사용자에게 경고 토스트를 노출.

## 4. 검증

실제 브라우저에서 시나리오 기반으로 확인했다.

| 시나리오 | 결과 |
|---|---|
| 삭제 → localStorage에서 즉시 제거 | ✅ |
| **삭제 → 새로고침 → 되살아나지 않음** | ✅ (핵심 회귀 검증) |
| 신규 추가 → localStorage 반영 | ✅ |
| 콘솔 에러 | 0건 |
| 검증용 테스트 데이터 | 기본값으로 원상복구 |

## 5. 회고 — 이 트러블슈팅에서 얻은 것

- **"증상 ≠ 원인"**: "버튼이 안 눌린다"는 제보를 액면 그대로 받지 않고, 이벤트 체인을 계측해 버튼은 정상임을 먼저 배제한 뒤 데이터 지속성 계층까지 추적한 것이 핵심이었다.
- **국소 수정이 아닌 구조적 관점**: 삭제 한 곳만 고치는 대신 같은 결함이 있는 추가·수정·메모까지 찾아, 반복되는 원인(모든 변이 지점의 persist 누락)을 단일 헬퍼로 해소했다.
- **중복 코드베이스의 일관성**: 미러링된 두 파일을 함께 수정해 화면 간 동작 불일치를 예방했다.
- **조용한 실패 방지**: 저장 실패를 사용자에게 드러내 "저장된 줄 알았는데 아니었던" 2차 사고를 막았다.
