# AI Team Harness

이 문서는 Codex, Claude Code, Gemini 등 어떤 AI 에이전트를 사용하더라도
같은 작업 경계, 입력 문서, 검증 기준을 따르기 위한 공통 하네스다.

## 1. SSOT와 읽는 순서

작업 전 아래 순서로 읽는다.

1. 대상 레포의 `AGENTS.md`
2. `docs/API-CONTRACT.md`와 연결된 API 계약 SSOT
3. `api-spec/05-db-unified-final.md` (DB를 읽거나 API 데이터를 다룰 때)
4. `docs/CODE-CONVENTION.md`
5. 담당 화면 명세와 최근 `work-logs/`
6. GitHub 이슈 본문과 기존 유사 코드

충돌할 때 우선순위는 계약/DB SSOT, 리더 승인, 화면 명세, 이슈, 기존 코드
순서다. 계약과 DB 스키마는 이슈와 승인 없이 바꾸지 않는다.

## 2. 작업 단위

- 이슈 1개 = 브랜치 1개 = 집중된 PR 1개
- 브랜치는 `feat/<issue>-<topic>`, `fix/<issue>-<topic>`,
  `chore/<topic>` 형식을 사용한다.
- `main`에 직접 커밋하지 않는다.
- 현재 다른 사람이 수정 중인 파일, 공통 설정, 마이그레이션은 병렬 수정하지
  않는다. 범위를 나누거나 먼저 이슈 댓글로 조율한다.
- 작업 전에 기존 변경 사항을 확인한다. 본인이 만들지 않은 변경은 되돌리거나
  섞어서 커밋하지 않는다.

## 3. 공통 금지 사항

- 실제 시크릿, `.env`, `application-secret.yaml`, 토큰, 비밀번호를 코드, PR,
  이슈, 로그, 테스트 데이터에 넣지 않는다.
- API 계약, DB DDL, 공통 응답 봉투, 인증 방식, 의존성을 임의로 변경하지 않는다.
- API에 JPA를 추가하지 않고 MyBatis와 `#{}` 바인딩만 사용한다.
- `role`, 방장, 관리자 개념을 만들지 않는다. 서비스 인가 규칙은 계약을 따른다.
- 프론트 컴포넌트에서 직접 HTTP 호출하거나 두 번째 API 클라이언트/토큰 저장소를
  만들지 않는다.

## 4. AI 에이전트 작업 절차

1. 이슈와 필수 문서를 읽고, 작업 범위와 완료 기준을 한 문장으로 정리한다.
2. 기존 유사 구현을 검색해 이름, 폴더, 테스트 패턴을 따른다.
3. 필요한 최소 파일만 수정한다. 요구되지 않은 리팩터링은 분리 이슈로 남긴다.
4. 대상 레포의 검증 명령을 실행한다.
   - API: `./gradlew.bat test`
   - Web: `npm run lint`와 `npm run build`
5. `git diff`와 `git diff --check`로 변경 범위를 검토한다.
6. 커밋과 PR에는 이슈 번호를 연결하고, 완료 보고는 아래 형식을 사용한다.

```text
- 변경: 핵심 변경 파일과 동작
- 검증: 실행한 명령과 결과
- 남은 점: 미검증 항목 또는 외부 의존성
```

## 5. 리뷰 게이트

리뷰어는 머지 전 다음을 확인한다.

- 계약의 경로, 요청/응답, 에러 코드, JSON ID 문자열화가 맞는가
- DB 컬럼/SQL/MyBatis mapper가 계약과 맞는가
- 새 이름과 폴더가 `CODE-CONVENTION.md`와 인접 코드 패턴을 따르는가
- 시크릿, 토큰, 비밀번호, 개인정보가 포함되지 않았는가
- 불필요한 파일이나 다른 이슈 변경이 섞이지 않았는가
- 요구된 테스트와 린트/빌드 결과가 있는가

## 6. 팬아웃 시작 기준

로그인 워킹 스켈레톤이 프론트 -> API -> DB까지 동작하고, 대표 PR의
구조와 리뷰 기준이 확인된 뒤 도메인 작업을 병렬로 나눈다. 그 전에는
환경 구축, 문서 정합성 확인, QA 기록 외의 기능 코딩을 시작하지 않는다.

## 7. AI 공통 시작 프롬프트

아래 블록을 작업 요청 첫 부분에 붙인다.

```text
작업 전 대상 레포의 AGENTS.md, web-design-repository/docs/AI-TEAM-HARNESS.md,
web-design-repository/docs/CODE-CONVENTION.md, 관련 API 계약과 화면 명세를 읽어.
이슈 범위 밖의 계약, DB, 공통 설정, 시크릿은 바꾸지 마.
기존 유사 코드의 폴더와 명명 패턴을 따르고, 작업 후 git diff와 필수 검증 결과를
변경/검증/남은 점 세 줄로 보고해.
```
