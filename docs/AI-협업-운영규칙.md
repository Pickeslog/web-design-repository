## 0. 한눈에 — 협업 모델

```
계약(SSOT) ─── 두 에이전트가 함께 읽는 단일 진실
   │
   ├─▶ 코덱스   : clov-api 백엔드 구현 (한 방향 #2→#3→#4→#6)  ── PR
   │                                                            │
   └─▶ 클로드   : 계약/스펙 정합성 감사 + PR 리뷰 + clov-web 이관
                     └─ 코덱스 PR을 머지 전에 계약 기준으로 검증
```

핵심 명제: **효율은 능력이 아니라 "경계"와 "인수인계"에서 갈린다.**
마찰의 두 원인 — ① 같은 파일을 둘이 건드림 ② 서로의 작업 맥락 단절.

---

## 1. 역할 분담 (강점으로 가른다 — 겹치면 통합이 터진다)

| | 코덱스 | 클로드 코드 |
|---|---|---|
| 강점 | 코드 편집·`git diff`·`apply_patch`·테스트 실행 | 여러 문서 교차 추론·모순 탐지·계획 |
| 담당 repo | **`clov-api`** (백엔드) | **`clov-web`**(이관) + `web-design-repository`(감사, 읽기) |
| 산출물 | 동작하는 PR + 초록 테스트 | 감사 리포트·이슈 코멘트·리뷰 승인 |
| 진행 방식 | 한 방향 세로 슬라이스, 다른 슬라이스 동시 착수 금지 | 코덱스보다 앞서 지뢰 제거 |

> 두 repo가 물리적으로 분리(`clov-api` / `clov-web`)돼 있어 **repo로 가르면 파일 충돌이 원천 봉쇄**된다. 한 에이전트 = 한 repo = 한 폴더.

---

## 2. 인수인계는 "사람의 기억"이 아니라 "영속 아티팩트"로

두 에이전트는 서로를 못 본다. 사람이 말로 옮기면 새는 게 생긴다.
**GitHub 이슈·PR·work-log가 공유 메모리**가 되게 한다.

- 모든 작업 = **이슈 1개 = 브랜치 1개 = PR 1개** (작게 유지)
- 발견·결정은 그때그때 **이슈 코멘트 / work-log**에 남긴다 → 다음 에이전트가 읽는다
- 각 에이전트 **시작 프롬프트에 §6 공통 블록**을 항상 붙인다 (규칙 안 읽고 시작 방지)

---

## 3. "한 명이 짜고, 한 명이 검증한다" — 최고 레버리지

코덱스가 PR을 열면 **머지 전에 클로드가 계약 기준으로 리뷰**한다.
이건 정확히 클로드가 잘하는 일이고, 팀의 지뢰를 머지 전에 잡는다.

```
코덱스: 이슈 구현 → PR
   └─ 클로드: PR을 API-CONTRACT.md·05-db 기준으로 리뷰 → 위반 있으면 코멘트
        └─ 코덱스: 수정 → 클로드 승인 → 머지
```

**리뷰 시 반드시 확인하는 계약 지뢰**

- ❌ `role` 컬럼/claim (계약 §3 "방장/역할 없음")
- ❌ base path `/api/v1` 누락 (강사 예제의 `/api/auth` 아님)
- ❌ 시크릿 커밋 (두 repo 모두 **public**)
- ❌ JPA 혼입 (`@Entity`/`JpaRepository`) — MyBatis만
- ❌ SQL `${}` 사용 (`#{}` 바인딩만)
- ✅ 응답 봉투 `{success, data}` / `{success, error{code,message}}`
- ✅ ID는 JSON에서 문자열 직렬화(정밀도)

## 4. 충돌 방지 실무 규칙 5개

1. **스켈레톤은 순차, 팬아웃은 병렬.** M0~M1(로그인 관통) 완성 전엔 코덱스 한 방향으로. 완성 후 M2 도메인 19개를 병렬로.
2. **작업 끝나면 커밋/스태시로 워킹트리를 비운다.** 미커밋으로 두면 다른 에이전트·폴더 정리가 그걸 날린다. (2026-07-20 stash 사건의 교훈)
3. **한 에이전트당 한 폴더.** 코덱스=`clov-api`, 클로드=`clov-web`(+감사는 `web-design-repository` 읽기). **`-collaboration` 폴더는 열지 않는다**(병합 완료된 잉여 클론).
4. **계약은 SSOT 1곳만 수정.** 스펙 충돌 발견 시 코드부터 고치지 말고 `web-design-repository`의 계약을 먼저 고치고 양쪽이 따르게 한다.
5. **막히면 원인을 구분해서 보고.** (예: 테스트 실패 시 Java / DB URL / 의존성 중 무엇인지) 다음 에이전트가 같은 삽질을 안 하게.

## 5. 단계별 적용

| 단계 | 코덱스 | 클로드 | 병렬? |
|---|---|---|---|
| M0 기반 | #2 DB → #3 봉투 → #4 Security/JWT | 각 PR 리뷰 + 계약 정합성 감사 | 순차(코덱스) + 리뷰(클로드) |
| M1 스켈레톤 | #5 OAuth · #6 Auth | clov-web #2 셸 · #3 로그인 연동 | 부분 병렬 (api 선행 의존) |
| M2 도메인 | api 도메인 슬라이스 | web 화면 이관 | **완전 병렬 (팀원 팬아웃)** |

> 원칙: **워킹 스켈레톤 하나(로그인 프론트→백→DB 관통)를 본보기로 만든 뒤** 팀원 4명이 팬아웃. 그 전에 둘 다 코드를 짜면 M0부터 패턴이 갈려 통합이 터진다.
