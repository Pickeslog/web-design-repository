## 1. 전체 흐름 — 5단계 파이프라인

```
[설계·계약]   기획 → DB 스키마(05 통일본) → API 명세(api-spec)
   상태:      ✅ 거의 완료   ⚠️ 실제 레포 계약이 낡음 → "통일"만 남음
     │
     ▼
[0단계 셋업]  레포 3개 유지 · 지침파일 · 계약 1개 · main보호 · CI
   상태:      🔄 진행 중
     │
     ▼
[1단계 워킹스켈레톤]  로그인 1개를 프론트→백→DB→CI 끝까지 관통 (리드 혼자)
   목적:      나머지 3명의 AI가 "베낄 정답 패턴"을 만든다 ← 하네스 일관성의 핵심
     │
     ▼
[2단계 기능 팬아웃]  4명이 기능 세로슬라이스를 각자 하네스로 개발
   방식:      한 명당 프론트+백 한 조각(기능 단위)
     │
     ▼
[3단계 통합·배포]  기능 합치기 → 테스트 → 배포
```

> **핵심 원칙**: 사람을 "프론트팀/백팀"으로 가르지 않고 **기능(세로)으로 나눈다**. 통합 = 기능마다 프론트+백이 붙어있다는 뜻이므로, 한 명이 기능 하나를 끝까지 책임진다.

**→ 현재(2026-08-13): 5단계 전부 완료.** 계약은 `API-CONTRACT.md` 단일본으로 통일됐고(DB 24테이블), 로그인 워킹 스켈레톤 이후 4명이 기능을 팬아웃해 우정공간·약속·추억·행운편지·상점·알림·인증까지 전 도메인이 구현됐다. 배포 인프라(GCP·nginx·Docker·GitHub Actions)도 구성돼 있다(`clov-api/deploy/DEPLOY.md` 참고).

## 3. 하네스 운영 — 3층 구조

AI를 4명·3도구로 굴리려면 아래 3층이 갖춰져야 한다.

### 1층. 에이전트가 "읽는" 것 (지침)
```
각 레포 AGENTS.md          ← HOW: 이 레포에서 어떻게 코딩하나 (있음)
 ├ CLAUDE.md → AGENTS.md   ← Claude/Codex용 포인터 (있음)
 └ GEMINI.md → AGENTS.md   ← Gemini용 포인터 (추가됨)

단일 계약 (1곳)            ← WHAT: 프론트-백 공통 약속(API·DB) ⚠️ 통일 필요
```
> **HOW(레포별)는 나눠도 되지만, WHAT(계약)은 반드시 한 곳.** 현재 `docs/API-CONTRACT.md`가 두 레포에 복제 + 낡음 → 하나로 통일이 최우선 숙제.

**→ 현재(2026-08-13)**: `GEMINI.md` 줄은 과거 기록이다 — 실제로 Gemini를 쓰는 팀원이 있었을 때 만들었던 포인터고, 2026-07-24 전원 Claude 전환 이후로는 안 쓴다(파일 자체를 없던 일로 치지 않는다, 실제로 있었다). 계약은 `docs/API-CONTRACT.md` 단일본으로 통일 완료 — 위 "⚠️ 통일 필요"는 해소됐다.

### 2층. 사람이 "지키는" 것 (작업 규칙)
- **3레포를 한 부모 폴더에 clone** → 하네스를 부모 폴더에서 실행하면 AI가 프론트+백+계약을 다 본다.
- **이슈 1개 = 브랜치 1개** (`feature/이슈번호-기능`), PR은 **작게** 자주 (AI는 빨리 뽑으니 충돌 예방).
- **계약(API·DB) 수정은 리드 1명만** → 갈라짐 방지.
- **AI가 만든 코드는 돌려보고 커밋** (생성물 그대로 밀지 않기).
- 기능이 프론트+백에 걸치면 **PR 2개**(백 먼저 머지 → 프론트).

**→ 현재(2026-08-13)**: 브랜치 이름은 실제로는 `feature/이슈번호-기능`이 아니라 `feat/<이슈번호>-<주제>` · `fix/<이슈번호>-<주제>`로 굳어졌다(각 레포 `AGENTS.md` 기준). "계약 수정은 리드 1명만"은 리더 부재 기간에 한해 "팀 자체 판단"으로 대체 가능하다고 확정됐다(`API-CONTRACT.md` 상단 참고) — 리더 복귀 시 원래 규칙으로 되돌아간다.

### 3층. 기계가 "강제"하는 것 (안전망) — 도구 3종이라 필수
- **CI**: lint·build·test 자동 실행 → 어느 AI가 썼든 규약 못 지키면 머지 차단.
- **main 보호**: PR 필수 + 리드 승인 1 → 아무도 main을 실수로 못 깬다.
- **단일 계약**: 프론트-백이 같은 약속으로 대화.

**→ 현재(2026-08-13)**: 셋 다 실제로 가동 중인 것 확인함 — CI는 `clov-api`(`./gradlew test`)·`clov-web`(build) 둘 다, main 보호는 두 레포 다 PR 필수+CI 통과 필수(승인 1은 리더 부재 기간엔 생략되는 듯 — 팀 자체 판단으로 셀프 리뷰만 거치고 머지하는 방식으로 운영 중).

## 5. Git 운영 (3레포)

```
main (보호: PR 필수 · 리드 승인 1)
 └ feature/이슈번호-기능   ← 이슈 하나 = 브랜치 하나, 짧게 살고 빨리 머지
```
- 이슈는 **그 일이 사는 레포**에 만든다(백=clov-api, 프론트=clov-web).
- 전체 진행은 **org Project 보드 하나**로 세 레포 이슈를 모아 본다.
- 커밋 메시지: `무엇을 했다 (#이슈번호)`.
- 이슈 제목 태그: `[api]` `[web]` `[design]`.

**→ 현재(2026-08-13)**: 브랜치 네이밍은 `feature/이슈번호-기능`이 아니라 `feat/<이슈번호>-<주제>`·`fix/<이슈번호>-<주제>`·`chore/<주제>`로 정착했다. 커밋 메시지는 Conventional Commits(`feat:`/`fix:`/`docs:` 등) 형식을 따른다. 계약 제안 이슈는 `web-design-repository`에도 만든다(태그 `[계약 제안]`).

### main 보호 켜는 법 (각 레포, 5분)
> GitHub → 레포 → **Settings → Branches → Add branch ruleset**
> - Branch name: `main`
> - ✅ Require a pull request before merging → **Require approvals: 1**
> - (CI 붙인 뒤) ✅ Require status checks to pass

**→ 현재(2026-08-13): 이미 켜져 있다.** `clov-api`·`clov-web` 둘 다 위 설정이 적용 중이고, 직접 `main`에 push를 시도하면 GitHub이 실제로 거부하는 것을 확인했다(`Changes must be made through a pull request` / `Required status check "build" is expected`). `web-design-repository`는 이 규칙을 켜지 않아서, 계약 문서만큼은 리더(또는 리더 부재 기간엔 팀)가 직접 `main`에 커밋하는 방식으로 운영 중이다.
