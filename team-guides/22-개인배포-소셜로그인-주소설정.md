# 개인 배포 — 소셜 로그인 주소 설정

> 개인 배포(도커) 후 **소셜 로그인이 `localhost:5173`으로 튕기거나 `redirect_uri_mismatch`가 날 때** 보는 문서다.
> **코드 문제가 아니라 설정 세 줄이 빠진 것**이고, 어느 칸이 비었느냐에 따라 증상만 달라진다.
>
> 배포 자체가 아직이면 [20-도커-배포와-HTTPS-인증서.md](20-도커-배포와-HTTPS-인증서.md) ·
> [21-CICD-자동배포-팀원-셋업.md](21-CICD-자동배포-팀원-셋업.md)를 먼저 본다.
> **이 문서는 배포가 끝난 다음 단계다.**
>
> 원문: clov-api #87 (2026-07-29). 예시 도메인 `clovlab.store`는 **본인 도메인으로 바꿔서** 읽을 것.

## 무슨 일이 일어나고 있나

배포한 백엔드가 **"로그인이 끝나면 어디로 돌려보낼지"를 모르는 상태**다. 그래서 개발할 때 쓰던 기본값(`localhost:5173`)으로 보낸다.

실제 증상은 이렇게 보인다.

```
1. 로그인 화면(clovlab.store/login) → 정상
2. 구글 로그인 버튼 → "400 오류: redirect_uri_mismatch"
   또는
3. 로그인은 되는데 주소창이 localhost:5173/oauth2/redirect?code=... 로 바뀌고
   "로그인을 완료하지 못했어요 / 인증 시간이 만료되었어요"
```

### 3번이 왜 "만료"라고 나오나

일회성 코드가 **엉뚱한 곳으로 배달됐기 때문**이다.

```
구글 → 배포 서버 백엔드 → 로그인 코드 발급
                          ↓ 복귀 주소가 localhost:5173
        내 PC의 개발 서버가 그 코드를 받음
                          ↓ 그 프론트는 localhost:8080 백엔드를 봄
        로컬 백엔드는 이 코드를 모름 → "만료되었어요"
```

배포 서버가 만든 코드를 **내 PC의 백엔드에게 물어본** 것이다. 앱은 정상이고 **주소만 어긋났다.**

---

## 설정 세 줄이 각각 하는 일

| 설정 | 역할 | 없을 때 기본값 |
|---|---|---|
| `APP_OAUTH_REDIRECT_BASE` | **소셜에게 알려줄 콜백 주소** (구글 → 내 백엔드) | `http://localhost:8080` |
| `APP_OAUTH2_REDIRECT_URL` | **백엔드 → 프론트 복귀 주소** | `http://localhost:5173/oauth2/redirect` |
| `APP_CORS_ALLOWED_ORIGINS` | 이 도메인의 브라우저 요청을 허용 | `http://localhost:5173` |

### ★ 빠뜨린 것에 따라 증상이 다르다

**"사람마다 증상이 다른" 이유가 이것이다.** 원인은 같은 표인데 어느 칸이 비었느냐만 다르다.

| 빠뜨린 것 | 증상 |
|---|---|
| `APP_OAUTH_REDIRECT_BASE` | 구글 화면에서 **`redirect_uri_mismatch`** |
| `APP_OAUTH2_REDIRECT_URL` | 로그인은 되는데 **`localhost:5173`으로 튕김** |
| `APP_CORS_ALLOWED_ORIGINS` | 화면은 뜨는데 **API 호출이 전부 CORS 에러** |
| 소셜 콘솔의 `http`/`https` 불일치 | **`redirect_uri_mismatch`** |
| 설정은 넣었는데 **재기동을 안 함** | 아무것도 안 바뀜 |

## 1단계 · 지금 뭐가 들어 있는지 확인

**고치기 전에 먼저 본다.** 원인이 다를 수도 있다.

백엔드를 **도커**로 돌린다면:

```bash
docker exec api env | grep APP_
```

**systemd**로 돌린다면:

```bash
sudo cat /opt/clov-api/clov-api.env
```

세 줄이 **전부** 있고 값이 **본인 도메인**이어야 한다.

```
APP_CORS_ALLOWED_ORIGINS=https://clovlab.store
APP_OAUTH_REDIRECT_BASE=https://clovlab.store
APP_OAUTH2_REDIRECT_URL=https://clovlab.store/oauth2/redirect
```

하나라도 없거나 `localhost`가 보이면 그게 원인이다.

---

## 2단계 · 소셜 콘솔에 `https://` 주소 등록

`redirect_uri_mismatch`는 **주소가 글자 하나라도 다르면** 난다. `http`와 `https`도 다른 주소로 친다.

**구글** — Google Cloud Console → 사용자 인증 정보 → 승인된 리디렉션 URI

```
https://clovlab.store/login/oauth2/code/google
```

**카카오** — 내 애플리케이션 → 카카오 로그인 → Redirect URI

```
https://clovlab.store/login/oauth2/code/kakao
```

**네이버** — 애플리케이션 → API 설정

```
PC 웹 서비스 URL:  https://clovlab.store
Callback URL:      https://clovlab.store/login/oauth2/code/naver
```

- 기존 `http://` 항목은 지워도 되고 둬도 무해하다
- **반영에 몇 분 걸릴 수 있다.** 저장 직후 안 되면 잠시 뒤 재시도
- ⚠️ 콘솔 프로젝트를 팀이 공유한다면 **리더에게 요청**해야 할 수 있다

> 어느 클라이언트를 고쳐야 할지 헷갈리면, 로그인 시도할 때 **구글 화면 주소창의 `client_id=` 값**을 콘솔의 클라이언트 ID와 대조하면 된다.

## 3단계 · 환경변수 채우기

**도커** — compose 파일의 `environment:` 아래에 추가

```yaml
    environment:
      - APP_CORS_ALLOWED_ORIGINS=https://clovlab.store
      - APP_OAUTH_REDIRECT_BASE=https://clovlab.store
      - APP_OAUTH2_REDIRECT_URL=https://clovlab.store/oauth2/redirect
```

**systemd** — `/opt/clov-api/clov-api.env`에 세 줄 추가

> `Permission denied`가 나면 `sudo nano` 또는 `sudo tee`를 쓴다. `sudo cat > 파일`은 **안 된다** — 리다이렉트(`>`)는 셸이 일반 권한으로 수행하기 때문이다.

---

## 4단계 · 백엔드 재기동

**환경변수는 켤 때 한 번만 읽는다.** 파일만 고치고 재기동을 안 하면 아무것도 안 바뀐다.

도커:

```bash
docker compose -f ~/api-docker-compose.yaml up -d --force-recreate && docker logs -f api
```

systemd:

```bash
sudo systemctl restart clov-api && sudo journalctl -u clov-api -f
```

### ⏳ 여기서 성급하게 판단하지 말 것

**`Started ClovApiApplication in XXX seconds`가 나올 때까지 기다린다.** VM 사양에 따라 **3~4분** 걸릴 수 있다(작은 인스턴스에서 200초 넘게 걸린 사례가 있다).

그 전까지는 —

- 로그가 **비어 있어도** 정상이다(배너가 나오는 데만 1분 가까이 걸릴 수 있다)
- `docker ps`가 `Up`이어도 **아직 안 뜬 것**이다
- 사이트가 **502를 줘도** 정상이다

나오면 `Ctrl+C`(로그만 끊기고 컨테이너는 계속 돈다).

## 5단계 · 확인

```bash
docker exec api env | grep APP_
```

세 줄이 본인 도메인으로 나오는지 본다. 그 다음 **브라우저에서 소셜 로그인**.

- 주소창이 **`localhost:5173`이 아니라 본인 도메인**으로 돌아오면 성공
- 여전히 `redirect_uri_mismatch`면 → 2단계 콘솔 반영이 아직이다. 몇 분 뒤 재시도
- 카카오·네이버·구글 **셋 다** 해볼 것 (콘솔이 각각이라 하나만 되는 경우가 있다)

## 그래도 안 되면 이걸 그대로 붙여서 물어보기

`clovlab.store` 부분만 본인 도메인으로 바꿔서 실행한다.

```bash
echo "== ENV =="; docker exec api env | grep APP_; echo "== 컨테이너 =="; docker ps --format '{{.Names}} | {{.Status}}'; echo "== 경로 =="; for p in / /login /oauth2/redirect /api/v1/rooms; do printf "%-18s " "$p"; curl -s -o /dev/null -w "%{http_code}\n" "https://clovlab.store$p"; done
```

기대값은 이렇다.

```
/                  200
/login             200
/oauth2/redirect   200      ← 여기가 401이나 JSON이면 nginx 설정 문제
/api/v1/rooms      401      ← 401이 정상(인증을 요구한다 = 백엔드까지 도달)
```

---

## 참고 — `/oauth2/redirect`가 200이어야 하는 이유

`/oauth2/redirect`는 **프론트 화면**이고 `/oauth2/authorization/...`은 **백엔드**다. nginx에서 `/oauth2/` 전체를 백엔드로 보내면 로그인 마지막 단계가 깨진다.

`/login`도 마찬가지다. **`/login`은 프론트 화면**, `/login/oauth2/`만 백엔드다.

nginx 설정은 이렇게 **좁게** 잡아야 한다.

```nginx
location /api/                  { proxy_pass http://백엔드; }
location /oauth2/authorization/ { proxy_pass http://백엔드; }
location /login/oauth2/         { proxy_pass http://백엔드; }
```

`location ~ ^/(api|oauth2|login|...)` 같은 **정규식 한 방으로 묶으면 안 된다.** 정규식은 prefix보다 우선순위가 높아서 `/login`·`/oauth2/redirect`까지 삼켜버린다.
