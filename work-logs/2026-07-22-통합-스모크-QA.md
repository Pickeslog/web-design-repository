## 버그: 약속 삭제 FK 500 → clov-api #48 머지
- **원인**: `plan_checklists`·`plan_stage_photos`가 `plans(id)` FK인데 **`ON DELETE CASCADE` 없음**, `PlanService.delete`는 plans 행만 삭제 → 자식이 있으면 제약 위반 500.
- **프론트 도달 가능**: 일정 상세 삭제 버튼은 `SCHEDULED`에 노출, 그 약속도 체크리스트 보유 가능.
- **수정**: 삭제 시 자식(체크리스트·단계사진) 먼저 제거(트랜잭션 안, 비작성자면 plans 0행→`NOT_WRITER`→롤백으로 자식 복원). `ChecklistMapper`·`StagePhotoMapper`에 `deleteByPlanId` 추가. 회귀 테스트(자식 있는 약속 삭제→200→404) 추가.
- **범위 밖(후속)**: `memories`(plan_id)도 plans FK. 완료 약속에 추억이 달린 삭제는 여전히 막힘 — 프론트는 SCHEDULED만 삭제라 도달 불가. "추억 있는 약속 삭제 차단"은 보존 정책상 별도 판단.

## 교훈 (오늘)
- **CI 사각지대**: 통합테스트 `@AfterEach`가 자식을 먼저 지우면, **API 삭제 경로가 자식과 함께 실행되는 케이스가 영영 안 돌아** FK 버그를 못 잡는다. 정리 픽스처가 실제 삭제 순서를 감춘다. → **실행 중 인스턴스에 스모크**가 이런 통합/제약 버그를 잡는다(단위·통합 테스트의 깔끔한 픽스처가 못 잡는 것).
- **FK 자식 삭제 순서**: 새 부모-자식 테이블 추가 시 부모 삭제 경로에서 자식 선삭제(또는 CASCADE) 여부를 항상 점검. memory_images(#46)는 memory soft-delete라 이 문제 없음(행 유지).
