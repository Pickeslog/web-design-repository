## 1. `#382` — 추억 상세/수정 모달 해시태그 + 카드-상세 표시 통일 (PR #389)

**배경**: 수정 모달엔 태그 입력이 없고, 저장 payload에도 `tags`가 안 실려서 태그를 바꿀 방법이 없었다. 상세보기도 `memory.tags?.length > 0`일 때만 렌더해서, 카드가 보여주는 자동 생성 폴백 태그(`cardTags()`)를 상세에서는 볼 수 없었다.

**구현**:
- `parseTagsInput()`을 모듈 스코프로 추출해 작성 모달(`CreateMemoryModal`)과 수정 모달(`MemoryDetailModal`)이 공용으로 쓰게 함
- `MemoryDetailModal`에 `tagsInput` 상태 추가, `startEdit()`에서 `memory.tags`로 초기값 채움, 저장 payload에 `tags` 포함
- 상세보기 태그 렌더를 `cardTags(memory, isMine)` 폴백 로직으로 통일(조건부 렌더 제거)

**추가 작업(이슈 밖, 같은 세션에 사용자가 스크린샷으로 지적)**: 여권 커버 제목(`.mp-cover-title`)이 공백 없는 긴 텍스트(예: 긴 숫자열)일 때 줄바꿈을 못 해 모달 밖으로 삐져나가는 버그. `word-break: keep-all`만 있고 `overflow-wrap`이 없던 게 원인 — `overflow-wrap: anywhere` 추가로 해결. PR 본문에 "이슈 본문에 없던 추가 작업"으로 명시.

**반성**: PR을 라벨 없이 올렸다가 사용자에게 지적받음 — `feedback-clov-labels` 메모리로 저장, 이후 두 PR은 생성 시점에 라벨 포함.

## 2. `#391` — 행운편지 생일 CTA 동시생일 + 말풍선 재설계 (PR #392)

**배경**: 편지함의 생일 축하 CTA(`Letters.jsx`)가 `birthdayMember = memberItems.find(...)`로 **오늘 생일인 멤버 중 첫 번째 한 명만** 잡았다. 레이아웃도 "편지 작성" 버튼 아래 일반 흐름 알약 버튼이라 창을 좁히면 세로로 밀려 쌓였다.

**구현**:
- `.find()` → `.filter()`로 `birthdayMembers`(배열) 전원을 잡음. 문구는 이름 전부 나열
- 클릭 시: 1명이면 바로 그 사람 앞으로 편지 작성, 2명 이상이면 선택 목록(`letter-birthday-picker`) 토글
- `letter-box-trigger`(우체통 버튼)를 `letter-box-wrap`으로 감싸고, 말풍선(`letter-birthday-cta`)을 절대배치 형제로 배치(버튼 속 버튼을 피하려고)

**설계가 두 번 바뀐 지점**: 처음엔 우체통 **위**에 뜨는 말풍선으로 구현했는데, 사용자가 스크린샷을 보고 "위가 아니라 좌우에"로 재지시 — 우체통 **오른쪽 옆**(세로 중앙 정렬)으로 다시 배치했다(우체통에 이미 오른쪽을 향한 깃발 장식이 있어 그쪽을 골랐다). 폭은 `min(190px, calc(100vw - 260px))`로, 창이 좁아질수록 옆에 남는 자리도 같이 줄어드는 걸 반영한 근사값이다(정밀한 브레이크포인트 계산은 아님, 실기기 확인 필요로 남겨둠).

## 3. `#393` — 추억 생일 배지 참여자 확장 (PR #395)

**배경**: 추억 카드·상세 모달의 생일 배지(`#378`)가 `memory.writer.id`(작성자) 한정이었다. 대시보드 생일 배너는 방 멤버 전원을 훑어 "오늘 생일인 사람"을 찾는데, 카드/상세는 다른 기준(작성자 본인)을 쓰고 있었다.

**진단 과정이 이번 세션에서 가장 길었다** — 사용자가 스크린샷 3장(대시보드 배너·피드 카드 3장·상세 모달)으로 "친구 생일이 안 뜬다"고 보고했을 때, 코드만 보면 카드/상세 로직이 이미 대칭적(작성자든 누구든 같은 함수로 조회)이라 즉시 "버그"라고 단정하지 않고, **작성자 전용 설계 vs 참여자 포함 기대**라는 두 가능성으로 나눠 먼저 확인 질문을 했다. 사용자가 "참여자 기준으로" 확장을 확정한 뒤에야 이슈(`#393`)를 썼다.

**구현이 세 단계로 넓어졌다**(전부 같은 세션, 사용자 지시로 매번 확장):
1. 1차: `birthMonthDayByWriter` → `birthMonthDayByUserId`로 바꾸고, `writer`+`participants` 전원 중 **첫 매치 1명만** 배지에 반영(이슈 본문에 "다중 나열은 범위 밖"이라고 명시)
2. 2차: 실기기 확인 결과 여전히 "내 생일만 나온다"고 재보고 — 원인은 그 FREE MEMORY의 작성자가 "나"였고 매치 대상인 친구는 참여자였는데, 참여자를 포함하는 로직 자체는 맞았지만 **동시에 두 사람(나+친구)이 매치되는 경우 첫 매치(나) 하나만 보여주던 것**이 실제 체감 버그였음 → `birthdayPeople`(배열)로 전원 표시하도록 확장(이슈 본문 조항을 뒤집음, PR에 명시)
3. 3차: 상세 모달에서 이름을 쉼표로 합친 문구 하나로 구현했더니, 사용자가 "닉네임 8자 이상 2명 이상이면 좁은 영수증 칼럼을 넘칠 것 같다"고 지적(작업 전 의견만 요청) → 내가 카드의 "+N" 패턴 재사용을 제안했으나 **사용자가 거부**("생일자는 모두 나와야지") → **생일자 한 명당 `mp-receipt-birthday` div를 하나씩** 렌더하는 방식으로 최종 정리. 덤으로 `overflow-wrap: anywhere`도 안전장치로 추가(닉네임 하나 자체가 길 때 대비)

카드 쪽(`memory-birthday-badge`)은 표시 텍스트가 원래 고정 "🎂 생일"이라 이름 목록 오버플로우 위험이 없어 그대로 뒀다(툴킵에만 전원 닉네임).
