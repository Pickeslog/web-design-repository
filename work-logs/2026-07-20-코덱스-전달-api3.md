# 2026-07-20 — 코덱스 전달: API #3 (전역 응답 봉투 + GlobalExceptionHandler)

> [Pre-#3 스펙 점검](2026-07-20-L1-정합성감사.md)에서 발견한 §14 공백을 코덱스 착수 중에 메꾸기 위한 전달 문서.
> **결정**: canonical generic 에러코드 6종 + 검증 에러 `details` 배열 **포함**(회원가입 폼 UX).
> **상태**: 코덱스에 프롬프트로 전달. 계약 §14·§2 본문 반영은 **리더 승인 후**(협업규칙 §4).

---

## 1. 계약 §14에 편입할 generic 에러코드 (붙여넣기용)

기존 §14는 도메인 코드만 있어, GlobalExceptionHandler가 뱉을 공통 코드가 없다. 아래를 §14 표 상단에 추가.

```markdown
| code | HTTP | 의미 |
|---|---|---|
| `VALIDATION_FAILED` | 400 | `@Valid` 입력 검증 실패(필드 상세는 `error.details`) |
| `UNAUTHORIZED` | 401 | 인증 토큰 없음/무효/만료 |
| `FORBIDDEN` | 403 | 인가 실패(도메인 코드가 없을 때 fallback) |
| `NOT_FOUND` | 404 | 리소스 없음 |
| `METHOD_NOT_ALLOWED` | 405 | 허용되지 않은 HTTP 메서드 |
| `INTERNAL_ERROR` | 500 | 처리되지 않은 예외 catch-all |
```

> 규약: 에러코드는 **UPPER_SNAKE_CASE**. 도메인 코드는 기존 §14 사례를 따른다.
> 인증 세부 코드(`INVALID_CREDENTIALS`·`EMAIL_DUPLICATED`·`TOKEN_EXPIRED` 등)는 [A·C 수정안](2026-07-20-계약수정안-A-C.md) C-6에서 #6 착수 시 편입.

## 2. 계약 §2 응답 봉투 — 검증 에러 `details` 확장 (붙여넣기용)

§2 실패 봉투에 **선택 필드 `details`** 추가. `VALIDATION_FAILED`에서만 채우고 그 외엔 생략.

```jsonc
// 실패 (일반)
{ "success": false, "error": { "code": "NOT_FOUND", "message": "..." } }
// 실패 (검증) — details는 VALIDATION_FAILED에서만
{ "success": false, "error": {
    "code": "VALIDATION_FAILED",
    "message": "입력값을 확인해주세요.",
    "details": [ { "field": "email", "reason": "형식 오류" },
                 { "field": "password", "reason": "8~20자, 2종 이상" } ] } }
```

> 효과: clov-web 회원가입 폼이 **어느 칸이 왜 틀렸는지** 표시 가능(필드 다수라 UX상 필수적).

## 3. 코덱스 전달 프롬프트 (복붙)

```
작업 전에 clov-api의 AGENTS.md와 web-design-repository/docs/API-CONTRACT.md의
§2(응답 봉투)·§14(에러코드)를 읽어. work-logs/2026-07-20-*.md로 맥락도 파악해.
계약·DB 스키마는 임의로 바꾸지 마.

이슈 #3([api] 전역 응답 봉투 + GlobalExceptionHandler)을 구현해.
이건 이후 모든 API의 본보기 패턴이니 특히 정확히 맞춰.

[응답 봉투 — 계약 §2 그대로]
- 성공: {success:true, data:{...}}
- 목록: {success:true, data:{items,page,size,total}}
- 실패: {success:false, error:{code, message, details?}}
- ID는 JSON에서 문자열로 직렬화(정밀도 안전)

[에러코드 — 아래 generic 세트를 그대로 써. 이 이름들이 계약 §14에 편입될
 canonical 이름이다. 임의 명명 금지]
- VALIDATION_FAILED 400  (@Valid 실패)
- UNAUTHORIZED     401  (토큰 없음/무효/만료)
- FORBIDDEN        403  (인가 실패 fallback)
- NOT_FOUND        404
- METHOD_NOT_ALLOWED 405
- INTERNAL_ERROR   500  (처리 안 된 예외 catch-all)
에러코드는 UPPER_SNAKE_CASE. 도메인 코드는 계약 §14 기존 사례를 따른다.

[검증 에러 상세 — details 배열 포함]
@Valid 다중 필드 실패 시 필드별로 담는다:
{ success:false, error:{ code:"VALIDATION_FAILED", message:"입력값을 확인해주세요.",
  details:[ {field:"email", reason:"형식 오류"} ] } }
details는 VALIDATION_FAILED에서만 채우고 다른 에러는 생략(또는 null).

[구조 — 이슈 #3 작업항목]
- global/response/ApiResponse<T> — {success,data} / {success,error{code,message,details?}}
- global/exception/GlobalExceptionHandler (@RestControllerAdvice)
- 도메인 예외 베이스 클래스 + 에러코드 enum(code, httpStatus)
- MethodArgumentNotValidException → VALIDATION_FAILED + details 매핑

[반드시 지킬 것]
- role 개념 만들지 마 (계약 §3 "방장/역할 없음")
- base path /api/v1
- 시크릿 커밋 금지 (레포 public)
- JPA 금지, MyBatis만
- 봉투/에러코드 이름을 위 스펙과 100% 일치

작업 후 git diff로 범위가 이슈 #3과 맞는지 확인하고, ./gradlew test 결과를 보고해줘.
봉투 직렬화와 에러 매핑 단위 테스트를 포함해.
```
