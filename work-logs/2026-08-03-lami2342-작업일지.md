## 1. clov-web #148 — 추억 수정 모달 글자수 제한

이슈는 리더가 사전에 범위를 글자수만으로 축소해둔 상태(사진개수·약속연결은 `#181`로 분리)에서 시작. 제목 25→40자, 친구 한 줄 메시지 255→80자로 목업 기준에 맞췄다.

- `MEMORY_TITLE_LIMIT`·`MEMORY_MESSAGE_LIMIT` 상수로 추출해 작성 모달(`CreateMemoryModal`)·수정 모달(`MemoryDetailModal`)이 같은 값을 공유하게 함 — 한쪽만 고치면 수정 모드로 우회 가능하다는 게 이슈의 핵심 요구사항
- 41·81자 붙여넣기를 `document.execCommand('insertText', ...)`(실제 브라우저 입력 경로 시뮬레이션)로 직접 확인 — `maxLength`가 붙여넣기도 막는다는 것 실측
- **작업 중 발견**: 협업 문서를 다시 읽다가 `API-CONTRACT.md` §10(Memories)의 요청 스펙 텍스트가 여전히 `title ≤ 25`로 남아있는 걸 발견(2026-07-30 갱신 로그에도 §10은 안 건드림). clov-api 실제 코드(`CreateMemoryRequest.java`)는 이미 `@Size(max=40)`이라 실질적 위험은 없었지만, 문서가 코드보다 뒤처진 사례. 사용자 판단으로 이슈화하지 않고 참고만 하기로 함.

## 2. clov-api #90/#91 — 합류 알림 버그 + MEMBER_JOINED 신설

사용자가 실제 화면에서 "A가 입장했는데 다른 사람이 합류했다"고 잘못 뜨는 스크린샷을 보여줘서 시작.

- **원인**: `InviteService.acceptJoinRequest`가 `InviteMapper.insertJoinNotifications`를 직접 호출하면서 (a) actor에 accept 호출자(수락자)를 잘못 넘기고 (b) 자체 SQL이 공용 팬아웃의 본인 제외 조건을 빠뜨려 합류자 본인에게도 알림이 감
- **초기 진단은 리더 리뷰로 더 깊어짐**: 단순 파라미터 교체가 아니라, `sub_type`이 계약과 안 맞는 `JOIN_REQUEST`를 오용 중이었다는 게 드러남(`#91`) — 계약 §13에 `MEMBER_JOINED`(신설)·`JOIN_ACCEPTED`(기존, 미구현) 둘 다 정확히 안 맞았음
- 계약 PR(`web-design-repository#24`, 리더가 직접 작업)로 `MEMBER_JOINED` 신설 확정 후, `InviteMapper.insertJoinNotifications`(중복 SQL) 삭제하고 공용 `NotificationService.fanOut`으로 교체 — actor 수정 + 본인 제외 + subType 세 가지를 한 번에 해결
- `#90`·`#91`을 한 PR(`#112`)로 묶음 — 같은 3줄짜리 호출 지점이라 분리하면 같은 코드를 두 번 건드리게 됨(리더도 동의)
- `InviteIntegrationTest`의 알림 개수 단언을 버그 전제(2, 본인 포함) → 수정 후 기대값(1, actor=신청자)으로 갱신, `recipient_id`·`actor_id`·`sub_type`까지 못박아서 회귀 방지

## 3. clov-api #113 — JOIN_ACCEPTED 신설 (+ 사고 정정)

`#112` 리뷰에서 리더가 지적: 본인 제외 조건이 정확히 적용되면서 **합류한 사람 본인은 이제 아무 알림도 못 받는** 빈자리가 생김 — 계약이 정의한 `JOIN_ACCEPTED`(신청자 본인에게, actor=수락자)가 구현이 0건이었기 때문.

- `MEMBER_JOINED` 팬아웃 직후 `notifyOne`으로 `JOIN_ACCEPTED` 1건 추가 — actor는 `MEMBER_JOINED`와 정반대(수락자)라는 게 계약이 둘로 나눈 이유
- undo 시 두 알림을 되돌리는 로직은 추가 안 함 — 기존에도 알림 보존이 기본 동작이었다는 기존 코드 패턴과 일관되게 진행(질문 대신 근거를 남기고 진행, 리뷰에서 동의받음)

**사고**: `#112`가 squash 머지된 뒤, 스택 브랜치(`#113`의 PR #114, base=`#112`의 브랜치)를 열었는데 리더가 머지하면서 **`main`이 아니라 그 스택 브랜치 자체로 병합**돼버림 — `main`엔 반영이 안 된 상태였다. 다행히 `Closes #113`이 기본 브랜치가 아닌 곳에 머지돼서 이슈가 자동으로 안 닫혀 데이터 유실은 없었음. 같은 브랜치를 `main` 위로 rebase해서 PR `#115`를 새로 열어 정상 반영·머지 완료. **교훈**: 스택 PR을 쓸 땐 머지 후 반드시 `main`에 실제로 들어갔는지 `git show origin/main:<file>`로 직접 확인할 것 — "머지됨" 표시만 믿으면 안 된다.

## 4. clov-web #225 — 알림 문구 MEMBER_JOINED/JOIN_ACCEPTED 케이스

- `Notifications.jsx messageFor`에 두 subType 케이스 추가
- 리더 리뷰로 우선순위 정정: `Notifications.jsx`는 JOIN 탭에서 알림을 아예 안 불러와서(`enabled: activeTab !== 'JOIN'`), 실제로 사용자 눈에 닿는 화면은 `RoomPreviewModal`(소식 피드)이었음 — `type`만 보고 문구를 고르던 걸 `subType` 분기로 교체하는 게 더 급했다고 지적받아 그쪽부터 수정
- 리뷰 후속: 알 수 없는 JOIN subType(옛 `JOIN_REQUEST` 데이터, actor가 잘못 박혀있음) 폴백을 "님이 합류했어요"(확신 있게 틀림)에서 다른 알림들과 같은 공용 기본 문구(모호하게 틀림)로 변경

## 5. clov-web #230 — JoinRoom `.proto.css` 리팩터

인증 화면 4개(`Login`·`Signup`·`OAuthRedirect`·`JoinRoom`) 중 `Login`(`#150`)에 이은 두 번째. 계획 문서를 먼저 만들어 소→대(JoinRoom→OAuthRedirect→Signup) 순서로 진행하기로 합의 후 착수.

- 목업(`join_room.html`)과 현재 코드의 CSS 변수 이름이 완전히 다른 걸 발견 — 착수 전에 이슈에 남겼고, 리더가 "현재 코드(전역 `tokens.css`)가 정본, 목업은 레이아웃만 참고"로 확인해줌(Login과 같은 전역 토큰 체계를 이미 쓰고 있었음)
- 의도적으로 안 한 것 둘: box-sizing 리셋 추가(현재 content-box로 이미 정상 렌더링 중이라 리셋을 넣으면 오히려 레이아웃이 바뀜), `Title`(h1)에 font-family 지정(지금도 전역 h1 리셋이 이미 적용된 채로 렌더링 중이라 그대로 두는 게 "전과 동일"에 맞음) — 둘 다 #150에서 겪은 함정을 반대 방향으로 피한 사례
- 전/후 스크린샷 3종(데스크톱 라이트/다크·모바일) + `getComputedStyle` 값 비교로 픽셀 동일 확인
- 리뷰 대기 중
