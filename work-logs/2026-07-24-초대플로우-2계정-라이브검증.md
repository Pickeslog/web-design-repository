| # | 단계 | 결과 | 확인 포인트 |

## 4. 검증 중 발견한 새 버그 → 수정 (clov-web #76 / PR #77 머지)

### 증상
신청을 **수락한 사람(A)** 화면에서 대시보드 `참여 멤버 N명`·멤버 목록·아바타가 그대로.
새로고침하면 그제서야 늘어남. (서버는 정상 — 수락 API 200, 멤버 ACTIVE 생성됨)

### 원인
`Notifications.jsx`의 `invalidate()`가 `['notifications', roomId]`·`['joinRequests', roomId]`만 무효화.
**멤버 구성이 바뀌는 처리(수락·되돌리기)인데** 방 상세(`['room', roomId]` = 인원수)·
멤버 목록(`['room', roomId, 'members']`)·방 목록(`['rooms']`) 캐시는 stale로 남았다.

### 수정
수락·되돌리기 전용 `invalidateMembership()` 추가 = 기존 무효화 + `['room', roomId]` + `['rooms']`.
`['room', roomId]`는 TanStack Query **접두 일치**라 `members`·`level` 하위 키까지 함께 갱신된다.
거절은 멤버 구성이 안 바뀌므로 기존 `invalidate()` 유지.

### 확인
수락 직후 **새로고침 없이 3명 → 4명**(아바타 4개)으로 갱신. lint/build·CI 초록.
머지: clov-web main `7e5f72c`.

## 5. 교훈

- **같은 사건이라도 "누구 화면이냐"를 나눠서 봐야 한다.** #73은 *신청자* 쪽 갱신(RoomList 폴링)만 고쳤고,
  *수락자* 쪽 캐시 갭은 그대로 남아 있었다. 양쪽 시점을 다 재현해야 끝난 것.
- **캐시 무효화는 "무엇이 바뀌었나" 기준으로 묶어라.** 알림 읽음과 멤버 수락은 영향 범위가 다른데
  같은 `invalidate()`를 공유하고 있었던 게 갭의 원인.
- **API 통과 ≠ 화면 정상.** 이번에도 서버는 200이었고 문제는 프론트 캐시였다.
  (7/22 크래시 건과 같은 결 — 백엔드가 검사상 정상이면 프론트부터 의심)
- **한 PC 2계정 테스트**: 토큰이 `localStorage`(`clov-auth`)라 **같은 브라우저 프로필 안에선 창을 여러 개
  띄워도 세션은 하나**다. 나중에 로그인한 계정으로 열려 있던 창까지 바뀐다(앱 버그 아님).
  → **Chrome 프로필 분리(사람 추가)** 권장(소셜 로그인도 계정별로 갈림) · 일반창+시크릿창 · 다른 브라우저.
  자동화 검증은 **순차 로그인**으로 우회 가능.
- **PowerShell 5.1로 API 검증 스크립트를 쓸 때**:
  `-SkipHttpErrorCheck` 없음(try/catch + `$_.Exception.Response`) ·
  스크립트 파일은 **UTF-8 BOM**이어야 한글 리터럴이 안 깨짐 ·
  `$resp.Content`는 응답에 charset이 없으면 ISO-8859-1로 디코딩하므로
  `RawContentStream`을 UTF-8로 직접 디코딩해야 한글이 정상으로 보인다.
  (서버 응답 `Content-Type: application/json`에 charset이 없지만 JSON 기본이 UTF-8이라 브라우저·axios는 정상)
