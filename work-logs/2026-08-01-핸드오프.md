### ⚠️ 팀원 3명 deploy 브랜치는 보류하기로 했다

```
api/deploy-myeongjun   behind=0 ahead=0   ✅ 배포 완료
api/deploy-lami        behind=8 ahead=0   ← FF 가능
```

## 3. ★ 프론트 CD 완성 (#182) — 첫 배포까지 성공

`clov-web`에 자동배포가 붙었다. `deploy-myeongjun`에 push하면 빌드→Docker Hub→VM 배포가 자동으로 돈다.

### 리뷰에서 2건 고쳐서 머지했다

- **헬스체크 추가** — `up -d` 뒤 `http://localhost/`를 4초 간격 30회(120초)까지 재시도. 없으면 compose 로그 50줄 찍고 실패. **가이드 21 §4의 "초록불 ≠ 서비스 정상"을 이 워크플로에서는 성립하게 만들었다.** 첫 배포에서 `웹 응답 확인 OK (1회차)`
- **`REACT_ENV`를 필수 → 선택** — 팀 공용 서버로 배포하는 사람은 등록할 이유가 없는데 강제돼 있었다. 없으면 레포 `.env.production`으로 빌드하고 `::warning::`과 함께 **실제 구워질 도메인을 찍는다**

**API 워크플로가 4번 실패하며 배운 3건은 이미 물려받은 상태였다** — 시크릿 사전 검증 · 이미지 이름 확인 · `compose down` 제거.

### 첫 배포에서 밟은 함정 4개 (다음 사람도 밟는다)

**① `push origin origin/main:deploy-X`는 로컬에 캐시된 `origin/main`을 민다**

`#182`를 머지한 직후라 로컬 `origin/main`이 옛날 것이었고, **워크플로 파일이 없는 커밋이 올라가 아무 일도 안 일어났다.** 에러도 안 난다. → **`git fetch origin`을 먼저 붙일 것.**

**② 브랜치를 처음 만들 때는 목적지를 완전한 이름으로**

```bash
git -C clov-web push origin origin/main:refs/heads/deploy-myeongjun
```

`:deploy-myeongjun`로 쓰면 *"not a full refname"* 으로 거부된다(원격에 그 브랜치가 없어서 git이 새로 만들지 판단 못 함). 한 번 생기면 짧은 형태로 된다.

**③ 시크릿은 레포마다 따로다**

`clov-api`에 24개가 있어도 `clov-web`은 전혀 못 본다. **같은 VM에 배포해도 다시 등록해야 한다.**

**④ ★ 이름에 `_<본인>` 접미사가 반드시 붙어야 한다**

`GCP_VM_HOST`가 아니라 **`GCP_VM_HOST_MYEONGJUN`**이다. 한 레포에서 4명이 각자 VM에 배포하므로 워크플로가 브랜치 이름을 보고 `..._MYEONGJUN`을 고른다. 접미사가 없으면 **어느 조건에도 안 걸려 전부 빈 값**이 된다.

> 이번에 실제로 접미사 없이 등록해서 한 번 헛돌았다. **이름만 나열하지 말고 "왜 필요한지"를 먼저 말해야 한다** — 형식처럼 보이면 사람은 단순화한다.

**필요한 건 5종이다**(`REACT_ENV_*`는 선택). `clov-api`의 6번째 `APPLICATION_SECRET_*`은 현재 워크플로가 쓰지 않는다.

### ⚠️ 개인키를 지우면 다른 레포에 못 넣는다

가이드 21 §2-2 ⑥이 "개인키 파일은 지운다"고 하는데, 그대로 지웠더니 **`clov-web`에 넣을 때 꺼낼 방법이 없었다**(GitHub·Docker Hub 둘 다 등록 후 값을 안 보여준다).

→ **새 키를 만들어 GCP 메타데이터에 추가**해서 해결했다. **메타데이터는 키를 여러 개 갖는다** — 기존 키가 살아 있어 `clov-api` 배포는 안 깨졌다. VM에서 확인:

```
4096 SHA256:PGRZsTa... bubaragi23 (RSA)   ← 학원에서 만든 것
4096 SHA256:LKaFaHl... bubaragi23 (RSA)   ← 이번에 추가
```

**지울 때는 "필요한 곳에 전부 넣은 다음"으로 문구를 고치는 게 맞다.**

## 6. #92 — 충돌 해소본을 만들어 넘겨놨다 (여전히 크리티컬 패스)

`#92`가 `CONFLICTING`인 원인을 찾았다. **브랜치가 상점 백엔드 전체를 들고 있는데 그건 이미 #99로 main에 있다.**

```
브랜치가 건드린 파일   27개
그중 main도 건드린 것   25개   ← rebase하면 전부 충돌
```

`git log`로는 안 보인다 — `#99`가 스쿼시 머지라 SHA가 갈라져 "안 들어간 것"처럼 보인다. **§9의 "`git log A..B`는 '앞선 커밋'이지 '같다'가 아니다"가 정확히 이 상황이다.**

### 해소안: rebase 말고 델타 재적용

진짜 새로운 건 골드 지급 3개 커밋(`c9c3065`·`711b2e6`·`4d9c09e`), **9개 파일 `+104/-8`**뿐이다.

```bash
git diff 5329b86 origin/feat/89-gold-earn > gold.patch
git checkout -B <새브랜치> origin/main
git apply --3way gold.patch
```

**6개는 그대로 붙고 3개 파일에서 충돌 4군데만 남는다.** cherry-pick으로 3개를 순서대로 얹는 것도 해봤는데 중간 상태를 거쳐 충돌이 더 났다 — **델타를 한 번에 얹는 쪽이 깔끔하다.**

충돌 4군데는 전부 **"main 쪽을 살리고 새 줄만 추가"** 다. 분기 후 `#100`이 같은 자리를 고쳤기 때문.

> ⚠️ **`MemoryService.java`에서 "theirs"를 통째로 받으면 `MAX_IMAGES_PER_MEMORY`가 8 → 10으로 되돌아간다.** 프론트는 이미 8이라 **9번째 사진부터 507이 나던 버그가 부활한다.**

**결과물: [`chore/92-conflict-resolved`](https://github.com/Pickeslog/clov-api/tree/chore/92-conflict-resolved) (`f695921`)** — 최신 main 위, 9개 파일 `+99/-3`, **컴파일·Testcontainers 통합테스트 모두 통과**([run 30690779637](https://github.com/Pickeslog/clov-api/actions/runs/30690779637)). 곁가지로 **`4d9c09e`가 main의 불안정한 필터식 jsonPath를 고친다** — main엔 아직 남아 있다.
