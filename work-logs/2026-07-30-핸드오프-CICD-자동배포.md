## 2. ★ 실패 원인이 사람마다 전부 달랐다

같은 워크플로, 같은 시크릿 구조인데 **세 사람이 세 군데서 막혔다.** 이게 이번 작업의 핵심 교훈이다.

### 2-1. 명준 — GCP 게스트 에이전트가 키를 지운다

`ssh: handshake failed ... [none publickey]` 가 계속 났다. 원인이 **네 겹**이었다.

1. 시크릿에 옛 2048비트 키가 들어 있었다(주석도 `bubargi23` — `a` 하나 빠짐)
2. VM에 등록된 키가 없었다
3. `~/.ssh/authorized_keys`에 손으로 넣었는데 **4분 만에 사라졌다** (07:28 등록 → 07:32 `~/.ssh` 텅 빔)
4. 시크릿을 고쳤다고 생각했는데 안 고쳐져 있었다

**3번이 제일 찾기 어려웠다.** GCP 게스트 에이전트가 **인스턴스/프로젝트 메타데이터에 등록된 키만 남기고** `authorized_keys`를 주기적으로 다시 쓴다. 손으로 추가한 줄은 지워진다.

→ **공개키는 GCP 콘솔의 인스턴스 메타데이터에 넣어야 한다.** 그러면 에이전트가 `authorized_keys`를 **써 준다**.

부수적으로 **공개키 맨 뒤 주석이 리눅스 사용자명으로 해석된다.** `-C "<whoami 결과>"`를 정확히 넣어야 한다.

### 2-2. 라미 — 한 줄 시크릿에 개인키를 넣었다

**첫 스텝**(`환경변수 세팅`)에서 죽었다. 빌드조차 시작 안 했다.

```
##[error]Unable to process file command 'env' successfully.
##[error]Invalid format '***'
```

렌더된 스크립트를 뜯어보니 라미 블록에서 `GCP_VM_HOST=***` 가 **27줄로 펼쳐져 있었다.** `GCP_VM_SSHKEY_LAMI`에 넣을 개인키를 `GCP_VM_HOST_LAMI`에 넣은 것이다.

`GCP_VM_SSHKEY`만 heredoc이고 나머지 5개는 한 줄 `echo "NAME=값" >> $GITHUB_ENV`다. 값에 줄바꿈이 있으면 `$GITHUB_ENV`에 **`=`가 없는 줄**이 생겨 죽는다.

> **첫 스텝에서 실패하면 100% 이 문제다.**

### 2-3. 규비 — 키가 VM에서 거부됐다

빌드·push까지 다 성공하고 SSH만 실패. `Setup SSH Key` 지문이 `2048 SHA256:jNe6aiC3...`였고 **뒤 사용자명이 `***`로 마스킹**돼 있었다 → 주석이 `GCP_VM_USERNAME_KIMGYUBI` 값과 일치한다는 뜻이라 사용자명은 문제가 아니었다. 남은 건 "VM에 이 키가 없다"뿐이어서 §2-1 절차로 해결됐다.

## 3. ★★ 진단 기법 — 다음에 또 쓸 것

이번 작업의 가장 값어치 있는 산출물은 워크플로가 아니라 **원인을 좁히는 방법**이다.

### 3-1. `Setup SSH Key` 스텝의 지문 한 줄

```
2048 SHA256:+cRbmnW4Ufev9gJKtdNFI9tXAP/cS4C+2gdhAFJjj/Y bubargi23 (RSA)
```

**GitHub 시크릿은 읽을 수 없다.** 이 한 줄이 시크릿에 실제로 무엇이 들었는지 알 수 있는 **유일한 창**이다.

- **비트수** — 4096으로 만들었는데 2048이 찍히면 시크릿에 옛 키가 있다
- **뒤 사용자명** — 오타면 키 생성 시 `-C`가 틀렸다
- VM의 `ssh-keygen -lf ~/.ssh/authorized_keys` 결과와 **`SHA256:` 값을 대조**하면 짝이 맞는지 확정된다

> 이 스텝은 기능상 **죽은 코드**다 — `appleboy/ssh-action`은 `with.key`만 읽고 러너의 `~/.ssh`는 보지 않는다. 그런데 진단 가치 때문에 남겼고, 차차가 #95에서 **`|| echo`로 통과하던 걸 실제로 끊게** 고쳤다.

### 3-2. 렌더된 스크립트의 `***` 줄 수

Actions 로그의 `Run ...` 접힌 블록을 펼치면 시크릿이 `***`로 치환된 **실행 스크립트 전문**이 보인다.

**한 줄 시크릿이 여러 줄로 펼쳐져 있으면 그게 원인이다.** 라미는 이걸로 잡았다 — 다른 세 명 블록은 `GCP_VM_HOST=***`가 한 줄인데 라미만 27줄이었다.

### 3-3. 끝 줄바꿈은 통과한다 — 오진 주의

`DOCKER_USERNAME_MYEONGJUN`에 **끝 줄바꿈이 있는데도 배포가 성공했다.** `$GITHUB_ENV`는 빈 줄을 무시한다.

**값이 있는 줄에 `=`가 없을 때만 죽는다.** "빈 줄 보이네, 이게 원인이겠다"고 오진하지 말 것.

내가 "나중에 하자"고 미뤄둔 항목들을 차차가 직접 잡았다. **main `60d8356`에 들어가 있다.**

| 개선 | 내용 |
|---|---|
| **배포 시크릿 검증** | 값이 비었는지·개인키로 파싱되는지 첫 단계에서 끊는다. 이름 접미사까지 에러 메시지에 찍어준다 |
| **VM compose 이미지 이름 대조** | 이름이 다르면 `pull`이 "성공"하며 옛 이미지를 다시 띄우고 초록불이 된다. SSH 스크립트에서 `grep`으로 먼저 확인 |
| **`down` 제거** | VM에서 api·web·certbot이 같은 compose 프로젝트 네트워크를 공유한다. `down`이 그 네트워크까지 지우려 들다 실패하고, `script_stop` 때문에 거기서 끊기면 **컨테이너는 지워졌는데 다시 안 뜬다** |
| **`ssh-action` v1.0.3 → v1.2.5** | `script_stop: true`, `port`, `timeout`, `command_timeout` 추가. `pull` 실패 시 뒤 명령이 안 돌게 |

`down` 문제는 내가 차차 배포 로그에서 본 경고(`Network ... Resource is still in use`)와 같은 건이다. 차차가 자기 VM에서 직접 겪고 고쳤다.

## 6. clov-web #182 — 프론트 워크플로 (머지 대기)

clov-api의 `main.yml`(`60d8356`)을 **그대로 옮기고 프론트 부분만** 바꿨다. 스텝 순서·시크릿 이름 규칙·브랜치 분기 방식은 동일하다.

| 바꾼 것 | 왜 |
|---|---|
| `REACT_ENV_<이름>` 시크릿 추가 | 사람마다 백엔드 주소가 다르다 |
| **`환경파일 주입` 스텝 신설** | 아래 ★ |
| 검증 목록에 `REACT_ENV` 추가 | 비어도 빌드가 성공해 조용히 깨진다 |
| `springboot-app` → `react-app` | 강사님 원본의 React 이미지 이름과 동일 |
| `api-docker-compose.yaml` → `web-docker-compose.yaml` | |
| `Springboot Build` → `React Build` | |

### ★ api에서 뺀 주입 스텝이 프론트에는 필요하다

백엔드는 시크릿을 이미지에 넣지 않고 VM의 `/app/application-secret.yaml`을 **런타임에 마운트**한다. 그래서 #93에서 강사님 원본의 주입 줄을 뺐다.

프론트는 그럴 수 없다. **Vite는 `VITE_*`를 빌드 시점에 번들 문자열로 치환**하므로 컨테이너를 띄울 때 바꿀 방법이 없다. 그대로 빌드하면 레포의 `.env.production`(팀 공용 도메인)이 박혀 **팀원 4명 프론트가 전부 리더 백엔드를 호출한다.**

**강사님 원본의 `REACT_ENV` 방식을 그대로 되살렸다.**

```yaml
echo "${{env.REACT_ENV}}" | base64 --decode > .env.production
```

env 변수가 늘어도 워크플로를 안 고쳐도 되는 게 이 방식의 장점이다.

### 원본과 딱 한 군데 다르다 — 푸는 파일 이름

**`.env`가 아니라 `.env.production`이다.** 우리 레포에서 `.env`는 **두 번 무력화된다.**

1. `.dockerignore`가 `.env`를 빌드 컨텍스트에서 뺀다
2. 들어가도 **Vite는 모드 파일(`.env.production`)을 범용 파일(`.env`)보다 우선**한다

둘 다 결과가 같다 — 팀 도메인이 그대로 구워지고 **워크플로는 초록불**이다. 강사님 프로젝트엔 `.env.production`이 없어서 `.env`로 충분했고, 우리는 #160·#170 겪으면서 그 파일이 생겼다.

덮어쓰는 건 **러너의 임시 체크아웃뿐이고 레포 파일은 그대로다.** 그 사실을 `.env.production` 파일 안에도 적어 뒀다(#170이 그 파일을 커밋으로 고쳐서 난 사고다).

### 시크릿 인코딩 — 반드시 한 줄

```bash
echo "VITE_API_BASE_URL=https://내도메인/api/v1" | base64 | tr -d '\n'
```

**`tr -d '\n'`이 없으면** `base64`가 76자마다 줄을 바꿔서 **여러 줄이 되고, §2-2와 똑같이 첫 스텝에서 죽는다.** 왕복 테스트는 해 뒀다.

디코드 가드도 넣었다 — `VITE_API_BASE_URL` 줄이 없으면 끊고 올바른 명령을 에러로 출력한다. 없으면 빈 파일로 빌드가 성공하고 `localhost:8080`이 번들에 박힌다(#160).

### 검토했지만 보류한 대안

`VITE_API_BASE_URL=/api/v1`(상대경로)로 가면 도메인이 번들에서 사라져 **이미지 하나로 4명이 다 되고 #170 유형이 원천 봉쇄**된다. 코드도 받쳐준다 — `client.js:11`의 `oauthAuthorizeUrl`이 빈 `apiOrigin`을 붙여 `/oauth2/authorization/<provider>`가 되고, 호스트 nginx가 `/api/`·`/oauth2/authorization/`·`/login/oauth2/`를 모두 프록시한다(`clov-api/deploy/nginx-clovlabcalss.conf`).

**전제는 "모든 VM에 앞단 nginx가 있다"다.** web 컨테이너가 80을 직접 잡은 VM이 있으면 상대경로가 컨테이너 내부 nginx로 가서 프록시 없이 404다(07-28에 밟은 함정). 4대가 균일하다는 보장이 없어 **별도 이슈로 남긴다.**

## 8. 오늘 나온 교훈

1. **초록불 ≠ 서비스 정상.** `up -d`는 즉시 반환하고 이 VM에서 Spring 부팅은 **185~208초**다. 헬스체크가 없어서 부팅 실패해도 워크플로는 초록불이다. 프론트는 nginx라 즉시 뜨므로 이 문제가 없다
2. **조용한 실패가 실패보다 나쁘다.** 이미지 이름 불일치는 `pull`이 성공하며 옛 이미지를 다시 띄운다. 차차가 #95에서 끊게 만들었다
3. **검증 없이 4명 동시에 열면 3명이 각자 다른 데서 막힌다.** 오늘 실제로 그랬다. **한 명 검증 후 확산**이 맞다
4. **시크릿은 개수가 아니라 값이다.** 24개가 다 있어서 "다 있는걸?" 했는데 오타 2건·잘못된 칸 1건·옛 키 1건이 있었다
5. **읽을 수 없는 값은 간접 증거로 확인한다.** GitHub 시크릿은 못 읽으니 지문·줄 수로 판별한다(§3)
6. **팀원이 리더보다 먼저 고칠 수 있다.** #95는 차차가 내가 미뤄둔 걸 직접 잡았다. 미룬 항목을 공개해 두면 누가 집어간다
