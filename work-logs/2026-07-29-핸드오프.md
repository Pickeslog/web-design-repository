## 3. 계약 §4-4 — 되돌리면 안 되는 결정 4개

### ★ (1) 실패는 401이 아니라 **400**이다

프론트 `api/client.js`의 응답 인터셉터가 **401을 받으면 `/auth/refresh`를 시도**한다(07-28 #159로 single-flight를 넣은 그 코드).

401로 두면 → 비로그인 상태인데 갱신을 부르고 → 실패해 토큰을 `clear()` → 사용자에겐 "만료된 링크"가 아니라 알 수 없는 동작으로 보인다.

refresh 계열(`INVALID_TOKEN`·`TOKEN_EXPIRED`)이 401인 것과 **다른 이유가 이것**이라, `ErrorCode`와 계약 양쪽에 근거를 주석으로 박아 뒀다. **"일관성 없다"며 401로 바꾸지 말 것.**

### (2) 계정 열거 방지는 **세 곳**을 다 막아야 한다

하나만 빠져도 나머지가 무의미해진다.

| 곳 | 조치 |
|---|---|
| 본문·상태코드 | 없는 이메일 / 소셜 전용(`password` NULL) / 정상 계정이 **전부 `200 data:null`** |
| 타이밍 | SMTP 발송이 `@Async`. 동기면 계정이 있을 때만 느려져 **응답 시간이 곧 계정 존재 여부** |
| 속도 제한 | 계정 존재 여부와 무관하게 **이메일 문자열만으로** 센다. 존재하는 계정만 제한하면 "제한에 걸렸다 = 그 계정이 있다" |

**프론트도 같다** — "가입되지 않은 이메일입니다" 같은 분기를 넣으면 백엔드 방어가 그대로 무너진다.

### (3) 토큰을 URL 쿼리로 넘기는 것은 §4-2 금지 규칙의 **명시된 예외**

메일 링크라 다른 수단이 없다. 상쇄 근거 셋(수명 1시간·1회용·권한이 재설정 하나뿐)을 계약에 함께 적었다. `api/auth.js` 주석에도 남겼다.

### (4) 가입 시 이메일 인증이 없는 점은 **의도된 동작**

남의 이메일로 가입된 계정이 있으면 실제 이메일 주인이 재설정으로 통제권을 가져갈 수 있다. 원래 그 이메일 주인에게 가는 것이 맞고, 재설정 기능이 사후 이메일 소유 확인 수단 역할을 한다. 가입 시 이메일 인증을 도입하면 재검토한다.

## 4. ★ 메일 발송 — `app.mail.mode`

| 값 | 동작 |
|---|---|
| **`log`(기본)** | 재설정 링크를 콘솔에만 출력. SMTP 설정이 없어도 부팅된다 |
| `smtp` | 실제 발송. `spring.mail.*` 필요 |

**설계안에서는 프로필로 가르기로 했다가(dev=로그/prod=SMTP) 속성 기반으로 바꿨다.** 프로필로 가르면 **메일 설정 없는 서버가 prod로 뜨는 순간 부팅이 깨진다** — 07-28에 `include: secret`을 빼면서 겪은 것과 똑같은 구조다. 기본값을 안전한 쪽에 두면 머지·배포해도 아무것도 안 깨지고, SMTP 계정이 생기면 **코드 수정 없이** `clov-api.env` 한 줄로 켜진다.

> ⚠️ **`APP_MAIL_MODE=smtp`와 `spring.mail.*`는 항상 같이 넣고 같이 뺀다.** 한쪽만 있으면 이렇게 죽는다(실제로 8099 포트로 재현해 확인했다):
> ```
> APPLICATION FAILED TO START
> Parameter 0 of method smtpMailSender ... required a bean of type
> 'org.springframework.mail.javamail.JavaMailSender' that could not be found.
> ```

**`client.url`의 첫 실사용처**가 이 기능이다. 07-28 #82에서 prod를 `https://`로 고쳤지만 읽는 코드가 없어 검증할 수 없던 값인데, 이제 메일 링크 베이스로 실제로 쓰인다.

## 6. DB — 마이그레이션은 적용했다

`clov-api/db/manual-migrations/2026-07-29-password-reset-tokens.sql` → **공유 개발 DB(`st4_clov`)에 적용 완료.** 개발·배포가 같은 학원 원격 DB라 배포 서버도 함께 반영된 셈이다.

반영처 3곳 전부 끝났다 — 정본 문서(#10) · `src/test/resources/schema.sql`(#85) · 개발 DB(수동).

### ★ 시크릿을 읽지 않고 마이그레이션을 적용하는 법

`application-secret.yaml`의 실제 값은 규칙상 읽지 않는다. **앱이 자기 자격증명으로 DDL을 실행하게** 하면 된다 — 커밋 파일은 안 건드리고 일회성 인자로만 넘긴다.

```bash
./gradlew.bat bootRun --args="--spring.sql.init.mode=always \
  --spring.sql.init.schema-locations=file:./db/manual-migrations/2026-07-29-password-reset-tokens.sql \
  --spring.sql.init.continue-on-error=false"
```

`continue-on-error=false`라 DDL이 실패하면 부팅이 멈춘다 = **부팅에 성공했으면 적용된 것**이다. `CREATE TABLE IF NOT EXISTS`라 재실행해도 안전하다.

## 7. 구현 메모 (다음에 비슷한 걸 만들 때)

- **`forgot`에는 `@Transactional`을 걸지 않았다.** 트랜잭션 안에서 메일을 보내면 **커밋 전에 비동기 발송이 나가** 사용자가 링크를 눌렀을 때 토큰이 아직 안 보일 수 있다. 폐기·발급이 원자적이지 않아도 "잘못된 링크가 살아남는" 방향의 실패는 안 생긴다. `reset`은 반대로 트랜잭션이다.
- **토큰 소모를 비밀번호 변경보다 먼저** 하고 영향 행이 1인지 확인한다. 0이면 그 사이 다른 요청이 같은 토큰을 썼다는 뜻이라 변경 없이 실패시킨다(동시 사용 차단).
- **속도 제한기는 인메모리다.** 단일 인스턴스 전제. 다중 인스턴스가 되면 `PasswordResetRateLimiter`만 공유 캐시로 갈면 된다.
- **프론트에 로그인 가드를 안 붙였다.** 붙였다면 #154의 `takeReturnTo()` 이중 소비를 다시 밟았을 자리다. 대신 재설정 성공 시 `authStore.clear()`로 로컬 토큰을 정리해 "반쯤 로그인된" 좀비 세션을 없앴다(서버가 이미 refresh를 전부 revoke했다).
- **새 화면은 Login의 변주로 만들었다.** `login.proto.css`를 같은 `.proto-login` 스코프로 재사용하고 `PasswordResetShell`로 묶었다. 덕분에 **`box-sizing` 리셋을 새로 깔 필요가 없었다** — 새 스코프를 팠다면 #153에서 34px 어긋남의 원인이던 그 리셋을 잊었을 자리다.
- **토큰 원문은 메일에만 있어 테스트가 API로 얻을 수 없다.** 통합테스트는 **발급된 행의 해시를 테스트가 아는 값의 해시로 갈아끼우는** 방식을 썼다. 서비스 입장에서는 구분할 수 없는 정상 토큰이라 만료·1회용·폐기 로직을 그대로 검증할 수 있다.

## 8. 오늘 밟은 함정 3개

- **Git Bash 인라인 `-d`가 한글을 깨뜨린다.** 한글 닉네임으로 가입하니 400이 났다. 07-28에 이모지로 겪은 것과 같은 함정이고 해법도 같다 — **`--data-binary @파일`**. **서버를 의심하기 전에 클라이언트를 의심할 것.**

## 12. 오늘 나온 교훈

- **★ 기본값은 "설정이 빠진 서버에서 무슨 일이 나는가"로 정한다.** 메일 모드를 프로필로 가르면 깔끔해 보이지만, 메일 설정 없는 서버가 prod로 뜨는 순간 부팅이 깨진다. 기본값을 안전한 쪽(`log`)에 두면 머지·배포가 아무것도 안 깨뜨리고, 켜는 것은 env 한 줄이 된다. **07-28 `include: secret` 제거와 같은 교훈의 반대편이다.**
- **★ 문서에 "이렇게 하면 실패한다"고 쓸 거면 실패시켜 보고 쓴다.** `JavaMailSender` 빈 없음으로 부팅이 깨진다는 경고를 세 곳에 달았는데, 8099 포트로 실제 재현해 에러 문구를 그대로 옮겼다. 추측으로 쓴 경고는 나중에 아무도 안 믿는다.
- **★ 방어는 층이 아니라 경로 단위로 뚫린다.** 계정 열거는 본문만 통일해선 안 되고 **타이밍과 속도 제한까지** 같이 막아야 한다. 그리고 백엔드를 다 막아도 **프론트가 "가입되지 않은 이메일입니다"를 띄우면 끝**이다.
- **에러 코드의 HTTP 상태는 클라이언트 인터셉터까지 보고 정한다.** 401이 "의미상 맞아 보인다"고 골랐다면 `client.js`가 refresh를 시도해 엉뚱하게 로그아웃됐을 것이다. 서버 혼자 정할 수 있는 값이 아니다.
- **비동기 발송과 트랜잭션을 같이 두면 커밋 전에 메일이 나간다.** "원자성"을 반사적으로 붙이기 전에 그 트랜잭션 안에 외부 호출이 있는지 볼 것.
- **새 화면을 만들 때 기존 화면의 스코프를 재사용하면 그 화면이 이미 해결한 것들을 함께 물려받는다.** `box-sizing` 리셋·목업과 맞춘 치수가 공짜로 따라왔다.
- **커밋 전 `git status --short`, 커밋 후 `git show --stat`.** 공유 워킹트리에서 오늘도 유효했다. 어제 파일이 섞이지 않은 것을 매번 확인했다.
