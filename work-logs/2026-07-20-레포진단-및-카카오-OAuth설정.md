## 1. 🔴 가장 중요 — 시크릿 파일이 Git 추적 대상이었다

`clov-api`에서 `application-secret.yaml`이 **`git add`된 상태(`A`)** 로 커밋을 대기하고 있었다.

```
A   src/main/resources/application-secret.yaml         ← 위험
A   src/main/resources/application-secret.example.yaml ← 정상
 M  .gitignore
 M  src/main/resources/application.yaml
```

`.gitignore`에는 아래처럼 **의도가 정확하게** 작성돼 있었다.

```gitignore
src/main/resources/application-secret*.yaml
!src/main/resources/application-secret.example.yaml
```

**그런데 작동하지 않는다.** `.gitignore`는 *아직 Git이 추적하지 않는 파일*에만 적용된다. 한 번 `git add`된 파일은 이미 추적 대상이라 `.gitignore`에 뭘 써도 무시되지 않는다.

- **현재 피해 없음** — 그 파일이 0바이트라 유출될 내용이 없다.
- **위험 시점은 지금부터** — 바로 다음 작업이 "이 파일에 DB 비밀번호 + 카카오·네이버·구글 시크릿 채우기"다. 채우고 커밋하면 그대로 공개된다.
- **처리**: 코덱스의 협업 하네스 PR에 "시크릿 파일 Git 추적 정책 정리" 항목으로 포함. 그 전까지 **키를 파일에 넣지 않기로** 함.

> 교훈: `.gitignore`를 나중에 추가하면 이미 add된 파일은 안 걸러진다. 시크릿 파일은 **만들기 전에** ignore부터 넣는다.

## 4. 강사님 협업 가이드 ↔ Clov 적용 차이

강사님 가이드는 일반 교육용이라 Clov의 확정 제약과 충돌하는 부분이 있다. **팀원이 그대로 AI에 시키면 사고 나는 순서**로 정리.

### 🚨 그대로 쓰면 안 되는 것

| 항목 | 강사님 | Clov | 왜 |
|---|---|---|---|
| **`role` 컬럼** | `users.role` + JWT `role` claim | **없음. 금지** | 계약 §3 "방장/역할 없음". 멤버 전원 동등이 서비스 핵심 원칙. 템플릿으로 주면 AI가 role을 만들어냄 |
| **Spring Boot** | 3.x | **4.0.7** | starter 이름이 다름(`starter-web`→**`starter-webmvc`**), MyBatis `3.0.4`→**`4.0.1`**. 그대로 붙이면 의존성 안 잡힘 |
| **API 경로** | `/api/auth/login` | **`/api/v1/auth/login`** | 계약 §2 base path |
| **계약 파일 복사** | 양쪽 레포에 복사 | **SSOT 1개 + 포인터** | §3 참조 |
| **커밋 규칙** | `feat: 요약` | `요약 (#12)` | §3에서 병합 결정 |

### ✅ 그대로 채택

- `AGENTS.md` 원본 + `CLAUDE.md` 포인터 패턴 → **roadmap §7-3 미결 사항이 이걸로 확정됨**
- `ApiResponse` / `GlobalExceptionHandler` 구조 — 우리 `{success,data}` 봉투와 정확히 일치. **M0 #2에 그대로 사용 가능**
- MyBatis 7원칙 (`#{}` 바인딩 · entity≠DTO · JPA 금지)
- jjwt 0.12.x 신 API (`subject()`/`expiration()`)
- `map-underscore-to-camel-case` — 이미 적용돼 있음

### 발견된 누락

`build.gradle`에 **jjwt 의존성이 없다.** 계약 §1이 `jjwt 0.12.x`를 명시하는데 빠져 있어 M0 #3(Security+JWT) 착수 시 바로 걸린다.

```gradle
implementation 'io.jsonwebtoken:jjwt-api:0.12.6'
runtimeOnly  'io.jsonwebtoken:jjwt-impl:0.12.6'
runtimeOnly  'io.jsonwebtoken:jjwt-jackson:0.12.6'
```

**등록한 Redirect URI (3사 공통 규칙)**

```
http://localhost:8080/login/oauth2/code/kakao
http://localhost:8080/login/oauth2/code/naver
http://localhost:8080/login/oauth2/code/google
```

`{백엔드주소}/login/oauth2/code/{registrationId}` — Spring Security가 자동 생성하는 경로다. `clov-api`에 `server.port` 설정이 없어 **8080**.

> ⚠️ `application.yaml`의 `app.oauth2.redirect-url: http://localhost:5173/oauth2/redirect`는 **완전히 다른 값**이다. 로그인 성공 후 백엔드가 JWT를 들고 프론트로 되돌려보내는 주소이고, 콘솔에 등록하는 값이 아니다. 이름이 비슷해 섞기 쉬움.

**팀원 로그인 허용은 3사 모두 별도 등록이 필요하다.** 소유자가 자동 통과되는지는 제각각이라 아래 표로 정리.

| | 소유자 자동 로그인 | 팀원 등록 위치 |
|---|---|---|
| 카카오 | ✅ | 앱 → 멤버 |
| 네이버 | ✅ (관리자는 등록 불필요) | 멤버관리 → **테스터 ID**(최대 20) |
| 구글 | ❌ **본인도 등록 필요** | 대상 → 테스트 사용자(최대 100) |

내일 팀원에게 **카카오계정 · 네이버 아이디 · Gmail 3종을 한 번에** 받는다. 따로 물으면 두 번 일이 됨.

### 5-1. 카카오

대상: **`Clov-TEST`** (테스트 앱 · 비즈 앱 · 원본 `Clov`에서 파생)

| 항목 | 위치 | 상태 |
|---|---|---|
| 동의항목 닉네임·프로필사진·이메일 | 제품 설정 → 카카오 로그인 | ✅ 필수 동의 |
| 동의항목 `name` | 〃 | ✅ **제거** |
| Client Secret | 카카오 로그인 → 보안 | ✅ 활성화 **ON** |
| Redirect URI | 앱 → 플랫폼 키 → **REST API 키** | ✅ `http://localhost:8080/login/oauth2/code/kakao` |
| JavaScript SDK 도메인 | 앱 → 플랫폼 키 → JavaScript 키 | ✅ `http://localhost:5173`·`:8080` |
| 팀원 초대 | 앱 → **멤버** | ⏸ 내일 (계정 수집 후) |
| 시크릿 재발급 | 카카오 로그인 → 보안 | ⏸ 보류 |

### 해소된 리스크

착수 전 최대 우려는 **카카오 이메일 수집 차단**이었다. `users.email`이 `NOT NULL`인데 카카오는 이메일 동의항목이 기본 잠금이라, 막히면 소셜 가입 설계를 바꿔야 했다.

→ **두 앱 모두 "비즈 앱"으로 전환돼 있어 해소.** 추가로 `Clov-TEST`는 테스트 앱이라 "원본 앱 권한 자동 동기화 + 테스트용 추가 권한"이 적용돼, 개발 중 동의항목으로 막힐 일이 사실상 없다.

### 콘솔 구조 관련 메모

카카오가 콘솔을 개편해 **기존 안내 문서의 메뉴 경로가 대부분 맞지 않는다.** 검색으로 나오는 글은 옛 구조 기준이니 주의.

| 기능 | 현재 위치 |
|---|---|
| REST API 키 · Redirect URI | 앱 → **플랫폼 키** → REST API 키 |
| 팀원 초대 | 앱 → **멤버** |
| 사이트 도메인 | 앱 → **플랫폼 키** → JavaScript 키 (`앱 → 일반`에 플랫폼 섹션 **없음**) |

- 플랫폼 키마다 "카카오 로그인 리다이렉트 URI" 칸이 **각각** 있다. Spring이 `client_id`로 REST API 키를 쓰므로 **REST API 키 쪽에 등록**한다.
- JavaScript SDK 도메인 미등록 경고는 무시 가능 — 우리는 서버사이드 OAuth라 JS SDK를 쓰지 않는다.

### 백엔드 구현 시 반영할 것

- **Client Secret이 ON이므로 Spring 설정에 `client-secret` 필수.** 누락 시 `invalid_client`
- 이메일 필수 동의라도 미인증 계정은 값이 안 올 수 있음 → `users.email`이 `NOT NULL`이라 500 대신 **`400 OAUTH_EMAIL_REQUIRED`** 로 막는 방어 코드 필요
- 카카오 `user-name-attribute: id` → `users.oauth_subject`에 저장
- REST API 키 화면의 "호출 허용 IP"는 **비워둔다** (팀원이 각자 다른 네트워크에서 개발)

### ⚠️ 보안 메모

콘솔 확인 과정에서 **클라이언트 시크릿 2개와 REST API 키가 가려지지 않은 스크린샷으로 노출됨.** 코드에 반영되기 전이라 재발급 비용이 0인 시점이므로 **재발급 권장**(보류 중). 이후 콘솔 화면 공유 시 값 마스킹 필요.

| Client ID / Secret | 개요 | ✅ 발급 |
| 테스터 ID 등록 | 멤버관리 | ⏸ 내일 |

**결정 — 회원이름 미수집**: 카카오 `name`과 동일. `users`에 대응 컬럼 없음. 네이버 화면도 "개인정보보호법 제3조 제1항·제16조 제1항에 따라 **필요한 최소한의 개인정보만**"을 명시하고 있어, 안 쓰는 실명을 필수로 받는 것은 근거가 없다.

**결정 — 생일/출생연도 미수집**: `users.birthdate`가 있어 받을 수는 있으나, 카카오에서 안 받기로 해 **소셜 종류별로 데이터가 갈린다.** 네이버는 생일(MM-DD)·출생연도(YYYY)가 분리돼 둘 다 받아야 온전한 날짜가 되는 부담도 있다. `birthdate`는 nullable이므로 소셜 가입자는 null로 두고, 필요 시 프로필 수정에서 입력받는다.

**결정 — 연결 끊기 콜백 미등록**: 네이버 → 우리 방향의 웹훅. 사용자가 네이버 쪽에서 연결을 끊거나 탈퇴할 때 호출된다. 우리 계약(§5)의 탈퇴는 `DELETE /api/v1/users/me` 하나뿐이고 **우리 앱에서 시작하는 흐름**이라, 받을 엔드포인트가 없다. 등록하면 404만 받는다.
→ 남는 공백: 사용자가 네이버에서 연결을 끊어도 우리 DB는 모른다. 다만 원칙이 "탈퇴=익명화, 기록 보존"이라 계정이 남아도 치명적이지 않아 **범위 밖으로 둔다.**

**멤버 관리 구조** — 네이버는 구글처럼 관리 권한과 로그인 허용이 **분리**돼 있다.

| | 뜻 | 대상 |
|---|---|---|
| 관리자 ID (최대 3) | 앱 **설정 변경** 권한 | 리더만. 팀 규칙상 계약·설정 변경은 리더 전용 |
| **테스터 ID (최대 20)** | '개발 중' 상태에서 **로그인 허용** | **팀원 3명** |

콘솔 안내: "관리자 아이디는 등록하지 않아도 로그인이 가능합니다." → 리더는 테스터 등록 불필요.

**백엔드 구현 시 반영할 것**
- 네이버 응답은 한 겹 감싸져 있다 → `user-name-attribute: response`, 파싱 코드 별도 필요
  ```json
  { "response": { "id": "...", "email": "...", "nickname": "..." } }
  ```
- `response.id` → `users.oauth_subject`
- ⚠️ 콘솔 경고: "Callback URL값이 잘못 입력되어 있으면 정확한 값으로 수정하실 때까지 **네이버 로그인 사용이 일시적으로 제한**됩니다." — 3사 중 유일하게 오설정에 페널티가 있다.

### 5-3. 구글

대상: 프로젝트 **`Clov`** (ID `clov-500407`) · OAuth 클라이언트 **`Clov Google Login`**

현재 콘솔은 개편된 **"Google 인증 플랫폼"** UI로, OAuth 동의 화면이 `브랜딩 / 대상 / 데이터 액세스 / 클라이언트` 탭으로 쪼개져 있다.

| 항목 | 위치 | 상태 |
|---|---|---|
| 앱 이름 · 사용자 지원 이메일 | 브랜딩 | ✅ |
| 앱 로고 · 앱 도메인 | 브랜딩 | ✅ **의도적으로 비움** |
| 게시 상태 = **테스트 중** | 대상 | ✅ 유지 |
| 사용자 유형 = **외부** | 대상 | ✅ |
| 범위 `openid`·`userinfo.email`·`userinfo.profile` | 데이터 액세스 | ✅ 추가 |
| OAuth 클라이언트 (웹 애플리케이션) | 클라이언트 | ✅ |
| 승인된 리디렉션 URI | 〃 | ✅ |
| 승인된 JavaScript 원본 `http://localhost:5173` | 〃 | ✅ |
| **테스트 사용자** | 대상 | ⏸ 본인 + 팀원 |

**결정 — 브랜딩 나머지 항목 비움**: 콘솔 안내가 "게시 상태가 '테스트 중'이 아니라면 로고를 업로드한 후 **인증을 위해 앱을 제출**해야 합니다"라고 명시. 로고를 올리면 검수 절차로 넘어갈 수 있다. 앱 도메인(홈페이지·개인정보처리방침·약관)은 **`localhost`를 넣을 수 없다**(소유 확인된 공개 도메인만). 둘 다 배포 시점 항목.

**결정 — "앱 게시" 누르지 않음**: 프로덕션 전환 시 개인정보처리방침 URL·공개 도메인이 필요해지는데 현재 `localhost`뿐이라 충족 불가. **개발·시연은 "테스트 중" 상태로 전부 가능하다.**

**⚠️ 구글만 다른 점 — 소유자도 테스트 사용자 등록이 필요**

콘솔 안내: "게시 상태가 '테스트 중'으로 설정된 동안에는 **테스트 사용자만 앱에 액세스**할 수 있습니다."

카카오·네이버는 소유자가 자동 통과하지만 **구글은 예외가 없다.** 미등록 계정은 `403 access_denied`가 뜨는데, 에러가 백엔드 문제처럼 보여 코드를 뒤지게 되는 대표적 함정. **본인 Gmail부터 등록**할 것.

**범위 3개가 DB에 매핑되는 방식**

| 범위 | 받는 값 | 컬럼 |
|---|---|---|
| `userinfo.email` | 이메일 | `users.email` (NOT NULL) |
| `userinfo.profile` | 이름·프로필 사진 | `users.nickname` · `profile_image_url` |
| `openid` | 고유 식별자 `sub` | `users.oauth_subject` |

세 개 모두 **"민감하지 않은 범위"** 라 구글 검수가 필요 없다. 카카오가 이메일 하나에 비즈앱 전환을 요구한 것과 대조적.

**백엔드 구현 시 반영할 것**
- 구글은 Spring Security **내장(`CommonOAuth2Provider`)** — provider 블록 없이 `client-id`/`client-secret`만 넣으면 된다. 3사 중 설정이 가장 단순.
- `user-name-attribute: sub`
- ⚠️ **반영 지연**: 콘솔 안내 "설정이 적용되는 데 **5분에서 몇 시간**이 걸릴 수 있습니다." 카카오·네이버는 즉시 반영이라 여기서 헷갈리기 쉽다. 저장 직후 `redirect_uri_mismatch`가 나면 **설정 오류가 아니라 미반영**일 수 있다.
- `localhost`는 승인된 도메인 자동 처리 → 별도 등록 불필요.

### 5-4. 3사 비교 요약 (구현 시 참고)

| | client_id | user-name-attribute | provider 블록 | 특이사항 |
|---|---|---|---|---|
| 카카오 | REST API 키 | `id` | **직접 작성** | Client Secret **ON** → 설정 누락 시 `invalid_client` |
| 네이버 | Client ID | `response` | **직접 작성** | 응답이 `response`로 한 겹 감싸짐 |
| 구글 | Client ID | `sub` | **불필요**(내장) | 설정 반영 지연 최대 수 시간 |
