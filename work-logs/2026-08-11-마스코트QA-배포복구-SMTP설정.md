### #155 — 로컬(포트 분리)에서 소셜 로그인 리다이렉트가 백엔드로 되돌아간다 (clov-api)

**증상**: 로컬에서 프론트(5173)·백엔드(8080) 띄우고 소셜 로그인하면 `localhost:8080/oauth2/redirect?code=...`로 리다이렉트되고 404. 배포(운영)는 문제없음.

**원인**: `OAuth2SuccessHandler`가 로그인 성공 후 리다이렉트 URL을 **요청이 들어온 도메인 그대로**(`ServletUriComponentsBuilder.fromContextPath(request)`) 계산함. 운영은 nginx가 프론트·백엔드를 같은 도메인으로 묶어줘서(#147, 멀티 도메인 지원) 문제없지만, 로컬은 프론트·백엔드가 nginx 없이 포트만 다른 상태라 백엔드 자기 자신으로 되돌아감.

**수정**: `app.oauth.local-frontend-origin` 설정값 추가 — 기본값은 빈 문자열이고 `dev` 프로필에서만 `http://localhost:5173`로 채움. 값이 있으면 고정 오리진으로, 없으면(운영) 기존 request-relative 로직을 그대로 씀. 운영 동작은 코드 경로 자체가 그대로라 회귀 위험 없음. 유닛테스트로 기존 멀티 도메인 동작(`clovlov.xyz`·`clovlabcalss.store`)이 안 깨지는 것과 로컬 동작을 둘 다 확인.

- 브랜치: `fix/155-oauth-redirect-local-dev`
- PR: [clov-api#156](https://github.com/Pickeslog/clov-api/pull/156)

## 4. 비밀번호 재설정 메일이 실제로 안 나가고 있던 문제

QA 중 "비밀번호 찾기"를 테스트해보니 메일이 전혀 안 옴. 확인해보니 `LoggingMailSender`(기본값, `app.mail.mode=log`)가 실제 발송 대신 **서버 로그에만 링크를 찍는 상태**였음 — 코드 주석에도 "운영에서 기본값으로 두면 안 된다(로그 열람 권한자가 남의 비밀번호를 재설정할 수 있다)"고 명시돼 있었고, `work-logs/2026-07-29-핸드오프.md` §5에 이미 알려진 문제로 기록돼 있었음(SMTP 미설정 상태로는 프론트 배포를 미뤘던 이력).

### 4-1. Brevo 가입 및 SMTP 키 발급

Gmail 앱 비밀번호를 먼저 시도했으나 신규 계정 제한(`앱 비밀번호를 계정에서 사용할 수 없습니다`)에 막혀서, 이메일 발송 전용 서비스인 **Brevo**(구 Sendinblue)로 전환.

1. `https://www.brevo.com` 무료 가입(신용카드 불필요, 하루 300통) — 가입 이메일은 새로 만든 `clovoffice@gmail.com`
2. 이메일 인증
3. 로그인 후 **오른쪽 위 프로필 → Settings → SMTP & API** (또는 직접 `https://app.brevo.com/settings/keys/smtp`)
4. **SMTP** 탭에서 "Generate a new SMTP key" — 이름 지정(`clov`), Variant는 **Standard**(64자), Expiry는 기본 1년
5. 발급된 키는 **한 번만 표시**되므로 그 자리에서 복사(이 문서에는 기록하지 않음 — secret)

발급된 SMTP 접속 정보(키 제외):
```
SMTP Server : smtp-relay.brevo.com
Port        : 587
Login       : b51b16001@smtp-brevo.com   ← 계정 이메일이 아니라 Brevo가 별도로 부여하는 인증 전용 아이디
```

> **함정**: Login 값을 계정 이메일(`clovoffice@gmail.com`)로 잘못 넣었다가 `MailAuthenticationException`(SMTP 인증 실패)이 남. Brevo의 SMTP 인증 아이디는 계정 이메일과 별개의 고정값이고, 사용자가 임의로 바꿀 수 없다. 실제 발신자로 표시되는 주소(`From`)는 이 로그인 아이디와 무관하게 별도 설정값(`APP_MAIL_FROM`)이 담당한다.

### 4-2. VM 설정 — 실제 파일 위치 (문서와 다름 주의)

`deploy/DEPLOY.md`엔 `/opt/clov-api/application-secret.yaml`이라고 적혀 있었지만, **실제로는 그 경로가 존재하지 않았다**(`nano`로 열려다 `No such file or directory`). VM이 systemd가 아니라 **Docker Compose**로 운영되고 있어서, 실제 설정은 홈 디렉터리의 compose 파일 안에 있었다.

```bash
cat ~/api-docker-compose.yaml
```
로 확인한 실제 구조:
```yaml
services:
  api:
    image: kimgyubi1234/springboot-app:latest
    container_name: api
    restart: always
    ports:
      - "8080:8080"
    environment:
      - SPRING_PROFILES_ACTIVE=prod
      - APP_OAUTH_REDIRECT_BASE=https://clovfriend.shop
      - APP_OAUTH2_REDIRECT_URL=https://clovfriend.shop/oauth2/redirect
      - APP_CORS_ALLOWED_ORIGINS=https://clovfriend.shop
    volumes:
      - /home/wjddus276/deploy/application-secret.yaml:/app/application-secret.yaml
```

즉 **환경변수는 `.env` 파일이 아니라 compose 파일의 `environment:` 목록에 직접 나열**돼 있고, 시크릿 파일은 `/home/wjddus276/deploy/application-secret.yaml`(호스트) → `/app/application-secret.yaml`(컨테이너)로 마운트되는 구조였다.

**1) `~/api-docker-compose.yaml`에 환경변수 3개 추가** — nano로 직접 편집하려다 브라우저 SSH 클라이언트에서 키 입력이 계속 씹혀서(Ctrl+O/Y/Enter 시퀀스가 여러 번 실패), 아래처럼 `sed`로 한 번에 삽입하는 방식으로 전환:

```bash
sed -i '/APP_CORS_ALLOWED_ORIGINS=https:\/\/clovfriend.shop/a\      - APP_MAIL_MODE=smtp\n      - APP_MAIL_FROM=clovoffice@gmail.com' ~/api-docker-compose.yaml
```

나중에 링크 도메인 문제(§4-4)가 추가로 발견돼서 한 줄 더 삽입:

```bash
sed -i '/APP_MAIL_FROM=clovoffice@gmail.com/a\      - CLIENT_URL=https://clovfriend.shop' ~/api-docker-compose.yaml
```

**2) `/home/wjddus276/deploy/application-secret.yaml`에 `spring.mail.*` 블록 추가** — 기존 `spring:` 섹션(들여쓰기 2칸)의 형제 항목으로, `jwt:`가 시작되는 줄 바로 앞에 삽입:

```bash
sed -i '/^jwt:/i\  mail:\n    host: smtp-relay.brevo.com\n    port: 587\n    username: b51b16001@smtp-brevo.com\n    password: <SMTP_KEY — secret, 파일에는 실제 키>\n    properties:\n      mail:\n        smtp:\n          auth: true\n          starttls:\n            enable: true\n' /home/wjddus276/deploy/application-secret.yaml
```

결과 형태(값은 마스킹):
```yaml
spring:
  datasource:
    ...
  security:
    ...
  mail:
    host: smtp-relay.brevo.com
    port: 587
    username: b51b16001@smtp-brevo.com
    password: ****(Brevo SMTP 키)****
    properties:
      mail:
        smtp:
          auth: true
          starttls:
            enable: true

jwt:
  ...
```

**3) 컨테이너 반영** — `docker compose up -d`는 **compose 파일 자체가 바뀔 때만 컨테이너를 재생성**하고, **마운트된 파일(`application-secret.yaml`)의 내용 변경은 감지하지 못한다.** 그래서 `application-secret.yaml`만 고친 뒤 `up -d`를 돌렸더니 `Running (0.0s)`로 아무 일도 안 일어났고, 옛날 설정을 물고 있는 컨테이너가 계속 그대로 SMTP 인증에 실패했다. **`restart`로 강제로 프로세스를 재시작**해야 마운트된 파일을 다시 읽는다.

```bash
sudo docker compose -f api-docker-compose.yaml up -d       # compose 파일(환경변수) 변경 반영
sudo docker compose -f api-docker-compose.yaml restart api # 마운트된 시크릿 파일 재로딩
```

**4) 검증**
```bash
sudo docker compose -f api-docker-compose.yaml logs --tail 100 api
# → Started ClovApiApplication in 17.128 seconds (에러 없이 부팅)

sudo docker compose -f api-docker-compose.yaml logs --tail 30 api | grep -i mail
# → 실패 시: [MAIL:smtp] 발송 실패 subject=... cause=MailAuthenticationException
# → 성공 시: 아무 로그도 안 남음(SmtpMailSender는 성공 시 로그를 안 남기고, 실패했을 때만 warn 로그를 남기게 되어 있다 — 계정 열거 방지 설계, 계약 §4-4)
```

### 4-3. 재설정 링크 자체가 엉뚱한 도메인이었던 문제

메일 발송까진 성공했는데, 메일에 온 링크가 `https://clovlab.store/reset-password?token=...`였다 — **`clovfriend.shop`도 `clovlabcalss.store`도 아닌 세 번째 도메인**. 원인은 `application.yaml`의 `client.url`이 `prod` 프로필에서 팀 공용 기본값(`https://clovlab.store`)으로 하드코딩돼 있었고, `PasswordResetService`가 이 값으로 링크를 만들고 있었기 때문(`@Value("${client.url:http://localhost:5173}")`).

코드를 고치지 않고, Spring Boot의 **환경변수 → 프로퍼티 자동 매핑**(`CLIENT_URL` → `client.url`)을 이용해 컨테이너 환경변수만으로 해결(§4-2의 `sed` 명령에 이미 반영됨). 재배포 후 메일 링크가 `https://clovfriend.shop/reset-password?...`로 정확히 나오는 것, 그 링크를 눌러 새 비밀번호 입력 화면까지 정상 도달하는 것을 확인.

## 5. 최종 상태

- clov-web·clov-api `main`·`deploy-kimgyubi` 모두 최신 상태로 동기화됨
- `https://clovfriend.shop`에서 마스코트 한도 대사·생일 대사·버거노인 제거·소셜 로그인·비밀번호 재설정 메일까지 전부 실사용 확인 완료
- SMTP 계정(Brevo, `clovoffice@gmail.com`)·`CLIENT_URL` 등은 사용자 개인 VM(`deploy-kimgyubi`)에만 적용된 설정으로, 저장소 공용 파일(`application.yaml`·`.env.production`)은 건드리지 않았다 — 다른 팀원의 배포에는 영향 없음
