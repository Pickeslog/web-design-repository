## 1. 지금 무엇이 막혀 있나

세 가지 문제가 **같은 뿌리**에서 나온다.

### ① 레벨업 알림을 넣을 자리가 없다

`type`이 **탭 필터로 그대로 쓰인다.**

```xml
<!-- NotificationMapper.xml -->
<if test="type != null">
  AND n.type = #{type}
</if>
```

프론트는 `?type=NOTICE|FRIEND|JOIN`으로 탭을 조회한다. 그래서 `LEVEL_UP`을 새 `type` 값으로 추가하면 **어느 탭 조회에도 안 걸리는 유령 알림**이 된다.

### ② '친구들 알림' 탭이 영구 공백

알림을 만드는 코드가 **딱 두 곳**이다.

| 생성 지점 | type |
|---|---|
| `RoomMapper.insertRoomUpdateNotifications` (방 설정 변경) | `NOTICE` |
| `InviteMapper.insertJoinNotifications` (가입 신청) | `JOIN` |

추억 작성·편지 발송·약속 완료는 **알림을 만들지 않는다.** `FRIEND` 타입을 만드는 코드가 저장소 어디에도 없다.

### ③ 알림 문구가 전부 제네릭

프론트는 `notification.payload?.title` / `payload?.content`를 읽는데 **`payload`라는 필드가 계약에도 백엔드에도 없다.** 항상 `undefined`라 fallback 문구만 나온다.

> "친구의 새로운 활동 알림이 있습니다."

누가 무엇을 했는지 알 수 없다.

### 근본 원인

**`type` 하나가 두 가지 역할을 겸하고 있다.**

- "어느 탭에 넣을까" (NOTICE / FRIEND / JOIN)
- "무슨 일이 일어났나" (추억? 편지? 레벨업?)

값이 3개뿐이라 이벤트 종류를 표현할 자리가 없고, 늘리면 탭 필터가 깨진다.

## 3. 권고안 — 탭과 이벤트를 분리

### 스키마

```sql
ALTER TABLE notifications
  ADD COLUMN sub_type VARCHAR(30) NOT NULL AFTER type,
  ADD COLUMN payload  JSON        NULL     AFTER reference_id;
```

| 컬럼 | 역할 | 값 |
|---|---|---|
| `type` (기존) | **어느 탭** | `NOTICE` / `FRIEND` / `JOIN` |
| `sub_type` (신규) | **무슨 일** | 아래 카탈로그 |
| `payload` (신규) | 문구에 필요한 부가 정보 | `{"level": 3}` 등, 없으면 `null` |

**`type`의 의미와 탭 필터 쿼리는 그대로 둔다.** 기존 조회·프론트 탭이 안 깨지는 게 핵심이다.

### 이벤트 카탈로그 (`sub_type`)

| type(탭) | sub_type | 언제 | actor | reference_id | payload |
|---|---|---|---|---|---|
| FRIEND | `ROOM_UPDATE` | 방 정보 수정 | 수정자 | roomId | — |
| FRIEND | `MEMORY_WRITE` | 추억 작성 | 작성자 | memoryId | — |
| FRIEND | `LETTER_RECEIVE` | 편지 받음 | 보낸이 | letterId | — |
| FRIEND | `PLAN_CREATE` | 약속 등록 | 등록자 | planId | — |
| FRIEND | `PLAN_COMPLETE` | 약속 완료 | 완료자 | planId | — |
| FRIEND | `LEVEL_UP` | 우정 레벨업 | **null** | roomId | `{"level": 3}` |
| JOIN | `JOIN_REQUEST` | 가입 신청 | 신청자 | joinRequestId | — |
| JOIN | `JOIN_ACCEPTED` | 신청 수락 | 수락자 | joinRequestId | — |
| NOTICE | `ADMIN_NOTICE` | 운영 공지 | null | null | `{"title":…, "content":…}` |

**레벨업만 `actor`가 없다**(방 전체 이벤트). `actor_id`는 이미 `NULL` 허용이라 스키마 변경이 필요 없다.

### 문구는 프론트가 만든다

백엔드는 **사실(누가·무엇을·어떤 값)** 만 주고, 문장은 프론트가 조립한다. 문구를 바꾸려고 백엔드를 건드리지 않게.

```js
const MESSAGE = {
  ROOM_UPDATE:    (n) => `${n.actor.nickname}님이 우정공간 정보를 바꿨어요`,
  MEMORY_WRITE:   (n) => `${n.actor.nickname}님이 추억을 남겼어요`,
  LETTER_RECEIVE: (n) => `${n.actor.nickname}님이 행운편지를 보냈어요`,
  PLAN_CREATE:    (n) => `${n.actor.nickname}님이 새 약속을 만들었어요`,
  PLAN_COMPLETE:  (n) => `${n.actor.nickname}님이 약속을 완료했어요`,
  LEVEL_UP:       (n) => `우정공간이 Lv.${n.payload.level}이 됐어요! 🎉`,
  JOIN_REQUEST:   (n) => `${n.actor.nickname}님이 우정공간 입장을 신청했어요`,
  JOIN_ACCEPTED:  (n) => `${n.actor.nickname}님이 합류했어요`,
}
```

### 계약 §13 응답

```jsonc
{ "id": "700", "type": "FRIEND", "subType": "LEVEL_UP",
  "actor": null, "referenceId": "31", "payload": { "level": 3 },
  "isRead": false, "createdAt": "2026-07-24T11:00:00" }
```

## 4. 대안 비교

| 안 | 내용 | 판정 |
|---|---|---|
| **A. `sub_type` 추가 (권고)** | `type`=탭 유지, 이벤트는 새 컬럼 | ✅ 기존 필터·프론트 무손상, 확장 가능 |
| B. `type`에 값만 더 넣기 | `LEVEL_UP`을 type에 추가 | ❌ 탭 필터에서 사라짐(유령 알림) |
| C. 탭도 새로 만들기 | 레벨업 전용 4번째 탭 | ❌ 프로토타입 3탭 구조 이탈, 알림 하나 때문에 탭 신설 |
| D. 프론트가 전부 받아 분류 | 서버 필터 제거 | ❌ 탭별 페이지네이션 불가, 전송량 증가 |

### `payload`를 지금 같이 넣는 이유

빼도 `sub_type`만으로 대부분 동작한다. 다만 **레벨업이 "Lv.3"을 못 쓴다**("한 단계 성장했어요"까지만).

지금 넣기를 권하는 건 **알림이 4건뿐인 지금이 스키마를 바꾸는 가장 싼 시점**이고, 나중에 편지 이모지·추억 제목 같은 걸 문구에 넣고 싶을 때 또 마이그레이션하지 않아도 되기 때문이다. 프론트가 이미 `payload`를 읽는 죽은 코드를 갖고 있어서, 형태를 정의해주면 그 코드가 오히려 정합해진다.

**범위를 줄이려면** `payload` 없이 `sub_type`만으로 1단계를 끝내도 된다.

## 5. 마이그레이션

데이터가 4건뿐이라 간단하다.

```sql
-- 기존 JOIN 알림 4건 → sub_type 채우기
UPDATE notifications SET sub_type = 'JOIN_REQUEST' WHERE type = 'JOIN';
-- NOTICE/FRIEND는 0건이라 대상 없음
```

`sub_type`을 `NOT NULL`로 만들 거면 **컬럼 추가 → UPDATE → NOT NULL 제약** 순서로. 기존 행이 4건뿐이라 한 번에 해도 무방하다.

## 6. 함께 정리할 것

### ① 방 설정 변경을 `NOTICE` → `FRIEND`로 이동

지금 방 정보 수정 알림이 **'관리진 공지' 탭**에 들어간다. 친구 활동이므로 `FRIEND`가 맞다.

→ 그러면 **`NOTICE` 탭에 생산자가 없어진다.** 운영 공지를 발행하는 기능이 아직 없기 때문.

| 선택지 | 판단 |
|---|---|
| **탭 유지 + 정직한 빈 상태**("아직 공지가 없어요") | ✅ 권고. 프로토타입 3탭 구조 유지, 나중에 운영 공지 기능이 생기면 그대로 씀 |
| 탭 제거(2탭) | 프로토타입 이탈 |

### ② 하드코딩된 가짜 공지 제거

`Notifications.jsx`의 `PROTOTYPE_NOTICES` 2건이 **실제 화면에 보인다.**

> "[업데이트] ➕ 새로운 방 추가 기능이 적용되었습니다!"
> "[공지] Clov v2.0 정식 오픈 안내 🎉"

실제로 있었던 일이 아니다. 배포 전에 반드시 제거하고 빈 상태 안내로 대체한다.

### ③ 죽은 `payload` 읽기 정리

`titleFor` / `messageFor`의 `payload?.title`·`payload?.content`·`payload?.actorName`은 현재 항상 `undefined`다. `sub_type` 기반 문구로 교체하면서 함께 걷어낸다.

### ⚠️ 구현 시 주의

**알림 생성은 새로운 부수효과다.** `notifications` 테이블에 행을 쓰기 시작하면, 그 도메인을 쓰는 기존 통합테스트의 `@AfterEach` 정리에 `notifications` 삭제가 빠져 있는지 **반드시 확인**해야 한다.

오늘 오전 경험치 작업에서 정확히 이것 때문에 **무관한 테스트 12건이 FK 위반으로 깨졌다**(`.claude/skills/clov-task/SKILL.md` §4에도 기록됨).

특히 `ExpIntegrationTest`는 레벨업을 직접 유발하므로 1순위 점검 대상이다.
