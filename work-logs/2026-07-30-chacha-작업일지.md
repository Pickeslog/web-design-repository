**브랜치**: `feat/mascot-wardrobe-dropdown` (`bedb5ae`, 5파일 +200/-5)

### 배치를 세 번 바꿨다

처음엔 사용자 설정 안에 코스튬 목록을 넣었는데, 좁아서 알약 버튼이 뭉개졌다. → 설정 안에 "마스코트 꾸미기" 전용 탭(미리보기 + 옷장 그리드)으로 다시 만들었다. → 최종적으로 **설정에서 완전히 빼내 헤더 독립 드롭다운**(`MascotWardrobe.jsx`)으로 옮겼다. 설정 모달은 원래의 2탭 구조로 되돌렸다.

**구현 메모**: 코스튬 오버레이 규칙은 `Mascot.jsx`의 기존 로직(`equippedSprite || SPRITES[mascotType]`)을 그대로 따랐다 — `prefs.equippedItem?.imageUrl`이 있으면 **기본 스프라이트를 완전히 대체**한다. 미리보기가 실제 대시보드와 달라지면 안 되므로 새로 짜지 않고 재사용했다.

### 글자 배치 버그 — `line-height` 상속

`.proto-settings`에 `line-height`가 없어서 html의 **고정값 `26.1px`**(18px 기준)를 그대로 물려받았다. 라벨(12px)·버튼(13px) 같은 작은 글자가 자기 폰트 크기와 무관한 줄높이를 써서 상하 여백이 붕 뜬 것처럼 보였다.

```css
.proto-settings {
  /* 폰트 크기에 비례하는 line-height로 재설정 */
  line-height: 1.4;
}
```

**검증**: computed style로 12px 텍스트의 line-height가 `26.1px → 16.8px`로 바뀐 것 확인. `npm run lint` 통과.

> 참고: 이 세션 내내 브라우저 스크린샷 도구가 고장나 있어서, 화면 확인은 `read_page`·DOM 쿼리·computed style 조회로 대체했다.

## 7. ★ clov-api — GCP-VM-CICD 복구 (실배포 성공)

**브랜치**: `fix/cicd-ssh-deploy` (커밋 3개)

myeongjundev가 올린 배포 워크플로([PR #93](https://github.com/Pickeslog/clov-api/pull/93))가 계속 실패했다. "Dockerfile 충돌 아니냐"는 의심이 있었지만 **Dockerfile은 무관했다.**

### 진단 — 스텝별 소요 시간이 답이었다

| 스텝 | 결과 | 소요 |
|---|---|---|
| Docker build + push | 성공 | 61s |
| GCP SSH REMOTE 원격접속 | 실패 | **1~3s** |

빌드·push가 61초 걸려 성공했으니 Dockerfile·빌드 컨텍스트·`DOCKER_*` 시크릿은 정상이다. SSH가 **1초 만에** 죽는 건 접속 타임아웃(30s)이 아니라 액션이 입력값을 보고 즉시 거절한 것이다. 문제는 **그 원인이 로그에 안 남는다**는 것이었다.

### 원인은 세 겹이었다

**① 진단이 불가능했다** — `Setup SSH Key` 스텝이 두 가지로 고장나 있었다.

- `~/.ssh/id_rsa`를 만들지만 **아무도 읽지 않는다.** `appleboy/ssh-action`은 `with.key` 입력만 쓰고 러너의 `~/.ssh`는 보지 않는다.
- 검증줄이 `ssh-keygen -l -f ... || echo "Invalid key format"`이라 **키가 깨져 있어도 초록불로 통과**했다.

→ 죽은 스텝을 실제로 끊어주는 **"배포 시크릿 검증"** 스텝으로 교체. 시크릿 5종이 비면 브랜치에 맞는 이름(`GCP_VM_HOST_CHACHA` 등)을 찍고 실패시키고, 개인키는 `ssh-keygen -y`로 실제 파싱해본다.

**② 이미지 이름이 어긋나 있었다** — ①을 고치기 전엔 보이지 않던 문제다.

| | 이미지 | Docker Hub |
|---|---|---|
| VM compose가 pull | `chacha1650a/`**`spring-app`** | 존재 (7/29 수동 push분) |
| 워크플로가 push | `chacha1650a/`**`springboot-app`** | 없었음 |

이대로면 새 이미지를 올려놓고 **VM은 어제 이미지를 pull해서 다시 띄운 뒤 워크플로가 초록불**이 된다. 배포가 안 됐는데 됐다고 보고하는 건 대놓고 실패하는 것보다 나쁘다.

→ 배포 전 compose의 `image:` 줄이 방금 push한 이미지를 가리키는지 확인하고, 아니면 `pull` 전에 끊고 현재 image 줄을 로그에 찍는다.

**③ `docker compose down`이 사이트를 내릴 뻔했다** — 이것도 ①②를 고친 뒤에야 보였다.

VM을 실제로 열어보니 `api`·`web`(nginx)·`certbot` 세 컨테이너가 **같은 compose 프로젝트 네트워크**(`g01058797023a_default`)를 공유한다. `api-docker-compose.yaml`엔 `api`만 정의돼 있지만 같은 홈디렉터리에서 올려서 프로젝트명이 겹친다.

이 상태에서 `down`을 부르면:
1. `api` 컨테이너 삭제 → 2. 그 네트워크까지 삭제 시도 → 3. web·certbot이 붙어 있어 **실패** → 4. ①에서 넣은 `script_stop`이 거기서 스크립트를 끊음 → 5. **`up -d`가 실행 안 됨. api만 사라진 채 끝.**

`script_stop` 자체는 옳지만 `down`과 같이 두면 이렇게 물린다. `pull`로 이미지가 바뀌면 `up -d`가 알아서 재생성하므로 **`down`은 애초에 불필요하다.** 네트워크를 안 건드려서 web·certbot도 안전하다.
