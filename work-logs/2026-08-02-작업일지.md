## 3. clov-web — 조용한 실패 3건

### `#210` 설정 저장 실패가 안 보인다 (`#208`)

테마 패널은 고르는 즉시 저장하는 낙관적 갱신인데 `onError`가 없어 **되돌릴 방법이 없었다.** 실패하면 화면은 바뀐 채로 남고, 새로고침해야 이전 값이 드러난다. 사용자에겐 *"설정이 이유 없이 되돌아간다"* 로 보인다.

- `prefMutation.onError` — 이전 값으로 되돌리고 `applyTheme`으로 `body` 클래스까지 되돌린다
- 테마 패널 푸터에 실패 표시 자리 신설(즉시 저장이라 `저장하기`가 없어 알릴 곳이 없었다)
- `deleteMutation` 실패 표시 — 계정 탈퇴가 실패하면 버튼만 원래대로 돌아와 눌렸는지조차 몰랐다
- `setPrefAndSave`가 `mutate`를 `setState` 업데이터 **안에서** 부르던 것을 밖으로. 업데이터는 순수해야 하고 StrictMode에서 두 번 실행돼 **개발 모드에서 저장 요청이 2번 나갔다**
- `Header.jsx:110` 골드 배지 `?? 0`

**전날 핸드오프의 과장을 정정했다.** *"`onError`가 0건 → 모든 저장 실패가 안 보인다"* 라고 썼는데, 5개 중 3개는 `isError` 렌더로 이미 메시지를 띄우고 있었다. 실제 구멍은 2개였다.

### `#211` 봉투 아닌 응답을 성공으로 넘긴다 (`#209`)

```diff
-  return body
+  throw new Error('서버 응답 형식이 올바르지 않습니다. 잠시 후 다시 시도해 주세요.')
```

**`#182`로 프론트 CD를 붙인 지금이 오히려 밟기 쉽다.** nginx 프록시가 어긋나면 `/api/*`에 `index.html`이 200으로 돌아오고, 그러면 모든 쿼리가 HTML 문자열을 "성공적으로" 받는다. 네트워크 탭은 전부 초록인데 화면만 깨지는, 제일 헷갈리는 형태다.

안전 근거를 정황이 아니라 **전수**로 확인했다:

| 확인 | 결과 |
|---|---|
| 컨트롤러 14개 `public` 핸들러 반환 타입 | **예외 없이** `ApiResponse` / `ResponseEntity<ApiResponse>` |
| `DELETE` 10개 | 전부 `ApiResponse.success(null)` → 200 + 봉투 |
| `noContent()` / `NO_CONTENT` | clov-api 전체 **0건** |
| R2 PUT | `uploadImage.js`가 순수 `fetch`로 우회 |

### `#213` 네트워크 오류가 영어로 나온다 (`#212`)

```js
return error instanceof Error ? error : new Error('네트워크 오류가 발생했습니다.')
```

`AxiosError`는 **`Error`의 인스턴스**라 삼항의 앞쪽으로 빠진다. **준비해 둔 한국어 문구는 사실상 도달하지 않는 코드였다.** 화면 5곳이 `error.message`를 그대로 렌더하므로 사용자에게 직행했다.

응답 유무로 두 갈래로 나누고, 원본은 `cause`에 남겼다.

## 4. 검증 — 로그인 없이 어디까지 되나

Claude는 로그인 화면 뒤를 못 본다. 그래서 `#211`·`#213`은 **실행 중인 앱에서 진짜 모듈을 import해서** 확인했다.

```js
const { api } = await import('/src/api/client.js')
api.defaults.baseURL = window.location.origin   // Vite dev가 모르는 경로에 index.html 200
await api.get('/__envelope_probe__')
```

**Vite dev 서버의 SPA 폴백이 nginx 사고와 똑같은 형태**라 별도 스텁 없이 그대로 재현됐다.

| | before | after |
|---|---|---|
| 봉투 아닌 200 | `200 · text/html · "<!doctype html>…"` 를 그대로 반환 | throw |
| 연결 실패 | `Network Error` | 서버에 연결하지 못했습니다… (`cause.code = ERR_NETWORK`) |
| 404 · 봉투 아님 | `Request failed with status code 404` | 요청을 처리하지 못했습니다… (`cause.response.status = 404`) |

404는 SPA 폴백이 `GET`만 처리하는 점을 이용해 `POST`로 받아냈다.

**이 방법은 앞으로도 쓸 수 있다** — 로그인 뒤 화면은 못 보지만, 앱이 로드돼 있으면 그 안의 모듈은 콘솔에서 직접 호출할 수 있다.

## 5. ★ 데모 데이터 정리 — 그리고 오늘의 사고

`#105`/`#106`. 어제 만든 스크립트를 **실제로 돌린 날**이다. 돌리면서 가정 4개가 깨졌다.

### ① "dev DB에서만"이 틀렸다

**분리된 dev DB가 없다.** 이 DB 하나를 배포된 팀 공용 서비스가 그대로 쓴다. `§0` 진단 결과에 **리더 실계정과 chacha 실계정이 들어 있어서** 확인됐다.

그 문구를 두면 다음 사람이 *"dev니까 괜찮겠지"* 하고 돌린다. 두 스크립트 머리를 실DB 기준으로 다시 썼다.

### ② 옵션 A를 데모에 쓸 수 없다

대상 **13계정** 중 4계정이 A 적용 시 **0으로 떨어진다.**

| id | | 현재 | A 적용 후 |
|---|---|---|---|
| 14 | 리더 | 18,320 | **0** |
| 41 | `shopA-0725@test.local` | 18,040 | **0** |
| 17 | chacha | 7,800 | **0** |
| 42 | `shopB-0725@test.local` | 140 | **0** |

A는 `20,000 − 19,000` **뺄셈**이라 이미 1,000 넘게 쓴 계정이 음수 방지로 0이 된다. *"실제 사용자가 섞였을 때 쓰는 보수적 옵션"* 으로 설계했는데 **여기선 그 실제 사용자가 곧 시연 계정**이었다.

옵션 B(전체 리셋)는 실DB라 팀원의 구매 이력·보유 아이템을 되돌릴 수 없게 지운다. 남의 데이터라 뺐다.

→ **`§1-B`(옵션 C) 신설.** 뺄셈이 아니라 **대입**으로 1,000에 맞추고 보유 아이템은 남긴다. 삭제가 없어 되돌릴 수 있다.

### ③ safe update mode (Error 1175)

`wallet_transactions` UPDATE가 `reason`·`amount`로만 걸러 Workbench에 막혔다(`user_wallets`는 PK 조인이라 통과).

**나쁜 건 실패 지점이다.** MySQL은 statement 하나가 실패해도 트랜잭션을 롤백하지 않는다. **지갑은 1,000으로 바뀌고 원장은 20,000인 채로 트랜잭션이 열려 있게 된다.** 반쪽 상태로 커밋하기 딱 좋다.

### ④ ★ 트랜잭션 중간에 멈추면 조용히 롤백된다

스크립트가 `START TRANSACTION` 안에 *"커밋 전에 확인"* 용 SELECT를 두고 있었다. 실DB라 눈으로 확인하고 커밋하려고 **18분** 멈췄다.

그 사이 Workbench가 유휴 연결을 끊고 재연결했다. **트랜잭션이 롤백됐고**, 그 뒤의 `COMMIT`은 새 연결에서 도는 빈 명령이라 `0 rows affected`로 **성공한 것처럼 보였다.**

```
#21  COMMIT                    → 0 rows affected   ← 성공처럼 보임
#22  SET SQL_SAFE_UPDATES = 1  → 0 rows affected
#23  검증: SIGNUP_GRANT=20000 남은 건수 → 13        ← 안 바뀌어 있었다
```

**Output 창은 전부 초록이고 커밋도 성공인데 데이터는 그대로였다.** `§3` 검증이 없었으면 "정리 끝났다"고 믿고 넘어갔을 것이다.

두 번째 실행에서도 `matched: 13`이 나온 게 첫 실행이 반영되지 않았다는 증거였다.

→ `START TRANSACTION`~`COMMIT`을 **한 번에** 실행하라는 경고 추가. 트랜잭션 안의 확인용 SELECT는 제거하고, 확인은 `§0-3` 미리보기(트랜잭션 밖)에서 끝내도록 바꿨다. 잘못되면 `§0-4` 스냅샷으로 되돌린다 — **스냅샷을 먼저 만드는 이유가 이거다.**

### 최종 결과 (20:05)

```
UPDATE user_wallets         13 matched / 13 changed
UPDATE wallet_transactions  13 matched / 13 changed
COMMIT

검증  SIGNUP_GRANT=20000 남은 건수 : 0
      잔액 20000인 지갑            : 0
```

13계정 전부 **1,000**, 보유 아이템 유지. 스냅샷 `_bak_user_wallets_20260802`가 DB에 남아 있다 — **데모 끝나면 `DROP TABLE` 할 것.**

## 6. 프로세스 — 승인 요건을 하루 만에 되돌렸다

어제 자체 머지 7건을 이유로 두 레포 main에 **승인 1건**을 걸었다. 오늘 그 첫 결과가 이랬다:

- 리더가 올린 PR 4건이 전부 `BLOCKED`
- **자기 PR은 자기가 승인 못 한다**(GitHub 규칙)
- **admin 우회도 안 된다** — 룰셋 `bypass_actors`가 `[]`. 클래식 브랜치 보호와 달리 **룰셋은 admin이 자동 예외가 아니다**

`admin: true`인데도 `repos/.../rules/branches/main`이 규칙 4개를 그대로 돌려줬다(우회 가능하면 빈 배열).

**리더 판단으로 승인 요건을 `0`으로 되돌렸다.** 근거:

> 비전공 팀원에게 리뷰 부담을 지우는 것보다 CI 초록이면 본인이 머지하는 쪽이 이 팀에 맞다. 프로젝트가 끝나면 각자 개인 배포·개인 머지를 하게 된다.

**나머지 보호는 전부 유지했다:**

```
PR 필수 · CI(build) 통과 필수 · squash만 · force push 금지 · 브랜치 삭제 금지
```

즉 *"리뷰 없이 머지 가능"* 이지 *"아무렇게나 main에 넣기 가능"* 이 아니다. **팀원들도 이제 자기 PR을 직접 머지할 수 있다.**
