## ★ 정합 버그 (반드시 수정) — 계약 §9 위반
`PlanService.addChecklist`가 **insert 후 재조회 없이** in-memory 객체를 그대로 반환한다:
```java
checklistMapper.insert(checklist);
return PlanResponses.Checklist.from(checklist);   // checklist.checked == null!
```
insert XML은 `(plan_id, content)`만 넣고 `checked`는 DB default(false)에 맡기므로, 반환 객체의 `checked`는 **null**이다. 계약 §9는 생성 응답이 `{ "id":"9", "content":"항공권 예매", "checked": false }` — **false**를 요구한다.
→ **fix**: `updateChecklist`가 이미 하는 대로 insert 후 재조회해서 반환.
```java
checklistMapper.insert(checklist);
return PlanResponses.Checklist.from(checklistMapper.findById(checklist.getId()).orElseThrow());
```
이건 invite에서 겪은 **"insert 후 Java객체 그대로 반환→DB default null"** 버그의 재발이다. **insert 후 재조회 패턴 필수**(room/invite 교훈). `create`(→`detail()` 재조회)·`commit`(→`stageItems()` 재조회)은 이미 올바르니 그대로.

## 문제 2 — 아직 압축포맷인 파일 (표준화 미완)
controller/service/DTO/XML은 이미 정리됐다. 하지만 아래는 **여전히 한 줄 압축**이라 마저 표준화해야 한다:
- `entity/Plan.java`·`PlanChecklist.java`·`PlanStagePhoto.java` — 필드·getter/setter가 한 줄에 다 붙어 있음. `domain/room/entity`처럼 필드/메서드 줄바꿈.
- `mapper/PlanMapper.java`·`ChecklistMapper.java`·`StagePhotoMapper.java` — `@Mapper public interface ... { ...전부 한 줄 }` + 와일드카드 `import ....*`. `domain/room/mapper/RoomMapper.java`처럼 메서드 줄바꿈 + 개별 import.
- `test/.../PlanIntegrationTest.java` — 전체가 압축(문제 3에서 재작성).

## 표준 포맷 규칙 (auth/room 슬라이스와 동일하게)
1. **한 줄에 한 문장.** `;`로 여러 문장을 한 줄에 붙이지 마.
2. **import는 각각 별도 줄**, 와일드카드(`import ....*`) 대신 auth/room처럼 **개별 클래스 import**.
3. 클래스 선언·필드·생성자·각 메서드는 **표준 4-space 들여쓰기로 별도 블록**. 메서드 본문도 문장별 줄바꿈.
4. **XML**: 선언·DOCTYPE·`<mapper>`·`<resultMap>`·각 `<select>/<insert>/<update>/<delete>`를 **별도 줄로 들여쓰기**(room `RoomMapper.xml` 형식 그대로). 통짜 1줄 금지.
5. **DTO는 auth/room처럼 개별 파일로 분리** 권장(`CreatePlanRequest.java`·`PlanDetailResponse.java` 등). 묶음 `PlanRequests`/`PlanResponses` 유지가 불가피하면 최소한 각 record를 표준 포맷 여러 줄로. 이름은 레지스트리 §2를 따르고, 표에 없으면 이슈로 제안.

> 기준 예시: 이미 머지된 `domain/room`(RoomService.java, RoomController.java, mapper/room/RoomMapper.xml)을 그대로 본떠라.
