## 1. `clov-web#412` — 알림 배지 안 꺼짐 + 방 목록 종 아이콘 제거 (PR #415)

**이슈 조사 단계에서 중복 방지**: 새 이슈를 만들려다가 `gh issue list`로 먼저 확인 — 배지 안 꺼지는 문제는 이미 팀원(lami2342)이 `#412`에 원인 3가지(①모달 기본 탭이 항상 빈 NOTICE ②배지가 계정 전체 기준·의도된 사양 ③목록이 20건 고정, 더보기 없음)까지 코드 근거를 달아 분석해둔 상태였다. 새로 안 만들고 그 이슈를 재사용하기로 사용자가 결정.

**스코프 병합**: 처음엔 "종 아이콘 제거"를 별도 이슈로 만들려 했으나, 사용자가 "같은 알림(종 아이콘) 기능이니 같은 브랜치에서 하자, PR에 추가 작업했다는 코멘트만 남기자"고 정리 — 브랜치 하나(`fix/412-notification-badge-not-clearing`)에 세 가지를 묶었다.

**구현**:
- `Notifications.jsx`: 모달 기본 탭 `NOTICE` → `FRIEND`(원인①). "모두 읽음" 버튼 신설 — 계약에 이미 있었지만 프론트가 한 번도 안 쓰던 `PATCH .../notifications/read-all`(`markAllNotificationsRead`)을 연결(원인③).
- `Header.jsx`/`Header.css`/`api/notification.js`: 방 목록(홈) 종 아이콘 블록·전용 unread 쿼리 분기·CSS·안 쓰는 API export 제거.

**검증**: `npm run lint`·`npm run build` 통과 후, 실제 `localhost:5173`에서 room 11(스크린샷 속 그 방)에 접속해 재현 확인 — `GET /rooms/11/notifications?...size=20` 응답이 정확히 20건(원인③ 실측), "모두 읽음" 클릭 → `PATCH .../read-all` 200 → 이어진 `GET .../unread` 응답이 `{"hasUnread":false}`로 배지 소멸 확인. 방 목록 헤더 접근성 트리에서 종 아이콘 자체가 사라진 것도 확인. PR 본문에 이 네트워크 트레이스를 그대로 검증 근거로 남겼다.

사용자가 PR #415를 머지.

## 2. 파생 발견 — 가입 신청은 배지와 완전히 무관 → 계약 변경 → 철회

머지 후 사용자가 새 스크린샷(room/39)으로 질문: "여긴 가입 신청이 있는데 왜 종 배지가 안 켜져? room 11 배지가 사실 이거 오귀속이었던 거 아니야?"

**조사**: `NotificationMapper.xml`의 `existsUnreadInRoom`은 `room_id` 조건이 명시적이라 방 간 혼선은 구조적으로 불가능함을 먼저 확인(오귀속 아님). 대신 `NotificationService.java:30`에 `SUB_JOIN_REQUEST` 상수가 정의만 되고 전체 코드베이스에서 실사용처가 0건임을 발견 — `API-CONTRACT.md §13`에도 "JOIN_REQUEST는 사문화된 정의(생산자 없음), `getJoinRequests()`가 그 역할을 대신함"이라고 이미 명시돼 있었다. 즉 가입 신청은 애초에 `notifications` 테이블에 행을 안 남기도록 **의도적으로 설계**돼 있어서, 배지가 절대 안 켜지는 게 정상 동작이었다.

**하마터면 원칙을 어길 뻔한 지점**: 이 사실을 발견하기 전에 "혼자 구현할 수 있냐"는 사용자 질문에 답하려고 `InviteService.java`·`NotificationService.java`를 읽으며 구현 방향을 준비했는데, 사용자가 "내가 언제 진행하라고 했나? 질문을 한 건데?"라고 정정했다. 실제로 코드를 고치진 않았지만(읽기만 함), **다음 행동이 "혼자 구현하자" 쪽으로 기울어 있었다는 점 자체가 문제**였다 — 이후로는 조사 결과를 먼저 보고하고 반드시 확인을 받는 흐름으로 되돌렸다.

**계약 변경 결정과 진행**: 사용자가 "그래도 승인/거절 전까진 배지가 켜지게 하자"고 결정. 다만 사용자가 "계약을 바꾸려면 계약부터 고쳐야 한다"고 순서를 못박아서, 코드가 아니라 `web-design-repository`에 계약 제안 이슈(`#98`, `documentation` 라벨)부터 만들고, `API-CONTRACT.md §13`에 "PENDING 가입 신청이 있으면 `hasUnread`가 무조건 true" 규정을 추가(PR #99) — `notifications` 테이블은 안 건드리고 `room_join_requests`의 PENDING 존재 여부를 배지 판정에 OR로 얹는 설계로, 기존 "JOIN 탭은 알림 테이블과 무관하다"는 결정과 안 부딪히게 각주까지 남겼다. 사용자가 머지.

**철회**: clov-api 쪽 이슈·브랜치를 만들려는 시점에 사용자가 "서비스 차원에서는 수정하는 게 맞나, 이 기능 없어도 크게 문제될 요소는 없잖아"라고 재검토를 요청. 함께 따져본 결과 — `#412`로 이미 알림 모달 기본 탭이 FRIEND라 그 방 알림을 확인할 일이 생기면(레벨업·추억·약속 등으로 자주 발생) 대기 중인 가입 신청 배너가 이미 보이고, 우정공간이 최대 8명짜리 친한 친구 모임이라 가입 신청 자체가 드문 이벤트이며, "읽음 여부"와 "승인 필요 여부"라는 다른 개념을 배지 하나에 합치면 새로운 혼란을 만들 여지가 더 크다는 결론에 도달 — 사용자가 롤백 지시.

**롤백 처리**: `web-design-repository`에 `PR #100`으로 `§13`의 신설 규정 2곳(엔드포인트 절 불릿, 이벤트 카탈로그 교차 참조 각주)을 제거하고, changelog에는 "제안됐다가 철회"라는 사실과 사유를 새 항목으로 남겼다(과거 이력을 지우지 않고 쌓아가는 이 문서의 기존 관례를 따름). 이슈 `#98`엔 철회 사유 코멘트만 추가(이미 `#99` 머지 때 자동으로 닫혀 있었음). `clov-api`는 이슈·브랜치 둘 다 생성 전이었어서 되돌릴 코드가 아예 없었다.

## 3. 프로세스 노트

- **"진행해" 게이트가 실제로 작동한 사례**: 세션 내내 이슈/PR 초안을 먼저 제시하고 확인을 받은 뒤에만 `gh issue create`·`git push`·`gh pr create`를 실행했다. 유일한 예외는 이 작업일지 파일 — 사용자가 "이건 worklogs니까 바로 main에 해도 된다"고 명시적으로 허용.
- **계약 변경은 계약이 먼저**: 코드보다 `API-CONTRACT.md` 수정이 항상 선행돼야 한다는 걸 사용자가 직접 순서로 못박았고, 실제로 2번 항목에서 그 순서(계약 이슈 → 계약 PR → 머지 → 그다음에야 clov-api 구현 착수 예정)를 지켰다 — 철회도 같은 순서(계약부터 되돌림)로 처리했다.
- **기존에 결정된 사양을 뒤집을 뻔한 실수**: `JOIN_REQUEST`가 "사문화된 정의"라는 문구를 처음엔 놓치고 구현 이슈 초안을 준비했다가, 계약 문서를 한 번 더 정독하고서야 리더가 이미 확정해둔 설계였음을 발견했다. 계약 문서를 표면적으로 검색하는 것만으로는 부족하고, 관련 절 전체(배경 서술 포함)를 읽어야 이런 "의도된 것처럼 안 보이는 의도된 결정"을 놓치지 않는다는 교훈.
- **작은 규모 제품의 기능 판단 기준**: 2번 항목을 롤백하며 쓴 근거(8명 정원 · 이미 있는 배너로 충분 · 개념을 섞으면 생기는 새 혼란)는 앞으로 비슷한 "종 배지에 뭘 더 반영할지" 논의가 나올 때 재사용할 만한 기준이다.
