## 1. 왜 필요한가 — 현재 상태

이메일로 가입한 사용자에게 **비밀번호가 유일한 열쇠인데 복구 수단이 없다.** 잊으면 계정이 그대로 잠긴다.

| 층 | 현재 |
|---|---|
| 프론트 | `Login.jsx:215` — `setMessage('비밀번호 찾기는 추후 연결될 예정입니다.')` 안내문 한 줄 |
| 프로토타입 | `login.html:402` — 동일 placeholder("OAuth2 연동 단계에서 연결할 예정") |
| 화면명세 | `login.md:46·73` — **"실제 연동 전 안내 메시지"로 명세가 확정**돼 있다. 플로우 자체가 없다 |
| API 계약 | `PATCH /users/me/password`(로그인 상태 변경)만. **찾기/재설정 0** |
| 백엔드 | `spring-boot-starter-mail` 의존성 **없음**. 이메일 발송·인증이 프로젝트 전체에 0줄 |
| DB | 재설정 토큰 테이블 없음 |

**즉 프로토타입 이식이 아니라 신규 기능이다.** 명세 → 계약 → DB → 백엔드 → 프론트 5개 층을 새로 만든다.

### 이미 있어서 재사용하는 것

| 재사용 대상 | 위치 |
|---|---|
| `refresh_tokens` 테이블 구조(해시 저장·만료·revoke) | `05-db-unified-final.md:575` — 그대로 미러링 |
| `userMapper.updatePassword(userId, encoded)` | `UserService.java:69` |
| `refreshTokenMapper.revokeAllByUserId(userId)` | `UserService.java:70` — 비번 변경 시 전 세션 무효화 규칙이 이미 있다 |
| `RATE_LIMITED` 429 에러 코드 | 계약 §14 — **"발송/코드생성 속도 제한"으로 이미 정의돼 있다** |
| 계정 열거 방지 원칙 | 계약 §4-1 login — "실패는 이메일 존재 여부를 노출하지 않도록 **동일** 응답" |
| `client.url` (dev/prod 분기) | `application.yaml` — **아직 자바 코드에서 안 읽는다. 이 기능이 첫 소비자다** |

마지막 줄이 중요하다. 어제(#82) prod `client.url`을 `https://`로 고쳐뒀는데 소비자가 없어 검증할 방법이 없었다. **메일 링크의 베이스 주소가 정확히 그 값**이라 이번에 실제로 쓰이게 된다.

## 2. 결정 요약

| | 결정 | 이유 |
|---|---|---|
| 발송 수단 | **`MailSender` 인터페이스 + 프로필별 구현체** (dev=로그 출력, prod=SMTP) | Testcontainers 통합 테스트 73개가 진짜 메일을 쏘는 사고를 원천 차단. 나중에 Resend 등으로 갈아타도 도메인 로직 불변 |
| 토큰 저장 | **해시만 저장**(원문은 메일에만) | `refresh_tokens`와 동일. DB가 유출돼도 재설정 불가 |
| 토큰 수명 | **1시간** · **1회용** | 메일을 바로 확인하지 못하는 경우까지 감안. 1회용 + 재요청 시 이전 토큰 즉시 폐기라 살아 있는 링크는 항상 최대 1개다 |
| 응답 | **항상 200** | 계정 열거 방지(§4-1과 동일 원칙) |
| 실패 HTTP | **400** (401 아님) | ★ 프론트 `client.js`의 401 인터셉터가 refresh를 시도한다(§6-1) |
| 소셜 전용 계정 | 재설정 대상 아님. **응답은 동일**, 메일 본문에서만 안내 | "소셜 계정입니다"를 응답으로 주면 그 자체가 계정 열거 |
| 재설정 성공 시 | 해당 유저 **refresh 전부 revoke** | `PATCH /users/me/password`와 동일 규칙 |

## 3. 플로우

```
[로그인 화면] "비밀번호 찾기"
   └→ /forgot-password  (신규 화면)
        이메일 입력 → POST /auth/password/forgot
             서버: 이메일 조회
                   ├ 이메일 계정 존재      → 이전 토큰 revoke, 새 토큰 발급, 메일 발송(비동기)
                   ├ 소셜 전용(password NULL) → 토큰 없음. "소셜로 로그인하세요" 메일만
                   └ 없는 이메일           → 아무것도 안 함
             응답: 세 경우 모두 200 data:null  ← 구분 불가

[메일] "비밀번호 재설정" 링크
   └→ {client.url}/reset-password?token=<원문>
        진입 시 GET /auth/password/reset?token=  → 유효성 즉시 표시
        새 비밀번호 입력 → POST /auth/password/reset
             서버: 해시 조회 → 미사용·미만료·미revoke 확인
                   → BCrypt 저장 → 토큰 used 마킹 → refresh 전부 revoke
   └→ /login  "비밀번호가 변경되었습니다. 다시 로그인해 주세요."
```

**`GET /auth/password/reset`을 두는 이유**: 없으면 사용자가 새 비밀번호를 두 번 입력하고 제출한 **뒤에야** "만료된 링크"를 알게 된다. 화면 진입 시점에 판정하면 폼 자체를 안 띄우고 재요청 버튼을 보여줄 수 있다.

## 4. API 계약 추가안 — §4-4 신설

> 아래를 `docs/API-CONTRACT.md`의 §4-3 뒤에 넣는다.

### 4-4. 비밀번호 재설정 (2026-07-29 신설)

| Method | Path | 설명 | 인가 |
|---|---|---|---|
| POST | `/api/v1/auth/password/forgot` | 재설정 메일 요청. **결과와 무관하게 항상 200** | 비로그인 |
| GET | `/api/v1/auth/password/reset?token=` | 토큰 유효성 확인(화면 진입 시) | 비로그인 |
| POST | `/api/v1/auth/password/reset` | 재설정 실행 | 비로그인 |

**POST `/auth/password/forgot`**
```jsonc
{ "email": "a@b.com" }
// → 200  data: null   (계정 유무·소셜 여부와 무관하게 동일)
```
- 이메일 계정이 존재하면 재설정 토큰을 발급하고 메일을 보낸다. **이전에 발급된 미사용 토큰은 모두 무효화**(`revoked_at`)한다 — 살아 있는 링크가 여럿이면 안 된다.
- 소셜 전용 계정(`password` NULL)은 토큰을 발급하지 않고, 메일 본문에서 해당 소셜로 로그인하도록 안내한다. **응답은 동일하다.**
- 존재하지 않는 이메일은 아무 동작도 하지 않는다. **응답은 동일하다.**
- 메일 발송은 **비동기**다. 발송 실패도 응답을 바꾸지 않는다(응답 시간으로 계정 유무가 새는 것도 막는다).
- 속도 제한 초과 → `429 RATE_LIMITED`.

**GET `/auth/password/reset?token=...`**
```jsonc
// → 200  { "valid": true }        유효
// → 400  PASSWORD_RESET_TOKEN_INVALID   무효·만료·사용됨
```

**POST `/auth/password/reset`**
```jsonc
{ "token": "...", "newPassword": "aB3!xyzq" }
// → 200  data: null
```
- 토큰이 무효·만료·이미 사용됨 → `400 PASSWORD_RESET_TOKEN_INVALID` (**세 경우를 구분하지 않는다**).
- `newPassword`는 §4-1 비밀번호 정책(8~20자, 영문·숫자·특수문자 중 2종 이상)을 그대로 따른다. 위반 → `400 VALIDATION_FAILED`.
- 성공 시 토큰을 `used_at` 마킹하고, **해당 사용자의 refresh 토큰을 전부 revoke**한다(`PATCH /users/me/password`와 동일). 다른 기기의 세션이 모두 끊긴다.

**토큰 URL 전달에 대한 예외 명시** — §4-2는 "URL 쿼리스트링에 `accessToken`/`refreshToken` 직접 담기 금지"(로그·Referer 유출)로 못박았다. 재설정 토큰은 **메일 링크라 쿼리스트링 외 전달 수단이 없어 예외**로 둔다. 대신 위험을 세 가지로 상쇄한다:
- 수명 1시간 · **1회용** · 새 요청 시 이전 토큰 즉시 무효화
- 권한이 **비밀번호 재설정 하나뿐**이다(세션 토큰이 아니다)
- 사용 즉시 소모되므로 로그에 남은 값은 재사용 불가

**가입 시 이메일 소유 확인이 없다는 점** — §4-1의 가입은 이메일 인증 없이 즉시 로그인시킨다. 따라서 남의 이메일로 가입된 계정이 있으면 **실제 이메일 주인이 재설정으로 그 계정의 통제권을 가져갈 수 있다.** 이는 취약점이 아니라 **의도된 동작**으로 둔다 — 원래 그 이메일의 주인에게 통제권이 가는 것이 맞고, 재설정 기능이 사후 이메일 소유 확인 수단 역할을 한다. (가입 시 이메일 인증을 도입하면 이 항목을 재검토한다.)

### §14 에러 코드 추가

| code | HTTP | 의미 |
|---|---|---|
| `PASSWORD_RESET_TOKEN_INVALID` | 400 | 재설정 토큰 무효·만료·이미 사용됨(§4-4). **세 경우를 구분하지 않는다** |

> `RATE_LIMITED`(429)는 이미 정의돼 있다("발송/코드생성 속도 제한") — 그대로 쓴다.
> **401을 쓰지 않는 이유는 §4-4 아래 주석과 이 설계안 §6-1 참고.**

## 5. DB 추가안 — `password_reset_tokens`

> `api-spec/05-db-unified-final.md`의 `refresh_tokens`(:575) 바로 뒤에 넣는다. 19테이블 → 20테이블.

```sql
CREATE TABLE password_reset_tokens (
  id          BIGINT       NOT NULL AUTO_INCREMENT,
  user_id     BIGINT       NOT NULL,
  token_hash  VARCHAR(255) NOT NULL COMMENT '원문 아닌 해시 저장(refresh_tokens와 동일 방식)',
  expires_at  DATETIME     NOT NULL COMMENT '발급 +1시간',
  used_at     DATETIME     NULL COMMENT '1회용 — 재설정 성공 시 기록',
  revoked_at  DATETIME     NULL COMMENT '같은 계정이 재요청하면 이전 토큰 무효화',
  created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_password_reset_token_hash (token_hash),
  KEY idx_password_reset_tokens_user (user_id),
  CONSTRAINT fk_password_reset_tokens_user FOREIGN KEY (user_id) REFERENCES users(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**유효 판정**
```sql
used_at IS NULL AND revoked_at IS NULL AND expires_at > NOW()
```

**`used_at`과 `revoked_at`을 둘 다 두는 이유** — `refresh_tokens`는 `revoked_at` 하나만 쓴다. 여기서 나누는 것은 무효화 사유가 둘이기 때문이다: **사용자가 실제로 재설정을 완료**(`used_at`)한 것과 **새 요청이 들어와 자동 폐기**(`revoked_at`)된 것은 운영상 의미가 다르다. 판정 쿼리는 어차피 둘 다 NULL을 요구하므로 로직은 안 복잡해진다.

> 참고: 초대 코드 A안(2026-07-23)에서는 `used_at`을 "컬럼만 보존, 미사용"으로 남겼다. **여기서는 진짜 1회용이라 실제로 쓴다.**

**설계 노트 §3에 추가할 줄**
- **비밀번호 재설정(2026-07-29)**: `password_reset_tokens`는 원문이 아닌 해시를 저장하고 수명 1시간·1회용이다. 같은 계정이 재요청하면 이전 미사용 토큰을 `revoked_at`으로 즉시 폐기해 살아 있는 링크가 항상 최대 1개다. 재설정이 성공하면 `refresh_tokens`를 전부 revoke한다(계정 탈취 복구 시 공격자 세션까지 끊기 위해).

## 6. 구현 시 걸릴 함정

### 6-1. ★ 401을 쓰면 프론트 인터셉터가 오작동한다

`client.js`의 응답 인터셉터는 **401을 받으면 `/auth/refresh`를 시도**한다. 어제(#159) single-flight로 고친 바로 그 코드다.

재설정 API가 401을 반환하면:
- 비로그인 상태인데 인터셉터가 refresh를 부른다
- refresh 토큰이 없으니 실패 → `clear()` → 엉뚱한 로그아웃 처리
- 사용자에겐 "만료된 링크"가 아니라 알 수 없는 동작으로 보인다

**그래서 `PASSWORD_RESET_TOKEN_INVALID`는 400이다.** refresh 계열(`INVALID_TOKEN`·`TOKEN_EXPIRED`)이 401인 것과 다른 이유가 이것이니, 계약에 근거를 적어둬야 나중에 "일관성 없다"며 401로 바뀌지 않는다.

### 6-2. 새 화면 2개는 프로토타입에 없다

`/forgot-password`·`/reset-password`는 프로토타입에 대응 화면이 없어 **새로 그려야 한다.** 07-27 #153에서 Login을 `.proto.css`로 이식하며 확정한 패턴을 따른다.

- ⚠️ **`box-sizing: border-box` 리셋을 스코프에 반드시 넣는다.** 이 저장소엔 전역 `*` 리셋이 없고 `#root`에만 걸려 있다(#153에서 34px 어긋남의 원인).
- 검증은 `team-guides/19-프로토타입-화면-이식-함정.md`의 3단 체크리스트.

### 6-3. 로그인 가드를 붙일 때 `takeReturnTo()` 이중 소비 주의

#154에서 겪은 그대로다. 새 화면에 "로그인 상태면 리다이렉트" 가드를 넣는다면 **마운트 시점만 판정**해야 한다(effect 의존성에 `accessToken`을 넣지 말 것).

다만 이 두 화면은 **가드를 안 붙이는 쪽을 권장**한다 — 로그인 상태에서 메일 링크를 열 수 있고, 재설정에 성공하면 어차피 refresh가 전부 revoke돼 세션이 끊긴다. 성공 후 `/login`으로 보내면 충분하다.

### 6-4. 메일 발송은 비동기여야 한다

동기로 보내면 SMTP 지연이 그대로 API 응답 시간이 된다. 더 중요한 건 **응답 시간 차이로 계정 유무가 샌다**는 점이다(존재하면 발송하느라 느리고, 없으면 즉시 반환). `@Async`로 분리한다.

### 6-5. SMTP 시크릿은 `application-secret.yaml`에 넣는다

`.gitignore`·`.dockerignore`·`bootJar` 세 곳이 이미 `application-secret*`를 거른다. **오늘 스프링 도커화를 하면서 이 파일을 컨테이너에 마운트하므로 같이 처리하면 된다**(마운트 위치 `/app/application-secret.yaml` — `WORKDIR`가 `/app`이라 Spring이 `file:./`에서 찾는다).

## 7. 프론트 화면 2개

| 화면 | 라우트 | 내용 |
|---|---|---|
| 비밀번호 찾기 | `/forgot-password` | 이메일 입력 → 제출 → **항상 같은 안내**("입력하신 주소로 재설정 링크를 보냈습니다. 메일이 보이지 않으면 스팸함을 확인해 주세요.") |
| 비밀번호 재설정 | `/reset-password?token=` | 진입 시 토큰 검증 → 유효하면 새 비밀번호 + 확인 입력, 무효하면 재요청 안내 |

- 로그인 화면의 `setMessage('비밀번호 찾기는 추후 연결될 예정입니다.')`를 `/forgot-password`로 이동시키는 링크로 교체한다.
- **화면명세 `login.md:46·73`도 함께 고쳐야 한다.** 지금은 "실제 연동 전 안내 메시지"로 확정돼 있어 이 작업이 명세 위반으로 보인다.
- 비밀번호 정책 문구·검증은 Signup과 동일하게 맞춘다(8~20자, 2종 이상).
