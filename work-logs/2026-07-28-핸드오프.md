## 4. ★ 로그인이 30분마다 풀리던 버그 (#158 → PR #159)

§13의 "로그인 유지 끄고 30분 이상 두기"를 실제로 돌려보려다 나왔다. **어제 PR들의 회귀가 아니라 최초 셸 PR #2(`d1ce4cc`) 이후 한 번도 바뀌지 않은 코드였다.**

### 무슨 일이 벌어지나

만료된 액세스 토큰으로 대시보드에 들어가면:

```
refreshCallCount: 7
refreshTimes(ms): 205, 210, 211, 212, 213, 214, 215
결과: sessionStorage·localStorage 토큰 모두 삭제 → /login
```

`client.js`의 401 인터셉터가 **요청마다 독립적으로** `/auth/refresh`를 불렀다. 대시보드는 진입 시 쿼리를 7개 쏜다(`/rooms/{id}`·`/level`·`/members`·`/plans`·`/memories`·`/users/me`·`/users/me/preferences`).

서버 `AuthService.refresh`는 리프레시 토큰을 **1회용으로 회수한다**(`revokeByTokenHash`). 그래서 7번 중 1번만 200이고 나머지 6번은 401 `TOKEN_EXPIRED`인데, 그 실패가 `catch { clear() }`를 돌려 **방금 성공한 갱신이 저장한 토큰까지 지웠다.**

curl로 같은 토큰 동시 5회를 쏴서 서버 쪽 1회용 회수도 따로 확증했다 — **1×200, 4×401**.

### 해법 — in-flight Promise 공유

```js
let refreshInFlight = null

function refreshAccessToken(refreshToken) {
  refreshInFlight ??= refreshClient
    .post('/auth/refresh', { refreshToken })
    .then((refreshed) => { useAuthStore.getState().setTokens(refreshed.data.data) })
    .finally(() => { refreshInFlight = null })
  return refreshInFlight
}
```

`setTokens`에 `remember`를 넘기지 않아야 authStore가 현재 "로그인 유지" 선택을 그대로 잇는다(#144 회귀 방지).

**검증**: 갱신 호출 7회 → **1회**, 로그아웃 없이 대시보드 정상 로드, `remember='0'` 유지. **갱신이 진짜로 실패하는 경로도 확인**했다 — 리프레시 토큰까지 무효화하면 1회만 호출하고 정상 로그아웃되며 돌아올 URL도 보존된다(#137 무회귀).

> **교훈**: **회전(rotation)하는 토큰과 병렬 요청은 같이 두면 안 된다.** 재시도 로직이 요청마다 독립적이면 "하나만 성공하고 나머지가 그 성공을 지우는" 구조가 된다. 인터셉터에서 갱신을 부를 땐 single-flight가 기본이다.

## 5. 프론트 개발·배포 환경 분리 (#160 → PR #161)

`DEPLOYMENT_ENV_SPLIT_PLAN.md`의 프론트 파트 + 컨테이너 이미지 실측 문제 3건.

### ★ 계획서에 없던 구멍 — `.gitignore`가 계획을 무력화한다

계획서는 `.env.development`·`.env.production`을 만들라는데, **어제 머지된 #143의 `**/.env.*` 규칙이 이 파일들을 막고 있었다.** 파일만 만들면 팀원 클론·CI·Docker 빌드에는 여전히 없고, 개발 기본값이 그대로 운영 번들에 굳는다.

**`VITE_*`는 시크릿이 아니다** — 번들에 평문으로 박혀 어차피 공개된다. 모드별 기본값만 예외로 열고 `.env`·`.env.local`은 계속 막았다.

```
.env                IGNORED
.env.local          IGNORED
.env.development    추적 가능 ✓
.env.production     추적 가능 ✓
```

### 컨테이너 이미지에서 실측된 문제 3건

| | 문제 | 확인 방법 | 수정 |
|---|---|---|---|
| 1 | 번들에 API 주소가 `localhost:8080`으로 굳음 | 이미지 안 JS를 grep | `.env.production` + `.gitignore` 예외 |
| 2 | **SPA 딥링크가 전부 404** | 컨테이너 띄워 curl | `nginx.conf`의 `try_files` |
| 3 | 빌드 컨텍스트 130 MB | `du -sh` | `.dockerignore` |

**2번이 제일 컸다.** `nginx:alpine` 기본 설정엔 fallback이 없어 루트 말고는 전부 404였다 — 새로고침만 해도 404고, #134에서 만든 **초대 링크가 통째로 죽는다.** 호스트 nginx(`clov-api/deploy/nginx-clovlabcalss.conf`)엔 이미 fallback이 있었고 **컨테이너 이미지에만 빠져 있었다.**

**재빌드 후 결과**

```
번들 주소     http://localhost:8080/api/v1 → https://clovlabcalss.store/api/v1  (localhost 잔존 0건)
딥링크 8종    404 → 200 전부  (/assets/nope.js 는 여전히 404 = fallback 과잉 아님)
빌드 컨텍스트  130 MB → 6.2 MB
```

`.env.production`이 컨텍스트에 들어가므로 **`--build-arg` 없이도** 주소가 맞는다(Vite build는 기본이 production 모드).

> **`.dockerignore`에 `.env*`를 통째로 넣으면 안 된다.** 넣는 순간 1번이 재발한다. 파일 안에 경고 주석을 달아 뒀다.

### 범위 밖으로 남긴 것

`npm install` → `npm ci` 교체는 **하지 않았다.** 재현 가능한 빌드엔 `ci`가 맞지만 이슈 범위 밖이라 남겼다. 필요하면 별도 이슈로.

## 6. 백엔드 profile 분리 (#81 → PR #82)

`application.yaml`에 **리더가 미커밋으로 작업 중이던 분량**이 있었다. 남의 작업물이라 **먼저 그대로 커밋하고**(`e1ede9d`), **그 위에 정리했다**(`d9f2ad6`). 어디까지가 리더 작업분인지 보이게 하려는 것이다.

```diff
   profiles:
-    include:
-      - secret
     group:
-      dev: [ dev, db, secret]
-      prod: [ prod, db, secret]
+      dev: [db, secret]
+      prod: [db, secret]
     active: dev
```

prod `client.url`도 `http://` → `https://`로 고쳤다.

### ⚠️ 이 변경의 유일한 리스크

`include`를 뺐으므로 **활성 프로필이 반드시 하나는 있어야 시크릿을 읽는다.** 로컬은 `active: dev`, 운영은 `SPRING_PROFILES_ACTIVE=prod`가 그 역할을 한다. **둘 중 하나라도 빠지면 부팅이 깨진다** — 그래서 §1의 VM 작업이 필수다.

**양쪽 프로필을 실제로 부팅해 확인했다.**

```
기본 실행                      → profiles active: "dev", "db", "secret"    Started in 3.1s
--spring.profiles.active=prod  → profiles active: "prod", "db", "secret"   Started in 3.0s, 에러 0건
```

둘 다 **DB 연결에 성공해서 떴다 = 시크릿 정상 로드.**

### 파일 구조는 `---` 다중 문서 유지

계획서는 `application-dev.yaml`/`-prod.yaml` 별도 파일을 권했지만, 미커밋분이 이미 `---` 다중 문서로 같은 일을 하고 있었다. **파일이 안 늘고 "기존 미커밋 변경을 덮어쓰지 않는다"는 계획 원칙과도 맞아** 다중 문서를 유지했다.

`application-db.yaml`은 만들지 않았다. group의 `db`는 현재 **no-op 자리표시자**다.

### JAR 시크릿 판정 기준 정정

```
$ unzip -l build/libs/*.jar | grep -i application-secret
(없음)
```

이슈엔 "`.example`만 보여야 한다"고 적었지만 `build.gradle` 패턴이 `application-secret*.yaml`이라 **`.example`도 함께 빠진다.** 무해하고(JAR 안의 템플릿은 쓸모가 없다) 보안 기준인 "실제 시크릿 없음"은 충족한다. 로컬 클래스패스(`build/resources/main`)엔 남아 있어 `bootRun`은 정상이다 — #80의 의도 그대로.

## 7. Docker Desktop 복구 — "unable to start"

`docker build`가 `Error response from daemon: Docker Desktop is unable to start`로 죽었다. **빌드 에러가 아니라 엔진이 아예 안 뜬 것**이었다.

### 진단

| 확인 | 결과 |
|---|---|
| `docker version` | client 29.6.2 / **server 없음** |
| `docker-desktop` WSL 배포판 | **등록된 적 없음**(Ubuntu만) |
| `%LOCALAPPDATA%\Docker\wsl\` | **폴더 자체가 없음** |
| `log\vm\init.log` | **비어 있음** = VM 초기화 이력 0 |
| 가상화 · 디스크 | `HypervisorPresent: True` · 319 GB 여유 — **정상** |

**타임라인이 결정적이었다.**

```
10:16  Docker Desktop 4.84.0 첫 실행 → 백엔드 기동(이후 계속 실패)
10:22  WSL 2.7.11.0 MSI 설치됨       ← 백엔드가 뜬 뒤에 WSL이 바뀜
10:28~ 아이콘 클릭 = 대시보드만 다시 보임, 백엔드는 그대로
```

**새 WSL 위에서 배포판을 만들어야 하는데 옛 WSL 기준으로 뜬 백엔드가 계속 살아 있었다.** 앱 창을 닫아도 백엔드는 트레이에 남아 재시작이 안 된다. `wsl --shutdown`만으로도 안 됐던 이유가 이것이다.

### 해결

1. `Docker Desktop`·`com.docker.backend` 프로세스 **전부 강제 종료**
2. `wsl --shutdown`
3. **관리자 권한으로 Docker Desktop 실행**

곧바로 배포판이 생성됐다 — `docker-desktop` 등록, `wsl\main\ext4.vhdx`(96 MB)·`wsl\disk\docker_data.vhdx`(1,580 MB) 생성, `init.log` 61 KB, `server=29.6.2 os=linux/amd64`.

> **교훈**: Docker Desktop이 "unable to start"면 **로그의 `backend process exited` / `backend already running`을 먼저 본다.** `backend already running`만 반복된다면 재시작이 안 된 것이다. 창을 닫는 것과 종료하는 것은 다르다.

### 덤 — Testcontainers 로컬 첫 실행

Docker가 살아나면서 그동안 CI에서만 돌던 통합 테스트를 **처음 로컬에서 전부 통과**시켰다.

```
BUILD SUCCESSFUL in 1m 24s
tests: 73   failures: 0   ignored: 0   (테스트 클래스 18개)
```

clov-api #72 체크리스트의 "Docker/Testcontainers 통합 테스트" 항목에 해당한다.

## 8. 오늘 나온 교훈

- **★ 회전하는 토큰 + 병렬 요청 = single-flight 필수.** 재시도가 요청마다 독립적이면 하나만 성공하고 나머지가 그 성공을 지운다. 크래시도 로그도 없이 "가끔 로그아웃되네"로만 보인다(§4).
- **★ `.gitignore`가 계획을 조용히 무력화할 수 있다.** "파일을 만들라"는 계획을 그대로 따라도, 그 파일이 ignore 규칙에 걸리면 **팀원·CI·빌드에는 존재하지 않는다.** 새 설정 파일을 도입할 땐 `git check-ignore`로 먼저 확인할 것(§5).
- **★ 컨테이너 이미지는 띄워서 확인해야 한다.** 빌드 성공 ≠ 동작. 이미지 안 번들을 grep하고 실제 라우트를 curl해야 "localhost가 박혔다"·"딥링크가 404다"가 드러난다(§5).
- **정적 SPA를 nginx로 서빙하면 `try_files` fallback이 없는 한 루트 말고 전부 404다.** 호스트 설정엔 있는데 컨테이너엔 빠지는 식으로 갈라지기 쉽다.
- **로컬 도구가 원인일 때가 있다.** 이모지 방 이름이 400을 뱉어 서버 버그로 의심했는데, Git Bash 인라인 `-d`가 깨뜨린 것이었다. 파일로 넘기니 201(§3).
- **"프로필을 안 줘도 뜨던" 설정을 정리하면 프로필이 필수가 된다.** `include`를 빼는 변경은 배포 서버 env까지 같이 봐야 한다(§6).
- **커밋 전 `git status --short`, 커밋 후 `git show --stat`.** 공유 워킹트리에서 계속 유효했다. 오늘도 남의 파일이 섞이지 않았음을 매번 확인했다.
- **남의 미커밋 작업 위에서 일할 땐 그 작업을 먼저 그대로 커밋한다.** 그러면 리뷰에서 "어디까지가 원작이고 어디부터가 내 수정인지"가 보인다(§6).

## 11. ★ VM 배포를 Docker로 전환 — 그 과정에서 사이트를 한 번 내렸다

오후에 리더가 수업을 따라가며 배포를 컨테이너로 옮겼다. **중간에 사이트가 약 1시간 반 반쪽으로 죽어 있었고**, 원인과 복구 과정이 다음에도 그대로 재현될 만한 것이라 남긴다.

### 무슨 일이 있었나

`react-app` 컨테이너를 **80 포트에 직접 띄우면서** 호스트 nginx를 내렸다.

```
Jul 28 02:20:55 UTC   nginx.service: Deactivated successfully.   (= 11:20 KST)
```

그런데 호스트 nginx가 갖고 있던 게 두 개였다:

- **HTTPS(443) + Let's Encrypt 인증서**
- **`/api`·`/oauth2`·`/login/oauth2` 백엔드 프록시**

컨테이너 이미지의 nginx는 **정적 서빙 전용**으로 만든 것이라(#161에서 의도적으로 프록시를 뺐다 — "백엔드 주소를 이미지에 굽지 않는다") 둘 다 사라졌다.

**증상**: `http://`로는 화면이 뜨는데 `https://`는 연결 거부, `/api/v1/rooms`는 JSON이 아니라 **index.html이 돌아온다**(SPA fallback이 삼킴). 화면은 멀쩡해 보이는데 로그인만 안 되는 상태다.

### 진단 방법

밖에서 curl 한 번이면 갈린다.

```
http  → 200        nginx(또는 컨테이너)는 살아 있음
https → 연결 거부   443 리스너가 없음
/api/v1/rooms → HTML   프록시 블록이 없음
```

번들 파일명(`index-BUujd8Yp.js`)으로 **어느 빌드가 배포됐는지**도 확인된다. 이 해시가 #161 빌드와 같아서 "컨테이너가 80을 차지했다"는 추정이 굳어졌다.

### 복구 — nginx 설정을 건드리지 않는 쪽을 골랐다

컨테이너를 8081로 내리고 nginx를 프록시로 세우는 방법도 있었지만, **손댈 곳이 적은 쪽**을 택했다.

```bash
docker rm -f web api
docker create --name tmp kimmyeongjun998/react-app:latest
sudo mv /var/www/clov /var/www/clov.bak          # 지우지 않고 옮긴다
sudo mkdir -p /var/www/clov
sudo docker cp tmp:/usr/share/nginx/html/. /var/www/clov/
docker rm tmp
sudo nginx -t && sudo systemctl start nginx
```

**이미지에서 `dist`만 꺼내 기존 위치에 넣는 방식**이다. nginx의 인증서·프록시·SPA fallback을 하나도 안 건드리면서 **오늘 머지한 새 프론트를 그대로 서비스**할 수 있었다.

> **교훈**: 컨테이너에 80을 직접 주면 앞단 nginx가 통째로 밀려난다. 컨테이너로 서빙하려면 **`-p 8081:80`으로 올리고 nginx가 `proxy_pass`** 하거나, 지금처럼 **컨테이너를 빌드 산출물 저장소로만** 쓴다. 이미지 안 nginx가 프록시를 갖고 있지 않다는 걸 잊으면 매번 같은 사고가 난다.

## 12. Docker 전환에서 반복해서 걸린 함정 4개

전부 여러 번 되풀이됐다. 다음 사람이 같은 데서 시간을 쓰지 않도록 적는다.

### ① 도메인을 이미지 이름에 쓰면 레지스트리로 해석된다

```yaml
image: clovlabcalss.store/react-app:latest    # ✗
image: kimmyeongjun998/react-app:latest       # ✓
```

첫 조각에 점(`.`)이 있으면 Docker는 그걸 **레지스트리 호스트**로 본다. 실제로 웹서버에 이미지를 받으러 가서 `index.html`을 받아왔다:

```
failed to unpack image: unexpected media type text/html
```

### ② 컨테이너 안 `127.0.0.1`은 호스트가 아니다

백엔드는 호스트에서 systemd로 돈다. 컨테이너 nginx가 `proxy_pass http://127.0.0.1:8080`을 쓰면 **자기 자신**을 부른다.

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```
→ `proxy_pass http://host.docker.internal:8080;`

**`/api/v1/rooms`가 401을 주면 성공**이다(인증 요구 = 백엔드까지 도달). 이게 이번 구성에서 제일 확인하기 어려운 지점이었다.

### ③ 채팅에서 복사한 도메인이 마크다운 링크로 오염된다 ★

이것 때문에 가장 많이 헤맸다. `www.example.com` 같은 문자열을 복사하면 이렇게 들어간다:

```bash
domains=(clovlabcalss.store [www.clovlabcalss.store](https://www.clovlabcalss.store))
```

- 몇 번을 다시 써도 같은 게 들어와서 "파일이 저장이 안 되나" 싶었다
- **`sed`로 고쳐도 그대로였다** — 치환 문구 안의 `www.`가 복사되면서 **다시 링크로 바뀌었기 때문**이다. sed는 정상 동작하고 있었다
- `bash -n`이 통과할 때도 있어 더 헷갈렸다(괄호가 ASCII가 아니면 문법 오류가 안 난다). **문법이 통과해도 값은 쓰레기다**

**대응**: `www.`가 들어간 문자열은 복사로 옮기지 않는다. 이번엔 **www를 아예 뺐다** — 애초에 `www.clovlabcalss.store`는 DNS가 서버를 가리키지도 않았다(`168.126.63.1` = KT DNS 폴백). 넣었으면 certbot 검증이 실패했을 것이다.

### ④ vim이 읽기 전용으로 열리는 이유

`E45: 'readonly' option is set` → root 소유 파일을 sudo 없이 열었거나, **다른 vim이 살아 있어서**다. 실제로 SSH가 끊기며 남은 vim(PID 398508)이 파일을 잡고 있었다.


**설정 파일은 vim 대신 `sudo tee` 히어독으로 통째로 쓰는 편이 안전하다.** 이때 종료 구분자를 작은따옴표로 감싸야(`<<'구분자'`) `$${!}` 같은 문자가 셸에 먹히지 않는다.

> 이 핸드오프를 쓰면서도 같은 함정을 밟았다 — 히어독 본문 안에 예시로 `EOF`를 넣었더니 거기서 문서가 잘렸다. **본문에 등장하는 단어와 겹치지 않는 구분자를 쓸 것.**

## 13. ★ HTTPS 인증서 — certbot을 컨테이너로 옮긴 전 과정

가장 오래 걸린 부분이라 상세히 남긴다.

### 최종 구성

```
[인터넷] → :80/:443 → web 컨테이너 (nginx)
                        ├─ /                    → /usr/share/nginx/html (이미지 안 dist)
                        ├─ /api/, /oauth2/...   → host.docker.internal:8080 (호스트 systemd clov-api)
                        └─ /.well-known/...     → /var/www/certbot (ACME 챌린지)
                      certbot 컨테이너 → 12시간마다 renew (※ 아직 안 띄움 — §1)
볼륨: certbot-etc(/etc/letsencrypt) · certbot-var(/var/www/certbot)
```

파일 3개: `web-docker-compose.yaml` · `nginx/default.conf` · `init-letsencrypt.sh` (전부 VM 홈 `/home/bubaragi23`).

### 스크립트 순서에 이유가 있다

certbot과 nginx는 **닭과 달걀** 관계다. nginx는 SSL 설정을 읽으려면 인증서 파일이 있어야 뜨는데, 인증서를 받으려면 nginx가 ACME 챌린지를 서빙해야 한다. 그래서:

1. **임시(dummy) 자체서명 인증서 생성** — nginx가 일단 뜰 수 있게
2. **web 컨테이너 기동**
3. **임시 인증서 삭제**
4. **Let's Encrypt에 진짜 인증서 요청** (webroot 방식, nginx가 챌린지를 서빙)
5. **nginx 재로드**

`set -e`를 넣어 중간 실패 시 즉시 멈추게 했다. 실제로 2단계에서 두 번 멈췄고, 덕분에 인증서 요청까지 가지 않아 **발급 할당량을 쓰지 않았다.**

### 실제로 막힌 지점들

**(1) 포트 80 충돌 — 두 번 겪었다**

```
failed to bind host port 0.0.0.0:80/tcp: address already in use
```

`sudo systemctl stop nginx`를 안 했거나, 했다고 생각했지만 반영되지 않은 경우다. **세 명령을 한 번에 붙여넣지 말고 확인 관문을 둘 것**:

```bash
sudo systemctl stop nginx
sudo systemctl is-active nginx                  # inactive 여야 함
sudo ss -tlnp | grep -E ':80 |:443 '            # 아무것도 안 나와야 함
```

`ss` 출력이 빈 것을 확인하고 나서야 스크립트가 통과했다.

**(2) named volume이면 컨테이너 안에 디렉터리를 만들어야 한다**

원본 스크립트는 호스트에 `mkdir -p ./data/certbot/conf/live/<도메인>`을 한다. 그런데 compose가 `/etc/letsencrypt`를 **named volume**에 연결하면 호스트 폴더와 무관해서, 다음 `openssl`이 디렉터리가 없다며 실패한다. 한 줄 추가로 해결:

```bash
$compose run --rm --entrypoint "mkdir -p $path" certbot
```

**(3) compose 파일이 편집 중 깨졌다**

```
'services[web].extra_hosts' invalid additional host, missing IP: certbot
```

`certbot:` 서비스 블록이 들여쓰기 사고로 `extra_hosts` 목록 안으로 빨려 들어갔다. **`docker compose config`가 이걸 잡아준다** — 실행 전 한 번 돌리는 습관이 좋다. 고치는 건 통째로 다시 쓰는 게 빨랐다.

> 이때 실행한 명령은 **파싱 단계에서 실패해 아무 동작도 하지 않았다.** 인증서 요청이 안 갔으니 할당량도 안 썼다.

**(4) `certbot` 서비스에 인자를 붙여도 안 먹는다**

```bash
docker compose run --rm certbot certonly --webroot ...   # ✗ 무시된다
```

compose의 `entrypoint`가 **무한 갱신 루프**로 고정돼 있어서, 뒤에 붙인 `certonly ...`를 루프가 무시하고 그냥 돈다. 그래서 스크립트는 매번 `--entrypoint`로 덮어쓴다. **직접 `certbot certonly`를 치지 말고 스크립트를 쓸 것.**

### staging → 진짜 인증서

**`staging=1`로 먼저 돌렸다.** Let's Encrypt 테스트 서버를 쓰므로 **할당량을 안 쓰면서** 전체 흐름을 검증할 수 있다. 이때 이미 확인된 것:

```
/                 200
/login            200
/join/<코드>       200
/api/v1/rooms     401   ← 백엔드 프록시 성공
```

**★ 그런데 staging 인증서로는 브라우저 접속이 안 된다. HSTS 때문이다.**

```
NET::ERR_CERT_AUTHORITY_INVALID
웹사이트에서 HSTS를 사용하므로 지금은 clovlabcalss.store에 방문할 수 없습니다.
```

예전에 정상 인증서로 접속한 기록을 크롬이 기억해 **"고급 → 계속 진행" 링크 자체가 안 나온다.** 굳이 보려면 경고 페이지에서 `thisisunsafe`를 타이핑하면 되지만, **staging의 목적(흐름 검증)은 curl로 이미 달성**되므로 바로 실제 발급으로 넘어가는 게 맞다.

```bash
sudo sed -i 's/^staging=1/staging=0/' init-letsencrypt.sh
docker compose -f web-docker-compose.yaml down -v    # staging 인증서 삭제
./init-letsencrypt.sh
```

### 최종 검증 — `-k` 없이 통과해야 진짜다

```
Successfully received certificate.
This certificate expires on 2026-10-26.
```

| 경로 | 결과 |
|---|---|
| `/` `/login` `/join/<코드>` `/rooms/24` | **200** |
| `/api/v1/rooms` | **401** |
| `http://` | **301** → HTTPS |

`curl -k`(검증 생략)로만 200이면 staging, **`-k` 없이 200이면 진짜 인증서**다. 이 차이 하나로 판별한다.

### 발급 횟수 관리

Let's Encrypt는 **같은 도메인 주당 5회**다. 오늘 실제 발급은 **1회** 썼다(staging은 안 셈).

인증서를 백업해 두면 실습 중 날려도 복구할 수 있다:

```bash
mkdir -p ~/cert-backup
docker run --rm -v bubaragi23_certbot-etc:/src -v ~/cert-backup:/dst alpine sh -c 'cp -a /src/. /dst/'
```

복구는 `down` → `docker volume create` → 반대 방향 복사 → `up -d`.

### 언제든 되돌리는 법

```bash
docker compose -f web-docker-compose.yaml down -v
sudo systemctl start nginx
```

호스트의 `/etc/letsencrypt`와 `/var/www/clov`(+ `clov.bak`)는 그대로라 **컨테이너 이전의 잘 돌던 상태**로 즉시 복구된다. 이 안전망이 있어서 과감하게 실험할 수 있었다.

## 14. 오늘 배포에서 얻은 교훈 (§11~§13 요약)

- **★ 컨테이너에 80을 직접 주면 앞단 nginx가 통째로 밀려난다.** HTTPS·프록시·리다이렉트가 함께 사라지는데 **화면은 멀쩡해 보여서** 알아채기 어렵다. `https`와 `/api`를 따로 찔러봐야 드러난다.
- **★ 컨테이너 안 `127.0.0.1`은 호스트가 아니다.** 호스트 서비스로 프록시하려면 `extra_hosts: host.docker.internal:host-gateway`가 필요하다.
- **★ 채팅·문서에서 복사한 도메인이 마크다운 링크로 오염될 수 있다.** `sed`로 고쳐도 치환 문구가 같이 오염되면 무한히 제자리다. **문법 검사(`bash -n`)가 통과해도 값은 틀릴 수 있다.**
- **이미지 이름 첫 조각에 점이 있으면 레지스트리로 해석된다.** `도메인/이미지` 형태를 쓰지 말 것.
- **`docker compose config`를 실행 전 습관적으로 돌린다.** 들여쓰기 사고를 즉시 잡아준다.
- **staging 인증서는 HSTS가 걸린 도메인에서 브라우저로 볼 수 없다.** 검증은 curl로 하고, 눈으로 볼 단계면 바로 실제 발급으로 간다.
- **되돌릴 방법을 먼저 확보하고 실험한다.** 호스트 nginx와 `/var/www/clov`를 남겨둔 덕에 매번 1분 안에 복구할 수 있었다.
