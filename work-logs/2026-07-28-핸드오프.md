## 4. ★ 로그인이 30분마다 풀리던 버그 (#158 → PR #159)

§13의 "로그인 유지 끄고 30분 이상 두기"를 실제로 돌려보려다 나왔다. **어제 PR들의 회귀가 아니라 최초 셸 PR #2(`d1ce4cc`) 이후 한 번도 바뀌지 않은 코드였다.**

### 무슨 일이 벌어지나

만료된 액세스 토큰으로 대시보드에 들어가면:

```
refreshCallCount: 7
refreshTimes(ms): 205, 210, 211, 212, 213, 214, 215
결과: sessionStorage·localStorage 토큰 모두 삭제 → /login
```

`client.js`의 401 인터셉터가 **요청마다 독립적으로** `/auth/refresh`를 불렀다. 대시보드는 진입 시 쿼리를 7개 쏜다(`/rooms/{id}`·`/level`·`/members`·`/plans`·`/memories`·`/users/me`·`/users/me/preferences`).

서버 `AuthService.refresh`는 리프레시 토큰을 **1회용으로 회수한다**(`revokeByTokenHash`). 그래서 7번 중 1번만 200이고 나머지 6번은 401 `TOKEN_EXPIRED`인데, 그 실패가 `catch { clear() }`를 돌려 **방금 성공한 갱신이 저장한 토큰까지 지웠다.**

curl로 같은 토큰 동시 5회를 쏴서 서버 쪽 1회용 회수도 따로 확증했다 — **1×200, 4×401**.

### 해법 — in-flight Promise 공유

```js
let refreshInFlight = null

function refreshAccessToken(refreshToken) {
  refreshInFlight ??= refreshClient
    .post('/auth/refresh', { refreshToken })
    .then((refreshed) => { useAuthStore.getState().setTokens(refreshed.data.data) })
    .finally(() => { refreshInFlight = null })
  return refreshInFlight
}
```

`setTokens`에 `remember`를 넘기지 않아야 authStore가 현재 "로그인 유지" 선택을 그대로 잇는다(#144 회귀 방지).

**검증**: 갱신 호출 7회 → **1회**, 로그아웃 없이 대시보드 정상 로드, `remember='0'` 유지. **갱신이 진짜로 실패하는 경로도 확인**했다 — 리프레시 토큰까지 무효화하면 1회만 호출하고 정상 로그아웃되며 돌아올 URL도 보존된다(#137 무회귀).

> **교훈**: **회전(rotation)하는 토큰과 병렬 요청은 같이 두면 안 된다.** 재시도 로직이 요청마다 독립적이면 "하나만 성공하고 나머지가 그 성공을 지우는" 구조가 된다. 인터셉터에서 갱신을 부를 땐 single-flight가 기본이다.

## 5. 프론트 개발·배포 환경 분리 (#160 → PR #161)

`DEPLOYMENT_ENV_SPLIT_PLAN.md`의 프론트 파트 + 컨테이너 이미지 실측 문제 3건.

### ★ 계획서에 없던 구멍 — `.gitignore`가 계획을 무력화한다

계획서는 `.env.development`·`.env.production`을 만들라는데, **어제 머지된 #143의 `**/.env.*` 규칙이 이 파일들을 막고 있었다.** 파일만 만들면 팀원 클론·CI·Docker 빌드에는 여전히 없고, 개발 기본값이 그대로 운영 번들에 굳는다.

**`VITE_*`는 시크릿이 아니다** — 번들에 평문으로 박혀 어차피 공개된다. 모드별 기본값만 예외로 열고 `.env`·`.env.local`은 계속 막았다.

```
.env                IGNORED
.env.local          IGNORED
.env.development    추적 가능 ✓
.env.production     추적 가능 ✓
```

### 컨테이너 이미지에서 실측된 문제 3건

| | 문제 | 확인 방법 | 수정 |
|---|---|---|---|
| 1 | 번들에 API 주소가 `localhost:8080`으로 굳음 | 이미지 안 JS를 grep | `.env.production` + `.gitignore` 예외 |
| 2 | **SPA 딥링크가 전부 404** | 컨테이너 띄워 curl | `nginx.conf`의 `try_files` |
| 3 | 빌드 컨텍스트 130 MB | `du -sh` | `.dockerignore` |

**2번이 제일 컸다.** `nginx:alpine` 기본 설정엔 fallback이 없어 루트 말고는 전부 404였다 — 새로고침만 해도 404고, #134에서 만든 **초대 링크가 통째로 죽는다.** 호스트 nginx(`clov-api/deploy/nginx-clovlabcalss.conf`)엔 이미 fallback이 있었고 **컨테이너 이미지에만 빠져 있었다.**

**재빌드 후 결과**

```
번들 주소     http://localhost:8080/api/v1 → https://clovlabcalss.store/api/v1  (localhost 잔존 0건)
딥링크 8종    404 → 200 전부  (/assets/nope.js 는 여전히 404 = fallback 과잉 아님)
빌드 컨텍스트  130 MB → 6.2 MB
```

`.env.production`이 컨텍스트에 들어가므로 **`--build-arg` 없이도** 주소가 맞는다(Vite build는 기본이 production 모드).

> **`.dockerignore`에 `.env*`를 통째로 넣으면 안 된다.** 넣는 순간 1번이 재발한다. 파일 안에 경고 주석을 달아 뒀다.

`npm install` → `npm ci` 교체는 **하지 않았다.** 재현 가능한 빌드엔 `ci`가 맞지만 이슈 범위 밖이라 남겼다. 필요하면 별도 이슈로.

## 6. 백엔드 profile 분리 (#81 → PR #82)

`application.yaml`에 **리더가 미커밋으로 작업 중이던 분량**이 있었다. 남의 작업물이라 **먼저 그대로 커밋하고**(`e1ede9d`), **그 위에 정리했다**(`d9f2ad6`). 어디까지가 리더 작업분인지 보이게 하려는 것이다.

```diff
   profiles:
-    include:
-      - secret
     group:
-      dev: [ dev, db, secret]
-      prod: [ prod, db, secret]
+      dev: [db, secret]
+      prod: [db, secret]
     active: dev
```

prod `client.url`도 `http://` → `https://`로 고쳤다.

### ⚠️ 이 변경의 유일한 리스크

`include`를 뺐으므로 **활성 프로필이 반드시 하나는 있어야 시크릿을 읽는다.** 로컬은 `active: dev`, 운영은 `SPRING_PROFILES_ACTIVE=prod`가 그 역할을 한다. **둘 중 하나라도 빠지면 부팅이 깨진다** — 그래서 §1의 VM 작업이 필수다.

**양쪽 프로필을 실제로 부팅해 확인했다.**

```
기본 실행                      → profiles active: "dev", "db", "secret"    Started in 3.1s
--spring.profiles.active=prod  → profiles active: "prod", "db", "secret"   Started in 3.0s, 에러 0건
```

둘 다 **DB 연결에 성공해서 떴다 = 시크릿 정상 로드.**

### 파일 구조는 `---` 다중 문서 유지

계획서는 `application-dev.yaml`/`-prod.yaml` 별도 파일을 권했지만, 미커밋분이 이미 `---` 다중 문서로 같은 일을 하고 있었다. **파일이 안 늘고 "기존 미커밋 변경을 덮어쓰지 않는다"는 계획 원칙과도 맞아** 다중 문서를 유지했다.

`application-db.yaml`은 만들지 않았다. group의 `db`는 현재 **no-op 자리표시자**다.

### JAR 시크릿 판정 기준 정정

```
$ unzip -l build/libs/*.jar | grep -i application-secret
(없음)
```

이슈엔 "`.example`만 보여야 한다"고 적었지만 `build.gradle` 패턴이 `application-secret*.yaml`이라 **`.example`도 함께 빠진다.** 무해하고(JAR 안의 템플릿은 쓸모가 없다) 보안 기준인 "실제 시크릿 없음"은 충족한다. 로컬 클래스패스(`build/resources/main`)엔 남아 있어 `bootRun`은 정상이다 — #80의 의도 그대로.

## 7. Docker Desktop 복구 — "unable to start"

`docker build`가 `Error response from daemon: Docker Desktop is unable to start`로 죽었다. **빌드 에러가 아니라 엔진이 아예 안 뜬 것**이었다.

### 진단

| 확인 | 결과 |
|---|---|
| `docker version` | client 29.6.2 / **server 없음** |
| `docker-desktop` WSL 배포판 | **등록된 적 없음**(Ubuntu만) |
| `%LOCALAPPDATA%\Docker\wsl\` | **폴더 자체가 없음** |
| `log\vm\init.log` | **비어 있음** = VM 초기화 이력 0 |
| 가상화 · 디스크 | `HypervisorPresent: True` · 319 GB 여유 — **정상** |

**타임라인이 결정적이었다.**

```
10:16  Docker Desktop 4.84.0 첫 실행 → 백엔드 기동(이후 계속 실패)
10:22  WSL 2.7.11.0 MSI 설치됨       ← 백엔드가 뜬 뒤에 WSL이 바뀜
10:28~ 아이콘 클릭 = 대시보드만 다시 보임, 백엔드는 그대로
```

**새 WSL 위에서 배포판을 만들어야 하는데 옛 WSL 기준으로 뜬 백엔드가 계속 살아 있었다.** 앱 창을 닫아도 백엔드는 트레이에 남아 재시작이 안 된다. `wsl --shutdown`만으로도 안 됐던 이유가 이것이다.

### 해결

1. `Docker Desktop`·`com.docker.backend` 프로세스 **전부 강제 종료**
2. `wsl --shutdown`
3. **관리자 권한으로 Docker Desktop 실행**

곧바로 배포판이 생성됐다 — `docker-desktop` 등록, `wsl\main\ext4.vhdx`(96 MB)·`wsl\disk\docker_data.vhdx`(1,580 MB) 생성, `init.log` 61 KB, `server=29.6.2 os=linux/amd64`.

> **교훈**: Docker Desktop이 "unable to start"면 **로그의 `backend process exited` / `backend already running`을 먼저 본다.** `backend already running`만 반복된다면 재시작이 안 된 것이다. 창을 닫는 것과 종료하는 것은 다르다.

### 덤 — Testcontainers 로컬 첫 실행

Docker가 살아나면서 그동안 CI에서만 돌던 통합 테스트를 **처음 로컬에서 전부 통과**시켰다.

```
BUILD SUCCESSFUL in 1m 24s
tests: 73   failures: 0   ignored: 0   (테스트 클래스 18개)
```

clov-api #72 체크리스트의 "Docker/Testcontainers 통합 테스트" 항목에 해당한다.

## 8. 오늘 나온 교훈

- **★ 회전하는 토큰 + 병렬 요청 = single-flight 필수.** 재시도가 요청마다 독립적이면 하나만 성공하고 나머지가 그 성공을 지운다. 크래시도 로그도 없이 "가끔 로그아웃되네"로만 보인다(§4).
- **★ `.gitignore`가 계획을 조용히 무력화할 수 있다.** "파일을 만들라"는 계획을 그대로 따라도, 그 파일이 ignore 규칙에 걸리면 **팀원·CI·빌드에는 존재하지 않는다.** 새 설정 파일을 도입할 땐 `git check-ignore`로 먼저 확인할 것(§5).
- **★ 컨테이너 이미지는 띄워서 확인해야 한다.** 빌드 성공 ≠ 동작. 이미지 안 번들을 grep하고 실제 라우트를 curl해야 "localhost가 박혔다"·"딥링크가 404다"가 드러난다(§5).
- **정적 SPA를 nginx로 서빙하면 `try_files` fallback이 없는 한 루트 말고 전부 404다.** 호스트 설정엔 있는데 컨테이너엔 빠지는 식으로 갈라지기 쉽다.
- **로컬 도구가 원인일 때가 있다.** 이모지 방 이름이 400을 뱉어 서버 버그로 의심했는데, Git Bash 인라인 `-d`가 깨뜨린 것이었다. 파일로 넘기니 201(§3).
- **"프로필을 안 줘도 뜨던" 설정을 정리하면 프로필이 필수가 된다.** `include`를 빼는 변경은 배포 서버 env까지 같이 봐야 한다(§6).
- **커밋 전 `git status --short`, 커밋 후 `git show --stat`.** 공유 워킹트리에서 계속 유효했다. 오늘도 남의 파일이 섞이지 않았음을 매번 확인했다.
- **남의 미커밋 작업 위에서 일할 땐 그 작업을 먼저 그대로 커밋한다.** 그러면 리뷰에서 "어디까지가 원작이고 어디부터가 내 수정인지"가 보인다(§6).
