## 3. ★ 초대→입장 플로우 = 3중 버그였다 (디버깅 교훈)

증상: "알림에서 수락 눌렀는데 팀원이 입장이 안됨." → 3개가 겹쳐 있었다.

1. **[clov-web #72] 알림 페이지 크래시(진짜 1번 원인).** 가입신청 카드가 시각을 `request.createdAt`(존재X)으로 읽음 → 실제 필드는 `requestedAt`. `parseUtc`가 `undefined.endsWith('Z')`에서 터져 **알림 페이지 전체 화이트스크린** → A가 수락 버튼 자체를 못 봄. 수정: `createdAt→requestedAt` + `parseUtc`/`formatDate`/`formatTime` null안전화.
2. **[clov-web #73] 수락돼도 B 화면에 방 안 뜸(자동갱신).** 전역이 `refetchOnWindowFocus:false`. 대기신청 6초 폴링 + **대기신청 수 줄면 `['rooms']` 강제 invalidate**(수락 순간 신청이 사라지며 폴링 멈추는 레이스 보완).
3. **[clov-api #54] 재입장 시 500.** `room_members` UNIQUE(room_id,user_id). 방나가기=`leave`(status LEFT 행 잔존, undo와 달리 행 삭제 아님) 후 코드 재입장→수락 시 `acceptJoinRequest`가 무조건 `insert`→중복 위반→500. 수정: **멱등/revive-aware**(ACTIVE면 그대로·LEFT면 `revive`·없으면 insert, membershipId는 처리후 `findActiveByRoomIdAndUserId` 재조회).

**★ 디버깅 방법 교훈**: 백엔드 코드가 검사상 정상일 땐 **프론트 크래시/필드명 불일치부터** 의심. DB 3테이블(`room_join_requests`·`room_members`·`room_invites`) 직접 쿼리로 "어느 단계에서 끊기는지"부터 좁히면 빠름. 콘솔 에러(스택트레이스)가 결정타였음.

**초대 플로우 구조(참고, 대부분 기구현)**: JOIN(코드입력→신청)=RoomList 홈 · ACCEPT(수락/거절/5분되돌리기)=Notifications · SEND(코드 생성/복사)=대시보드 인라인 초대 모달(#69). 백엔드 §7 완비. **초대코드는 1회용**(`markUsedIfActive`). `InviteService.accept`(코드입력)는 `@Transactional` 누락(코드 USED 마킹+신청 insert 비원자적) — 미착수 후속.

## 5. ★ 캐시 방향 검토 (리더 아이디어 — "자주 쓰는 건 DB 다이렉트 말고 캐시로")

**리더 문제의식**: 자주 조회되는 것들을 매번 DB 다이렉트로 치지 말고, 자주 쓰는 것은 캐시에 얹으면 되지 않나?

**스택 현황**: 백엔드 Spring Boot + MySQL(MyBatis) — 읽기마다 DB 쿼리. 프론트 react-query — 이미 클라 캐시(`staleTime:30s`, `refetchOnWindowFocus:false`, `lib/queryClient.js`). 이번 폴링은 일부러 신선도 위해 캐시를 우회한 것.

**어디에 캐시가 맞나 (읽기 잦고 잘 안 변하는 것)**:
- `GET /rooms`(방 목록)·방 메타(이름/테마/커버)·`GET /users/me`(프로필)·우정 레벨/EXP·정적 공지 — 읽기 빈번, 변경 드묾 → 캐시 이득 큼.

**어디에 캐시가 위험한가 (실시간/협업 상태)**:
- 가입 신청(join-requests)·알림 배지·수락 상태 — **신선도가 생명**. 방금 우리가 폴링으로 staleness 버그를 고쳤는데, 여기에 서버 캐시를 얹으면 오히려 "수락했는데 안 보임"류 재발. **캐시 금지 영역.**

**선택지**:
1. **백엔드 캐시**: Spring Cache 추상화 + **Caffeine(인메모리, 단순·의존성 0에 가까움)** 또는 **Redis(다중 인스턴스·공유 캐시)**. `@Cacheable`로 hot GET에 TTL, 쓰기(`@CacheEvict`)로 무효화. → **읽기 잦은 안정 데이터부터** 소규모로.
2. **프론트**: 쿼리별 `staleTime`/`gcTime` 튜닝(이미 클라 캐시 있음). 안정 데이터는 staleTime 길게, 실시간은 짧게/폴링.
3. **HTTP 캐싱**: ETag/Cache-Control(정적 자원·거의 안 변하는 GET).

**권고(탐구 방향, 미확정)**: **캐시는 "읽기 잦고 잘 안 변하는" 데이터에만**(방 메타·프로필·레벨). **상호작용·협업 상태(신청/알림/수락)는 항상 신선하게.** 시작은 Caffeine으로 hot GET 1~2개에 얹고 **DB 부하/응답 측정 후 확대**. 다중 서버로 가면 Redis 검토. **무엇을 캐시 안 할지(신선도 필요)를 먼저 정하는 게 핵심** — 캐시 무효화 실수가 곧 "옛 데이터 보임" 버그. 계약/DB SSOT엔 캐시 전략 별도 문서로 추가 권장(예: `api-spec/`에 캐시 정책).
