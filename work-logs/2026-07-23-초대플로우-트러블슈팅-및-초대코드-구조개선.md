## Part 1 — 트러블슈팅: 초대→입장 3중 버그

### 1-1. 증상 (사용자 리포트)
> "알림에서 **수락**을 눌렀는데 팀원이 방에 **입장이 안 돼요.**"

전형적으로 모호한 리포트다. 어디서 끊기는지 알 수 없었고, 백엔드 수락 API 코드는 정적 검사상 정상으로 보였다.

### 1-2. 디버깅 접근법 (좁혀 들어간 순서)
1. **백엔드 코드가 검사상 정상일 땐 프론트 크래시/필드명 불일치부터 의심한다.**
2. **DB 3테이블을 직접 쿼리해 "어느 단계에서 끊기는지" 물리적으로 좁힌다.**
   - `room_join_requests`(신청) → `room_members`(멤버십) → `room_invites`(코드)
   - 신청은 생겼는지, 수락 후 멤버 행이 ACTIVE로 바뀌는지, 코드가 USED로 마킹되는지를 단계별로 확인.
3. **브라우저 콘솔 스택트레이스가 결정타.** "수락 버튼을 못 봤다"는 사실이 여기서 드러났다.

### 1-3. 원인 — 세 개가 겹쳐 있었다

| # | 계층 | 근본 원인 | 수정 |
|---|---|---|---|
| **#72** | 프론트 (진짜 1번 원인) | 가입신청 카드가 시각을 `request.createdAt`으로 읽음 → **실제 필드는 `requestedAt`**. `parseUtc`가 `undefined.endsWith('Z')`에서 예외 → **알림 페이지 전체 화이트스크린** → 수락하는 쪽(A)이 **수락 버튼 자체를 못 봄** | `createdAt→requestedAt`, `parseUtc`/`formatDate`/`formatTime` null 안전화 |
| **#73** | 프론트 | 수락돼도 상대(B) 화면에 방이 안 뜸. 전역 `refetchOnWindowFocus:false`라 화면이 갱신 안 됨 | 대기신청 6초 폴링 + **대기신청 수가 줄면 `['rooms']` 강제 invalidate**(수락 순간 신청이 사라지며 폴링이 멈추는 레이스 보완) |
| **#54** | 백엔드 | 나갔다 재입장 시 500. `room_members`는 `UNIQUE(room_id,user_id)`. 방나가기(`leave`)는 **status를 LEFT로만 바꾸고 행은 남김**. 이후 코드로 재입장→수락 시 `acceptJoinRequest`가 무조건 `insert` → **중복 위반 500** | **멱등/revive-aware**: ACTIVE면 그대로, LEFT면 `revive`, 없으면 insert. `membershipId`는 처리 후 재조회 |

### 1-4. 배운 점
- **"한 증상 = 한 원인"이 아니다.** 사용자에게는 "입장이 안 된다" 하나였지만 프론트 크래시·자동갱신 누락·백엔드 제약 위반 셋이 겹쳐 있었다. 하나만 고쳤으면 여전히 안 됐을 것.
- **모호한 리포트는 DB로 물리적 위치를 먼저 좁힌다.** 코드를 노려보는 것보다 3테이블 상태를 찍어보는 게 빨랐다.
- **soft-delete(LEFT 행 잔존) 테이블은 재삽입 경로에서 UNIQUE 제약을 반드시 점검.** insert 대신 revive/upsert가 정답.
- 이 세 개를 각각 **작은 PR(#72·#73·#54)로 분리**해 원인별로 리뷰·검증 가능하게 했다.

## Part 2 — 구조 개선: 초대코드 DB 무한 누적

### 2-1. 발견 계기
초대 버그를 검증하려 `room_invites` 테이블을 열었더니, **한 방(room 11)에 초대코드가 6행**(5 USED + 1 ACTIVE) 쌓여 있었다. 재발급할수록 죽은 행이 계속 남는 구조.

### 2-2. 현재 구조 (코드 근거)
`InviteService.create()` — [clov-api/.../invite/service/InviteService.java]

- 재발급마다 **무조건 `INSERT`** (`CLV-JOIN-XXXXXX` 랜덤, 72시간 만료).
- 코드는 **1회용** — 수락 시 `markUsedIfActive`로 `USED` 마킹.
- `findByRoomId`는 USED·CANCELED·EXPIRED를 **전부 포함**해 반환.

→ **재발급마다 새 행이 쌓이고, 죽은 행이 정리되지 않는다.**

### 2-3. 정직한 캘리브레이션 (중요)
- **지금 스케일(우정공간·최대 8명)에선 이 누적이 "성능 문제"가 아니다.** MySQL은 이런 작은 행 수백만 개도 거뜬하다.
- 진짜 이슈는 두 가지: **(1) 위생/설계 냄새**(죽은 행이 안 치워짐), **(2) 근본적으로 "코드를 1회용으로 둘 거냐"는 제품 결정.**
- **누적을 만드는 건 저장 기술이 아니라 "재발급마다 새 코드" 정책이다.** 따라서 가장 큰 레버는 캐시가 아니라 **의미(semantic) 결정**.

### 2-4. 대안 비교

| 방식 | 누적 | 추가 인프라 | 이 제품 적합도 |
|---|---|---|---|
| **A. 방당 고정 코드(재사용/회전)** ⭐ | **없음** (방당 1행 or rooms 컬럼) | 없음 | ★★★ |
| B. 1회용 유지 + 활성 1개 + 정리 배치 | 유계(최근만) | 없음(스케줄러) | ★★☆ |
| C. Redis 캐시(휘발 코드 TTL) | 없음(DB 미기록) | Redis 필요 | ★☆☆ (단독은 과함) |
| D. 파생/해시 코드(무저장) | 없음 | 없음 | ✕ (회전·폐기 불가) |

- **A. 방당 고정 회전 코드** — 카카오 오픈채팅·게임 파티코드·Zoom 회의코드 방식. 방마다 살아있는 코드 1개만 두고, "재발급"은 새 행이 아니라 **값을 제자리 회전(UPDATE)**. 수락 시 USED 마킹 안 함(다회용). `room_id`에 `WHERE status='ACTIVE'` 부분 유니크 인덱스로 활성 1개 보장.
- **B. 1회용 유지가 필요하면** — 방당 ACTIVE 1개 강제 + `@Scheduled` 정리 잡으로 USED·EXPIRED·CANCELED N일 경과분 하드 삭제. 감사 이력 유지하며 성장 유계화.
- **C. Redis** — `code→roomId`를 `SETEX` TTL로. 초대코드만을 위해 단독 도입은 지금 스케일엔 과함. 다만 **hot-GET 캐시(방 메타·프로필·레벨)로 Redis가 어차피 들어오면 합류 후보.**
- **D. 파생 코드** — 회전·폐기가 안 돼 revocable invite엔 부적합. 기각.

### 2-5. 캐시 원칙과의 연결
2026-07-22 캐시 검토에서 정한 원칙이 여기서도 유효하다:
- **협업·실시간 상태(가입 신청·알림·수락)는 캐시 금지** — 방금 폴링으로 고친 그 영역. 캐시 얹으면 "수락했는데 안 보임" 재발.
- **안정·읽기 위주 조회(초대코드 code→roomId)는 캐시해도 안전.**
- → "무엇을 캐시 **안** 할지"를 먼저 정하는 게 핵심.

### 2-6. 결정 (확정 — 2026-07-23)
**A안(방당 고정 회전 코드) 채택 확정. Redis는 별도 캐시 이니셔티브가 뜰 때 합류.**

- 근거: 제품 성격(8인 친구방·동등 멤버·캐주얼 공유)에 가장 맞고, **인프라 0으로 누적을 뿌리째 제거.**
- 트레이드오프(수용): "누가 어느 코드로 들어왔나" 개별 감사 이력은 약해짐 → 단, 입장 이력은 `room_join_requests`에 남아 실질 손실 작음.
- 1회용 감사가 반드시 필요하다고 판단되면 → B안으로 전환.
