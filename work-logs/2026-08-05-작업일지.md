## 2. ★★ `#92`가 6일간 멈춘 진짜 이유 — 어제의 진단도 반만 맞았다

어제 작업일지 §8은 이 PR의 정체 원인을 두 번 틀리게 진단한 것을 기록했다(머지 충돌 → 승인 대기). 그리고 룰셋을 열어 **"GitHub은 이걸 한 번도 막은 적이 없다"**로 결론냈다.

오늘 다시 열어보니 **그것도 반만 맞았다.**

```
mergeable = MERGEABLE      (충돌 없음)
build     = SUCCESS        (07-30부터 통과)
리뷰 스레드 = 0개           (미해결 없음)
상태       = BLOCKED        ← 그런데 BLOCKED
```

```json
"required_approving_review_count": 0,
"required_review_thread_resolution": true,
"dismiss_stale_reviews_on_push": false     ← 어제 안 본 줄
```

체크도 스레드도 깨끗한데 `BLOCKED`이므로, 남은 원인은 **`CHANGES_REQUESTED` 리뷰 2건**이다(07-31 06:34 · 08-04 02:18).

> **★ 어제는 `required_approving_review_count: 0`만 보고 "리뷰는 게이트가 아니다"로 읽었다.** 승인 **개수** 요구가 0인 것과, **변경 요청이 머지를 막는 것**은 다른 규칙이다. 룰셋을 열긴 했는데 **필요한 줄을 안 봤다.**
>
> 정확히 하면 — **07-31 06:34 이전까지는 실제로 아무것도 막지 않았다.** 첫 `CHANGES_REQUESTED`가 그 시각에 들어갔다. **어제 진단은 시점을 안 붙여서 틀린 문장이 됐다.**

**그리고 `dismiss_stale_reviews_on_push: false`가 결정적이었다.** 작성자가 6건을 다 고쳐 푸시해도 리뷰는 자동으로 안 풀린다. **리더가 새 리뷰를 올려 덮어야만 열린다.**

> **★ "요청만 처리되면 바로 머지된다"가 아니었다.** 어제 핸드오프에 그렇게 적혀 있었는데, 실제로는 **작성자가 할 수 있는 일이 끝나도 리더가 한 번 더 움직여야** 하는 구조였다. 그걸 모르면 양쪽이 서로를 기다린다.

## 4. ★★★ 계약 전수 검토 — 여덟 군데

리더가 *"계약을 전체 검토하고 수정해야겠다"*고 해서 골드 관련 절을 전부 다시 읽었다. 코드·DB 실측과 대조했다.

### A. 노력 순서 원칙이 총량에서 깨져 있었다

§15-4가 스스로 이렇게 썼다 — *"금액이 노력 순서를 어기면 사용자가 가장 성의 없는 경로만 반복하게 된다."*

**건당 금액만 고쳤고 하루 총량은 안 고쳤다.**

| 행동 | 건당 | 하루 최대 | 상한 3,000 대비 |
|---|---:|---:|---:|
| 마스코트 교감(클릭 한 번) | 200 | **2,000** | **67%** |
| 자유 추억(글 작성) | 200 | 600 | 20% |
| 약속 연결 추억 | 300 | 캡 없음 | — |

**클릭 10번이 하루 예산의 3분의 2였다.** 개정 전(100 × 3회 = 300 / 상한 500)에는 60%였으니 **개정 후 오히려 늘었다.**

### B. 추억 생성 응답에 `earnedGold`가 없었다

§12-1 마스코트 응답에는 있다.

```jsonc

```
> **`0`이 정상 응답이다.** 화면은 이 값으로 판단한다(`earnedGold > 0`일 때만 골드 획득 연출).

**추억 생성 응답에는 계약에도 없고 `#92`도 안 넣는다.** `#92`가 바꾼 DTO는 `MascotInteractionResponse` 하나뿐이었다.

> **★ 이게 리더가 겪은 증상의 나머지 절반이다.** 지급이 0인 이유가 넷인데(상한 초과 · 횟수 초과 · 본문 미달 · **기능이 없음**) **화면에 전부 똑같이 보인다.** 원장 조회 API도 없어서 확인할 다른 경로가 없다.
>
> **지급 코드를 넣어도 이 침묵은 그대로 남는다.** 그래서 계약 §10에 신설했다.

계약 표는 자체 제한을 *"약속에 연결된 추억만(약속당 1개라 자연 상한)"*, 하루 최대를 **`—`**로 적었다.

## 5. 개정한 값과 근거

리더 확정으로 이렇게 정했다.

| | 개정 전 | 개정 후 |
|---|---|---|
| `EARN_MEMORY_FREE` | 200 × 하루 **3회** | 200 × 하루 **10회** + **본문 20자 이상** → **오후에 3자로 인하(§14)** |
| 하루 총 상한 | **3,000** (완주 17일) | **6,000** (완주 9일) |
| `EARN_MEMORY` 자체 제한 | "자연 상한" · 하루 최대 `—` | "횟수 캡 없음" · **총 상한까지** |
| 추억 생성 201 응답 | — | **`earnedGold`** 신설 |
| 마스코트 건당 | 200 | **200 유지**(리더 판단) |

### ★ 본문 20자 조건이 왜 필요했나 (⚠️ 이 값은 같은 날 오후 3자로 내려간다 — §14)

리더가 *"하루 3번은 너무 적으니 10번으로"*라고 했을 때, 올리기 전에 확인한 것이 있다.

```java
// CreateMemoryRequest
@NotBlank @Size(max = 40) String title,   // 제목만 필수
@Size(max = 100) String content,          // 최소도 @NotBlank도 없다 — 비어도 통과
```

**제목 한 글자짜리 글도 정상 저장된다.** 3회(600골드)일 땐 감수할 만했는데 **10회면 `"ㅇ"` 열 번에 2,000골드**다.

> **★ 캡을 올릴 때는 그 캡이 무엇을 세고 있는지 다시 본다.** 횟수 캡은 "몇 번 했나"만 세지 "그게 무엇이었나"는 안 본다. **자유 추억을 사유로 분리한 근거 자체가 *"혼자 무한히 쓸 수 있다"*였는데, 횟수만으로는 그 걱정이 안 막힌다.**

**XP는 조건 없이 그대로 주고 골드만 조건부로 걸었다.** 20자 미만이어도 글은 정상 생성되고 `201`이 나간다 — 계약이 이미 못박은 *"글쓰기를 막는 건 골드 캡이 할 일이 아니다"*와 같은 원칙이라 **`400`을 만들지 않았다.**

### ★ 마스코트 200 유지가 20자 조건과 맞물렸다

A에서 클릭 200 = 글 200이 문제라고 짚었고 100으로 내리는 안을 냈는데, **리더가 200 유지를 택했다.**

> 그 선택이 성립하는 이유가 20자 조건이다 — **노력 차이를 금액이 아니라 게이트가 만든다.** 자유 추억에는 20자 관문이 붙고 마스코트에는 안 붙는다. **이 게이트를 없애면 두 값을 다시 갈라야 한다**고 계약에 적어뒀다.

### ★ 상한 6,000의 근거는 "경로별 캡의 합"이었다

```
마스코트   200 × 10 = 2,000  (자체 캡)
자유 추억  200 × 10 = 2,000  (자체 캡)
                    ───────
                      4,000  ← 상한이 3,000이면 여기서 이미 초과
약속 완주  300 × N        0  ← 예산이 안 남는다
```

**상한이 4,000 이하면 약속 완주가 예산에서 통째로 밀려난다.** 08-04 개정이 바로잡은 노력 순서가 **반대 방향으로 다시 깨진다.**

⚠️ **이 개정은 §15-4의 "카탈로그를 먼저 본다" 가드레일에 걸린다** — 카탈로그가 52,000에 멈춘 채 획득량만 2배로 올렸다. **알고 넘겼고 근거를 계약에 적었다**: 지금은 상한을 조율하는 국면이 아니라 **골드가 아예 안 도는 상태를 푸는 국면**이다.

> **★ 어제와 오늘의 일수 변동은 성격이 다르다.** 08-04의 24 → 12 → 17은 **상한을 안 건드리고 카탈로그만 움직여서** 나왔고, 오늘의 17 → 9는 **카탈로그가 멈춘 채 상한을 올려서** 나왔다. 계약의 일수 절 제목을 그렇게 고쳤다 — **같은 숫자 변화라도 무엇이 움직였는지가 다음 판단을 가른다.**

## 6. ★★★ 회귀를 하나 냈다 — 로컬 컴파일 3회 통과, CI 3회 실패

리뷰 요청 ①(`EARN_` 접두사 합산)을 반영하며 이렇게 썼다.

```sql
WHERE reason LIKE 'EARN\_%' ESCAPE '\'
```

**MySQL 구문 오류다.** 문자열 리터럴 안의 백슬래시를 이스케이프 문자로 **먼저** 해석해서 `\'`가 닫는 따옴표를 이스케이프한다.

### 증상이 컸다

`sumEarnedToday`는 `earnGold`의 **첫 쿼리**라, 이게 깨지면서 **추억 생성·마스코트 교감이 전부 `500`**이 됐다.

```
473bbba   10건 실패   ← 그중 7건은 골드와 무관한 기존 테스트(ExpIntegrationTest 3건 포함)
884e8ad    4건 실패   ← SQL은 고쳐졌고 남은 건 파급
04340a1    success
```

### ★ 로컬 통과가 무증거인 범위가 정확히 드러났다

`compileJava`·`compileTestJava`는 **세 번 다 통과했다.** CI는 세 번 다 다른 것을 잡았다.

| 2 | 테스트 기댓값 산술 | 실행해야 난다 |

> **★ 이건 08-04 §10의 "에러가 안 나는 결함"과 반대 종류다.** 조용히 틀리는 게 아니라 **요란하게 죽는다.** 그래서 **통합 테스트가 있으면 반드시 잡힌다** — 문제는 로컬에 Docker가 없어 Testcontainers를 못 돌린다는 것이고, **그동안 CI가 유일한 방어선**이다.

### 계약에도 같이 박았다

§15-4가 `reason LIKE 'EARN\_%'`를 **그대로 처방하고 있었다.** 그 형태로 구현하면 누구든 같은 함정에 빠진다. `'!'`로 못박고 이유를 적었다.

```sql

```

> **★ 계약이 SQL 조각을 처방할 때는 그게 실제로 도는 형태여야 한다.** 08-04 §15의 *"계약의 경고는 검증 가능한 형태로 적는다"*를 지켜서 `reason LIKE ...`를 박아넣었는데, **박아넣은 그 코드가 안 돌았다.** 검증 가능한 형태로 적는 것과 검증된 형태로 적는 것은 다르다.

## 9. `clov-web#289` 사후 리뷰 — 근거가 자기를 반박했다

lami2342가 오늘 00:27에 열고 **7분 만에 본인이 셀프 머지**했다(룰셋상 승인 0건이라 GitHub은 허용).

**CSS 수정 자체는 정확했다.** 캐스케이드를 대조했다.

```
@scope 내부  :207  .letter-write-card                 (0,1,0)
@scope 밖    :938  .proto-letters .letter-write-card  (0,2,0)   ← 특이도로 이긴다
```

특이도는 스코프 근접성보다 **먼저** 비교되므로 안전하다. `box-sizing: border-box`도 필수가 맞고(`padding 32+32` + `border 1+1` = 66px), `margin: 24px 0`을 2-value로 쓴 것도 맞다.

### ★ 문제는 소스에 박힌 12줄짜리 정책 주석이었다

주장은 *"이 파일의 `@scope` 내부 규칙은 사용자 환경에서 반영이 안 된다"*이고, 근거로 `Letters.jsx:136` 주석을 달았다. **그 주석도 같은 주장을 근거 없이 단언하고 있을 뿐이다** — 순환 참조다.

**그리고 그 수정 자체가 반증이다.**

```css
@scope (.proto-letters) {            /* 1~926줄 */
  .letter-tab-container { max-width: 900px; padding: 0 20px; }   /* 정렬 기준선 */
  .letter-write-card { padding: 28px 32px; border: 1px; background: ...; }
}
```

`width: 100%`가 `.letter-stage`와 같은 오른쪽 끝을 만드는 것은 **`.letter-tab-container`가 먹기 때문이다.**

> **★ `@scope`가 정말 안 먹는다면 그 카드는 배경도 테두리도 패딩도 없는 맨 텍스트여야 하고, 이번 수정도 성립하지 않는다. 화면이 멀쩡하다는 사실이 곧 `@scope`가 적용된다는 증거다.**

관측된 현상(*파일·CSSOM은 최신인데 `getComputedStyle`은 옛 값*)은 **HMR 스타일시트 이중화**의 전형적인 증상이다.

세 가지를 더 짚었다 — **원인 수정과 파일 전역 정책이 한 PR에 있는 것**(어제 `#243`에서 막은 것과 같은 형태), **이슈가 명시적으로 배제한 도구로 검증한 것**(`#286`이 *"자동화 브라우저의 `getComputedStyle`만 믿지 말 것"*이라고 적었는데 다시 그걸로 검증), **정책이 반만 적용된 것**(`:910`·`:911`은 여전히 `@scope` 안).

## 12. ★★ 배포 — `401`이 "새 빌드가 떴다"를 뜻하지 않는다

`#92`를 배포하면서 응답 코드가 이렇게 움직였다.

```
10:44  deploy-myeongjun 푸시 직후   401   ← 아직 옛 컨테이너다
       워크플로 success              -
                                    502   ← 옛 것이 내려가고 새 것이 뜨는 중
                                    401   ← 새 컨테이너
```

**푸시 직후의 `401`을 "배포 완료"로 읽을 뻔했다.** 워크플로가 빌드·이미지 push·SSH·`compose pull`·재기동까지 도는 동안 **옛 컨테이너가 계속 401을 준다.**

> **★ `401` 하나는 "어떤 clov-api가 살아 있다"까지고 "방금 만든 것이 살아 있다"가 아니다.** `401 → 502 → 401` 순서가 교체를 증명한다. 계속 401만 보였다면 워크플로가 초록이어도 컨테이너가 안 바뀌었을 수 있다.
>
> **어제 핸드오프의 "초록불은 컨테이너가 떴다까지다"에서 한 칸 더 들어간 자리다** — 초록불도 못 믿고, **401도 그것만으로는 못 믿는다.**

### ★ 그래서 헬스체크만 넣으면 신호가 하나 사라진다

`clov-api#108`의 후보 A(응답 코드로 판정)는 **판정 기준이 여전히 "401이 나오나"라 옛 컨테이너가 답해도 통과한다.** 후보 B(actuator)를 고른다면 **`/actuator/info`에 커밋 SHA를 실어 "떴나"와 "뜬 게 새 것인가"를 같은 요청으로 판정**하는 게 맞다. `#108`에 적어뒀다.

### 곁가지 — 배포 검증에서 또 한 번 대조군이 살렸다

로그인 없이 새 빌드를 증명하려고 `/v3/api-docs`에서 새 필드(`earnedGold`)를 찾았다.

```
/api/v3/api-docs   → 401       nginx는 통과하는데 permitAll 이 /v3/api-docs/** 라 /api 접두사가 붙으면 안 걸린다
/v3/api-docs       → 200 875B  그런데 nginx SPA 폴백(index.html)이다
```

**`earnedGold` 0건이길래 "아직 옛 빌드"로 판단할 뻔했다.** 대조군으로 넣은 `MemoryDetailResponse`까지 0건이라 **검색 자체가 틀렸다**는 게 드러났다.

> **08-04 §13-5가 그대로 재현됐다** — *"없다는 결과는 '찾았는데 없음'과 '안 찾아짐'을 구분하지 못한다."* 그때 배운 대로 **있어야 할 것 하나를 같이 찾은 것**이 오진을 막았다.

**결론은 이것이다 — 내 변경이 전부 인증 뒤라 로그인 없이는 내용을 증명할 수 없다.** clov-web은 배포 번들에서 문자열을 찾을 수 있지만 **clov-api는 그 수단이 없다.** springdoc이 있는데도 nginx 라우팅과 `permitAll` 경로가 어긋나 외부에서 안 닿는다.

## 13. ★★★ 원장이 답했다 — 골드는 처음부터 지급되고 있었다

배포 뒤 리더가 추억피드에 글을 올리고 **"지급이 안 된 것 같다"**고 했다. 원장을 열어보니 정반대였다.

```
142  user 14  EARN_MEMORY_FREE  +200  → 49,800   01:56:59 UTC = 10:56:59 KST
141  user 14  EARN_MASCOT       +200  → 49,600   01:56:18
140  user 14  EARN_MASCOT       +200  → 49,400   01:56:14~18 (3회)
139  user 14  EARN_MASCOT       +200  → 49,200
```

**네 건 다 정상 지급됐다.** 배포(10:44) 이후 시각이다.

### 이 네 줄이 세 가지를 한 번에 증명했다

| | |
|---|---|
| **자유 추억 지급이 작동한다** | `EARN_MEMORY_FREE 200` — `#92`가 원래 **제외**하려던 경로고 리뷰 요청 ③으로 뒤집은 자리다(§3) |
| **마스코트가 200이다** | 옛 코드면 **100**이었다. 상수가 계약값으로 바뀐 것(요청 ②)이 실제로 반영됐다 |
| **배포된 게 새 빌드다** | §12에서 `401`만으로는 증명 못 하던 것이 여기서 확정됐다 — **`EARN_` 사유 자체가 옛 코드엔 존재하지 않는다** |

### ★ 증상의 원인은 백엔드가 아니라 화면이었다

**`clov-web#178`이 안 붙어서 헤더 골드 배지가 갱신되지 않는다.** 지급은 됐는데 화면이 말을 안 한 것이다.

> **★★ 계약 검토에서 B로 짚은 것이 그대로 일어났다**(§4-B). *"지급됨 / 캡에 걸려 0 / 기능이 없음이 화면에 전부 똑같이 보인다"* — 리더가 겪은 것이 정확히 이 세 갈래 중 하나를 못 고르는 상태였다.
>
> **그리고 이 혼동이 개발자에게도 일어났다.** 같은 보고를 받고 나도 "길이 조건이 문제인가"를 먼저 의심했다. **화면이 침묵하면 사용자만 헷갈리는 게 아니라 진단도 헷갈린다.**

### ★ 그래서 §14의 3자 인하는 이 증상과 무관하다

리더가 올린 본문은 **27자**였다. **20자 기준으로도 통과하는 길이**라 처음부터 지급 대상이었다.

> **★★★ 증상 보고를 받고 값을 고치기 전에 그 값이 원인인지 먼저 재야 한다.** 3자 인하는 사진 위주 기록을 위한 **별개의 타당한 개선**이지만, 그것만 하고 넘어갔으면 **"고쳤다"고 생각한 채 원인은 그대로 남았을 것이다.** 실제로 그렇게 될 뻔했다 — 원장을 안 봤으면 `#136` 배포 후 같은 증상이 또 나왔을 때 다시 처음부터 파야 했다.

### 검증 경로 — 세 번 막히고 네 번째에 닿았다

```
① /v3/api-docs 로 스키마 확인      → nginx SPA 폴백 (§12)
② curl 401 로 새 빌드 판정          → 옛 컨테이너도 401을 준다 (§12)
③ Claude 가 DB 조회                → 분류기 차단 (원격 DB 자격증명)
④ 리더가 직접 mysqlsh 실행          → ✅ 확정
```

**③이 막힌 것은 타당하다** — 운영 DB에 자격증명을 실어 접속하는 명령이다. 우회하지 않고 **읽기 전용 쿼리 한 줄을 그대로 넘겼고**(비밀번호를 손으로 다루지 않게 `application-secret.yaml`에서 읽는 형태로), 리더가 실행해 결과를 붙였다.

> **인증 뒤 검증은 결국 사람이 한 번 움직여야 한다.** 우회법 셋(axios 스텁 · 정적 자원 `curl` · 번들 문자열)은 **전부 인증 밖에서만 통한다.** 원장·잔액·지급처럼 로그인 뒤 상태는 그 셋 어디에도 안 걸린다 — **`#135`(원장 조회 API)가 그래서 필요하다.**

## 14. ★★ 본문 길이 조건 — 같은 날 20 → 5 → 3으로 두 번 내렸다

§5에서 20자로 걸었던 조건을 오후에 두 번 내려 **3자로 확정했다.** 계약에 반영된 최종값은 3자다.

내린 이유는 **사진 위주 추억은 본문이 짧은 것이 정상**이기 때문이다. 계약 §12가 `MEMORY_IMAGE_BONUS`로 사진을 이미 노력으로 인정하는데 **골드 쪽만 글 길이로 판정해 사진 기록을 벌하고 있었다.** 사진 유무로 판정하는 게 맞지만 **작성 시점에는 사진 수를 알 수 없다** — 생성 → presign → PUT → 커밋 순서라 `CreateMemoryRequest`에 이미지 필드가 없다.

### ⚠️ 그 결과 이 값은 채굴 방지 장치가 아니다 — 빈 글만 거른다

**채굴은 전적으로 하루 10회 캡이 막는다.** 길이 조건은 몇 자로 잡든 붙여넣기면 뚫린다. **방어력을 여기에 기대지 말 것.**

### ★ 그래서 §5의 "클릭 200 = 글 200" 근거가 무너졌다

§5에서 마스코트 200 유지가 성립한 근거는 *"노력 차이를 금액이 아니라 게이트가 만든다"*였다. **3자는 클릭 한 번과 다르지 않다.** 계약에 "근거가 약해졌고 알고 넘긴다"로 고쳐 적었다.

> **★ 며칠 지켜보고, 손대야 하면 게이트를 올리는 것보다 금액을 가르는 쪽**(자유 글 200 → 150)이 먼저다. **한 번 내린 게이트를 올리면 쓰던 사람이 벌을 받는다.**

### ★ 진짜 해법은 지급 시점을 옮기는 것이다

이미지 커밋 시점(`POST /memories/{id}/images`)에 지급하면 **글 길이가 아니라 사진 유무로** 판정할 수 있다. 계약 §12가 XP에 대해 이미 그 구조를 쓴다(`MEMORY_IMAGE_BONUS`, 추억당 상한 8). **`web-design#64`(약속 골드)와 같이 검토할 것.**

⚠️ **XP는 조건 없이 그대로 준다. 골드만 조건부다.** 3자 미만이어도 글은 정상 생성되고 `201`이 나간다 — 계약이 못박은 *"글쓰기를 막는 건 골드 캡이 할 일이 아니다"*와 같은 원칙이라 **여기에 `400`을 만들지 않는다.**

## 15. ★★ 오후 — 한정 상품 둘, 그리고 "한정"을 무엇으로 표현할지 정했다

오전에 골드가 돌기 시작하자 리더가 **한정 상품 두 개**를 만들었다. 크로비 스킨과 배경이다. 값을 정하다가 **계약 규칙과 부딪혔고, 그 자리에서 표현 방식이 갈렸다.**

### 15-1. ★★★ "한정"은 값을 가르는 축이 아니다 — 프로모션 축으로 표현한다

계약 §15-4의 기준이 *"등급도 같고 내용도 같으면 값도 같게 둔다"*이다. 크로비 한정 스킨은 **LEGENDARY이고 상태 9종을 다 가진다** — 아케이드 보스 롭과 **값을 가르는 두 축에서 완전히 같다.**

**"한정이니까 비싸게"로 갔으면 그 규칙을 어겼다.**

```
price          9,800   ← 등급이 말한다 (규칙 그대로)
discount_rate     80   ← "한정"이 말한다
실효가         1,960
```

> **★ 가격 축과 프로모션 축을 분리하니 규칙이 안 깨졌다.** 정가가 등급을 말하고 할인이 희소성을 말한다. **정가를 올려 한정을 표현했다면 다음 한정 상품마다 "얼마나 올릴까"를 근거 없이 정해야 했다.**

리더가 *"할인율은 많이 줘서 누구나 구매 가능하게"*라고 해서 **80%**로 정했다. 근거 둘.

- **체감** — 가입 첫날 마스코트 10클릭(2,000)이면 닿는다. 시작 골드 1,000으로는 못 사고 **하루를 채우면 살 수 있는** 자리다
- **★ 계약 숫자가 안 낡는다** — 카탈로그가 52,000 → 53,960이 되어 완주가 **약 9일**로 계약의 9일이 그대로 맞았다. 할인 없이 넣었으면 61,800 / 10일이라 또 고쳐야 했다

**바닥은 90%다.** `9,800 × 10% = 980 > 가장 싼 COMMON 900`. 91%면 882가 되어 **최고 등급이 상점에서 제일 싼 물건**이 된다.

> **★ 처음엔 "39% 이상은 안 된다"고 했다가 정정했다.** 실효가가 EPIC(6,000)보다 싸지는 선이 39%인데, **한시적 프로모션이면 그게 정상이다** — 세일이 원래 그렇고 정가가 등급을 말해준다. **문제는 그게 안 끝날 때다.** 규칙을 뻣뻣하게 세웠다가 실제 조건을 다시 보고 풀었다.

### 15-2. ★ 그래서 해제 SQL을 등록 SQL과 같은 파일에 넣었다

`discount_rate`를 **실제로 쓰는 첫 상품**이다. 계약 §15-3이 이 필드를 *"운영 주체·주기 미정"*으로 두고 있고(오늘 `web-design#66`으로 뗀 이슈) **관리 화면이 없어서 끝내려면 SQL을 직접 돌려야 한다.**

> **등록 SQL만 남기면 "어떻게 끝내지"를 나중 사람이 처음부터 만들어야 하고, 그러면 대개 안 끝난다. "한정"이 영구 할인이 되는 경로가 이것이다.**

⚠️ **해제해도 이미 산 사람의 가격은 안 바뀐다.** `user_inventory_items.paid_price`가 구매 시점 실효가를 박아둔다(§15-1 (4)). **되돌릴 수 없다.**

### 15-3. ★★★ 등급을 올릴 때는 "한정"을 근거로 쓰면 안 된다 — 같은 이유를 두 축에 쓰는 것이다

배경 쪽에서 이게 걸렸다. 리더가 *"한정 배경도 할인 80%, 전설 등급으로"*라고 했는데, **기존 배경 4종은 전부 `RARE 2,800`**이다.

**이 배경만 등급이 다르면 무엇이 다른지를 적어야 한다.** 그런데 "한정"은 이미 `discount_rate`가 표현하고 있다.

> **★ 같은 이유를 등급 축에도 쓰면 이중 계산이다.** 그러면 다음 한정 상품에서 *"그럼 이것도 등급을 올려야 하나"*가 근거 없이 반복된다.

**진짜 근거가 따로 있었다 — 이 배경에만 CSS 효과 레이어가 붙는다.**

```
사계절 4종   정지 이미지 한 장                    RARE      2,800
이 배경      정지 이미지 + 다른 배경엔 없는 효과   LEGENDARY 9,800
```

계약 규칙이 *"등급도 같고 **내용도 같으면**"*이다. **내용이 다르니 등급이 달라도 된다.** 이렇게 적으면 규칙 안이고, *"한정이라서"*로 적으면 규칙 밖이다.

> **★ 그래서 조건이 붙는다.** 효과 레이어를 빼면 **이 등급의 근거가 사라진다** — 그때는 `RARE 2,800`으로 내리는 게 맞다. SQL 주석과 `appBackground.js` 양쪽에 적었다.

### 15-4. ★★ GIF 배경 15.4MB — 포맷 문제가 아니었다

리더가 애니메이션 GIF로 배경을 만들어 넣었다. 실측이다.

```
15,453,713 B (15.4MB) · 720 × 405 · 약 102프레임    (같은 파일이 두 곳에 있어 30.8MB)
기존 배경 10종: 1920 × 1080 · 66KB ~ 431KB
```

**두 가지가 동시에 걸렸다.** 15.4MB는 JS 번들(639KB)의 **24배**고, 720×405를 1920×1080에 깔면 **2.67배 확대**된다. 확인해보니 **이 앱은 배경 위에 덮개도 블러도 없다** — `body`가 `cover` + `fixed`로 원본을 그대로 노출한다. **한정 상품인데 화질이 제일 나쁜 게 된다.**

> **★ "GIF를 WebP로 바꾸면 해결"이 아니었다.** 1920×1080 × 102프레임이면 애니메이션 WebP도 3~8MB다. **포맷은 절반의 답이고, 나머지 절반은 "전면을 다 움직여야 하나"였다.**
>
> **"한정" 느낌은 움직임의 양이 아니라 "다른 배경엔 없는 것"에서 온다.** 베이스를 정지 이미지로, 효과를 CSS로 갈랐다.

결과가 **15.4MB → 130KB(119분의 1)**이고, 해상도는 **720×405 → 1920×1080**으로 오히려 올라갔다. 정지 이미지는 고해상도로 다시 뽑기가 훨씬 쉽다는 게 부수 효과였다.

### 15-5. ★ 쌓임 함정 — `#root`를 안 건드리고 풀었다

효과 레이어를 `body::after`로 얹으면 **`#root`보다 위에 그려져 화면 전체를 덮는다**(`#root`에 `position`/`z-index`가 없다).

**`z-index: -1`이 정확히 답이었다.**

```
html 에 background 가 없다  →  body 배경이 캔버스로 승격  →  스택 맨 아래에 칠해진다
                                      ↓
        body::before/::after (z-index: -1)  ← 배경 위 · 콘텐츠 아래
                                      ↓
                            #root (문서 순서상 뒤)
```

> **`#root`에 `position: relative; z-index: 1`을 주는 방식은 안 썼다.** 전역 쌓임을 건드리면 **모달(240~9600)과의 관계까지 다시 봐야 한다.** 어제 `#243`에서 `<ScrollRestoration />`을 막은 것과 같은 계열의 판단이다 — **원인 수정에 전역 정책 변경을 끼워넣지 않는다.**

`pointer-events: none`도 잊지 않았다. **이건 빠지면 조용히 안 죽고 화면 전체 클릭이 막힌다.**

### 15-6. 검증 — 대조군이 또 값을 했다

Browser pane이 표시되지 않아 **스크린샷은 못 찍었다**(프레임 합성이 멈춰 타임아웃한다). 대신 측정 가능한 것으로 확인했다.


### 16-6. ★★★ #345 — `@scope` 리팩터, 그리고 숨어있던 버그 발견

`letters.proto.css`·`schedule.proto.css`만 `@scope(.proto-X){}`로 스코프를 잡고 있었다(나머지 화면은 클래스 접두 방식). `@scope`는 스펙상 스코프 루트 자신엔 안 먹는 함정과, **사용자 환경에서 블록 전체가 반영 안 되는 실측된 문제**(`Letters.jsx` 기존 주석)가 있어서 반복적으로 이슈를 일으켰다.

두 파일의 `@scope` 블록을 걷어내고 안의 모든 선택자에 `.proto-letters`/`.proto-schedule` 접두사를 붙이는 작업을, 정규식 치환이 아니라 **브레이스 깊이를 추적하는 실제 CSS 파서 스크립트**를 짜서 처리했다(주석·문자열 인식, `@media`·`@keyframes`·keyframe-step 보존, 쉼표 다중 선택자 각각 접두).

> **★★ 작업 중 letters.proto.css에서 진짜 버그를 하나 발견했다.** 파일이 "스코프 밖이라 안전하다"고 주석 달아둔 구역(`.recipient-chip`, 루트 팔레트, **PR #336(#333)이 방금 고친 `.letter-write-textarea`도 포함**)이 실제로는 브레이스를 정밀 계산해보니 여전히 `@scope` 안에 있었다. 즉 "스코프 밖에 둬서 안전하다"던 근거 자체가 틀렸던 것 — 아무도(과거 세션들도, 이번 리뷰도) 눈치채지 못했던 브레이스 불일치였다. 이번 리팩터로 스코프 자체가 사라지며 이 버그도 같이 해소된다.

변환 스크립트 첫 시도에서 실제로 버그를 하나 만들었다 — `body.light-mode .proto-letters { ... }`(스코프 루트 자신을 조상 조건으로 타게팅하는 손으로 쓴 선택자)에 접두사를 또 붙여 매칭이 깨지는 걸 diff 검토로 발견해서 고쳤다. "이미 `.proto-X`를 포함하는 선택자는 건드리지 않는다"는 예외 규칙으로 처리.

작업 도중 origin/main에 `letters.proto.css`를 추가로 건드리는 커밋(#346·#347, 발송 애니메이션·이모지 제거)이 더 들어와서, 스테일해진 브랜치를 버리고 최신 main 기준으로 변환을 처음부터 다시 돌렸다. `#345` 이슈 코멘트에서 리뷰어가 "letters 관련 다른 열린 PR을 먼저 머지하고 착수하라"고 지적한 조건도, 확인해보니 착수 시점엔 이미 충족돼 있었다.

검증: 브레이스 균형·`@scope` 잔존 스크립트 재확인(0/없음) + 실제 브라우저에서 두 트리키 케이스(전역 리셋 상속, `body.light-mode` 루트 오버라이드)를 `getComputedStyle`로 직접 확인 + lint/build 통과. **PR #353은 아직 리뷰 대기 중 — 다음 세션에서 코멘트 확인부터 시작할 것.**

### 17-2. ★★★ 이번에 제일 크게 배운 것 — "증상 셋이 한 원인"

우정공간에서 **검은 띠 · 탭바가 밀림 · 화면이 좌우로 흔들림** 세 가지가 동시에 보고됐다. 셋 다 탭바를 의심하게 만드는 모양이었는데, **탭바와 마스코트를 숨겨도 넘침이 그대로**였다.

```
clientW 375 · scrollW 534 = 159px 넘침
.cline-cards 숨김 → 375   ← 범인
.clov-hdr    숨김 → 534   ← 헤더는 무관
```

- 검은 띠 = `background-attachment: fixed`라 밀린 구역엔 배경이 안 칠해진다
- 탭바 밀림 = 문서가 가로로 넘치면 `position:fixed`가 레이아웃 뷰포트를 따라 움직인다

**둘 다 결과였다.** 하나씩 숨겨가며 `scrollWidth`를 재는 것 말고는 가를 방법이 없었다.

### 17-3. ★★ CSS에서 반복해서 밟은 함정 넷

**① `1fr` ≠ `minmax(0, 1fr)`** (`#338`, 내 회귀)
`1fr`은 `minmax(auto, 1fr)`이고 그 `auto` 바닥이 **콘텐츠 최소폭**이다. `white-space:nowrap` 자식이 있으면 트랙이 통째로 부푼다. **탭이 둘일 땐 안 드러났고 `#319`에서 5개로 쪼개지자 터졌다.**

**② `overflow-x:hidden`은 반대 축을 `auto`로 승격시킨다** (`#334`)
`overflow-y:visible`이 살아 있어야 하면 `clip`을 써야 한다. `hidden`을 주면 세로 스크롤 컨테이너가 새로 생겨 hover 팝아웃이 잘린다.

**③ 미디어쿼리는 특이도를 안 올린다** (`#342`)
파일 위쪽 블록에 넣었더니 `position:static`과 `width:auto`가 **조용히 무시**됐다. 같은 특이도면 나중에 온 쪽이 이긴다 — **기본 규칙보다 뒤에 놓아야 한다.**

**④ `flex-shrink:0`은 자기 `flex-wrap`을 죽인다** (`#344`)
max-content 폭으로 굳어서 줄바꿈이 영영 안 걸린다. `max-width:100%`를 같이 줘야 한다.

### 17-4. ★★ 검증 환경 함정 — "멈춘 전환 시계"에 세 번 속았다

프리뷰 창이 표시되지 않으면 **CSS transition/animation 시계가 멈춘다**(핸드오프에 이미 적혀 있던 것). 오늘 세 번 다시 밟았다.

```
라이트 모드 색이 다크 값으로 읽힘        transition: color 가 걸려 있었다
입력 테두리가 양쪽 테마에서 같은 값       transition: border-color
window.scrollBy({behavior:'smooth'})가 0  smooth는 애니메이션이다 (auto는 정상)
```

**컴퓨티드 값을 읽기 전에 `transition:none !important`를 주입할 것.** 그리고 `behavior:'smooth'`는 이 환경에서 검증이 불가능하다 — `scrollBy` 호출을 가로채 **인자**로 확인했다.

### 17-5. ⚠️ 안 고친 것 하나 — 구조적 한계

`#329`로 마스코트 아래 **세로 페이지 스크롤**은 살렸지만, **마스코트가 시각적으로만 겹친 가로 레일은 여전히 그 자리에서 안 밀린다.**

```
after   vScroller: HTML   ← 세로는 살아남
        hScroller: null   ← 가로 레일은 못 찾음
```

`touch-action`은 **어떤 제스처를 허용할지만 정할 뿐 터치를 아래 요소로 통과시키지 않는다.** 통과시키려면 `pointer-events:none`인데 그러면 못 누른다. **떠 있는 위젯이 내용 위에 있는 한 피할 수 없다** — `#328`에 남겼다.

## 18. ★★ 저녁 — 신규 사용자 온보딩 가이드 시안 (구현 전, 설계만)

리더 제안: **처음 접속한 사용자에게 START 버튼 → 가이드**. 레퍼런스는 마인크래프트/Sun Haven, 그리고 소니 **스파이디 트래커**(`spideytracker.net`).

### 18-1. ★ 한글 픽셀 폰트는 답이 없다 — 그래서 분리한다

유명 16비트 폰트(Press Start 2P, Silkscreen)는 **전부 영문 전용**이다. 지금도 폰트만 4.3MB(몽토리 3MB + 간판 1.25MB)를 싣고 있다.

**스파이디 트래커도 똑같이 했다** — 픽셀은 테두리·버튼·캐릭터가 만들고 **한글 설명은 일반 폰트**다.

```
"START" · 로고   →  5×7 비트맵을 SVG rect로 직접 그림   폰트 0KB
한글 본문        →  기존 폰트 유지
```

### 18-2. 픽셀감은 폰트가 아니라 규칙에서 나온다

```
테두리를 box-shadow 4겹으로       border-radius 0 · 블러 0
버튼 아래 두께 → 누르면 translateY
애니메이션을 steps(2)로            보간 없이 탁탁 끊김
4px 그리드에 배치
```

### 18-3. ★★★ 마스코트 픽셀화 — A안 채택, 이유는 유지보수

| | 방식 | 결과 |
|---|---|---|
| A | 스프라이트 자동 변환 | 채택 |
| B | 손으로 픽셀 찍기 | 크로비 1종 완성, 보류 |

크로비를 실제로 손으로 찍어봤다(32×46, 12색, 도형+자동 외곽선). **B가 더 예쁘다.** 그런데 **마스코트가 7종이고 스킨은 계속 는다** — 오늘만 한정 스킨이 하나 늘었다. B로 가면 새 스킨마다 픽셀도 새로 찍어야 하고, **사용자가 고른 마스코트를 못 보여준다.**

**확정 파라미터: 세로 64px · 색 12개.**

### 18-4. ★★ 줄이는 순서가 결과를 갈랐다

처음 64px·12색으로 돌렸더니 **오히려 더 지저분했다.** 색 수가 아니라 **줄이는 방식**이 문제였다.

```
니어리스트로 줄임  →  원본 일러스트의 잡티 픽셀을 그대로 집어옴
                   →  그 잡티가 12색으로 뭉개지며 얼룩

평균으로 줄임      →  면이 먼저 고르게 정리됨
                   →  색을 줄이면 딱 떨어짐
```

**줄일 때는 평균(`imageSmoothingEnabled=true`), 보여줄 때는 `image-rendering:pixelated`.** 롭·타코군은 원래 면이 평평해 티가 안 났고, 크로비처럼 디테일 많은 캐릭터에서 바로 드러났다.

팔레트는 **중앙값 분할(median cut)로 스프라이트마다 자동 추출**한다 — 캐릭터별 색 지정이 필요 없다.

### 18-5. "몇 픽셀"은 화면 배율과 같이 봐야 한다

```
세로 32px  → 220px로 띄우면 1픽셀 = 6.9px   블록 크고 디테일 적음
세로 64px  →                    3.4px   ★ 확정
세로 96px  →                    2.3px   경계선
세로 128px →                    1.7px   픽셀로 안 읽힘. 그냥 작은 그림
```

**1픽셀이 화면 2px 아래로 내려가면 픽셀 아트가 아니다.**

### 18-6. 확정된 사양

```
위치        방 목록(RoomList) 위 모달
구성        픽셀 창 프레임 + 모서리 클로버 + 도트 배경 + 가운데 마스코트 + START
가이드      4단계 (우정공간이란 / 들어오는 두 길 / 골드 / 준비 끝) · 이전·다음·건너뛰기
마스코트    64px · 12색 · 평균 다운샘플 → median cut
저장        localStorage + sessionStorage (기기 단위, 백엔드 작업 없음)
되돌리기    프로필 드롭다운 "가이드 다시 보기"
```

### 18-7. ★ 다시 뜰지 말지 — 세 갈래로 나눈 이유

```
건너뛰기 · X            이번 방문만    sessionStorage
다시는 안 보기           영구           localStorage
끝까지 보고 "시작하기"    영구           localStorage
프로필 → 가이드 다시 보기  둘 다 지움
```

**"건너뛰기"와 "다시는 안 보기"를 합치면 둘 중 하나가 손해를 본다.** 급해서 건너뛴 사람은 다시 볼 기회가 있어야 하고, 확실히 필요 없는 사람은 영구히 꺼야 한다. **되돌릴 길(프로필 메뉴)이 없으면 "다시는 안 보기"는 일방통행이 된다.**
