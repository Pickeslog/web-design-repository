## 0. 세션 시작 — 사용자 제보 3건 조사 (작업 없이 확인만)

사용자가 클로버 화면 스크린샷 2장(일정계획 영수증 모달, 알림 목록 팝오버)과 함께 "확인만 해봐, 진행은 하지마"로 시작. 코드를 읽어 원인을 특정만 하고 수정은 보류했다.

- **일정계획 삭제 안 됨** — `PlanService.delete()`(`clov-api`)가 자식으로 `plan_checklists`·`plan_stage_photos`만 지우고 `memories`는 안 건드림. `memories.plan_id`도 `plans.id` FK(`fk_memories_plan`, ON DELETE 옵션 없음)인데, 추억 삭제는 소프트 삭제(`deleted_at`만 세팅, row는 안 지워짐)라서 그 약속에 추억이 한 번이라도 있었으면(완료된 약속은 대부분 그렇다) 삭제가 FK 위반으로 실패했다.
- **종 아이콘 배지 없음** — 4가지 알림 트리거(편지 수신·댓글·가입·레벨업) 자체는 백엔드에 이미 다 구현돼 있었다(스크린샷에도 실제로 알림이 와 있었음). 문제는 배지 UI 자체가 없었고, `notifications` 테이블엔 `idx_notifications_recipient(recipient_id, is_read, created_at)` — "안읽음 배지" 주석까지 달린 인덱스가 처음부터 파여 있었는데 그걸 쓸 조회 API가 없었다.
- **카카오/네이버 이메일 중복 로그인 안 됨**(추가 제보) — `exchange()`가 `findByOauth(provider, subject)`로만 기존 계정을 판정해서, 같은 이메일이라도 provider가 다르면 무조건 신규 취급 → `signupOAuth()`가 `uk_users_email` UNIQUE에 걸려 `EMAIL_DUPLICATED`로 영구히 막힘.

세 건 모두 "어떻게 고칠지" 방향을 여러 라운드에 걸쳐 사용자와 논의(DB 스키마를 안 건드리는 쪽, 계약 변경 최소화, 보안 리스크 때문에 자동 로그인 대신 확인 화면 추가 등)한 뒤에야 "진행해" 지시로 실제 작업을 시작했다.

## 1. `clov-api#167` — 일정계획 삭제 FK 위반 (PR #170)

**해결**: plan 삭제 전 `memoryMapper.detachAllByPlanId(planId)`로 연결된 모든 추억(소프트 삭제분 포함)의 `plan_id`를 `NULL`로 갱신 — 하드 삭제가 아니라 연결만 끊는다. 게시글은 그대로 남고 FREE MEMORY로 전환된다(`memories.plan_id` nullable = FREE MEMORY는 이미 계약·DDL에 정의된 개념). 계약 변경 없음.

## 3. 카카오/네이버 이메일 계정 연결 — `#90`/`#169`/`#407` (PR #92·#172·#409)

**정책 결정**(여러 라운드 논의): 같은 이메일 = 같은 사람으로 취급하되, **자동 로그인은 안 함** — 소셜 프로필 이메일이 실제로 검증된 값인지 100% 보장 못 해서, 확인 없이 바로 로그인시키면 계정 탈취 리스크가 있다고 판단. "이 계정으로 연결하시겠어요?" 확인 화면을 한 번 거치기로 확정.

**계약**(`web-design-repository#90`, PR #92): `exchange()` 응답에 (A)/(B) 외 **(C) `linkCandidate`** 신설 — `{ authenticated: false, linkCandidate: true, registrationToken, maskedEmail }`. `POST /auth/oauth/link-confirm` 신설. `oauth_provider`/`oauth_subject`는 최초 가입 provider 값 유지. DB 스키마 변경 없음(`registrationToken`은 기존 `OAuthOneTimeCodeStore` 그대로 재사용).

**백엔드**(`clov-api#169`, PR #172): `exchange()`가 `findByOauth` 실패 시 `findByEmail`도 확인해서 (B) 대신 (C)로 분기. `link-confirm`은 새 row 안 만들고 기존 계정으로 바로 `authenticate()`. 이메일 마스킹(`k***@gmail.com`) 헬퍼 추가.
- **CI에서 실제 버그 발견·수정**: 내가 쓴 테스트가 계약 문서 문구("401 OAUTH_CODE_INVALID")를 그대로 믿고 401을 기대했는데, 실제 코드(`ErrorCode.java`)는 처음부터 400(`BAD_REQUEST`)이었다. CI 1차 실패 → 원인 파악 → 테스트를 실제 동작(400)에 맞춰 수정 → CI 재통과. 이 발견이 4번(계약 오타 정정) PR로 이어졌다.

**프론트**(`clov-web#407`, PR #409): `OAuthRedirect.jsx`에 `linkCandidate` 상태를 `registration`(완전 신규)과 분리해서 추가. 확인 화면에서 "이 계정으로 연결하기" 또는 "다른 계정으로 로그인"(취소).

**실사용 중 실제로 크래시 재현 → 방어 코드 추가**: 사용자가 실제 카카오 계정으로 테스트하다가 "Cannot read properties of null (reading 'provider')"로 화면이 통째로 죽는 걸 겪음. 원인 조사 결과 **버그가 아니라 내 세션 관리 실수** — 새 백엔드(`feat/169` 브랜치)를 띄워둔 채 프론트만 `main`으로 되돌려서, "새 백엔드(`profile:null`) + 옛 프론트(`linkCandidate` 모름)"라는 배포 순서 불일치가 우연히 떠 있었다(아래 "4. 사고" 참고). 재발 방지로 `exchangeResult.profile`이 없으면 `'consent'`로 안 넘어가고 에러 화면으로 처리하는 방어 코드를 PR #409에 추가.

**최종 검증**: 사용자가 실제 카카오 계정으로 로그인 → 화면 녹화(ScreenToGif)로 전체 흐름 확인 — 카카오 로그인 → exchange 처리 중 → **"이 계정으로 연결할까요? w\*\*\*@naver.com 이메일로 이미 가입된 계정이 있어요"** 확인 화면 정상 렌더 → "이 계정으로 연결하기" → 로그인 성공 → 방 목록·온보딩까지 정상 진행. 백엔드·프론트·정책 결정 전부가 실사용으로 증명됨.

## 4. 사고 — 내 브랜치 전환이 사용자의 백엔드를 죽임 (교훈)

작업 중 `clov-api` 폴더에서 브랜치를 여러 번 전환하고 `gradlew` 빌드/테스트를 반복 실행했는데, 그 폴더에서 사용자가 직접 띄워놨던 백엔드 서버가 그 과정에서 죽었다("방 정보를 불러오지 못했어요" 에러로 발견). `git status`로 main 확인 → 코드 자체는 안전함을 먼저 확인 → 재기동으로 해결.

이 과정에서 얻은 것:
- `.claude/launch.json`(레포 루트, `clov-api` 하위 아님)에 `clov-api` 프리뷰 설정 추가 — 앞으로는 Browser 프리뷰 도구로 안전하게 백엔드를 띄우고 로그도 볼 수 있게 함.
- 이 컴퓨터에 `JAVA_HOME`이 시스템 차원에서 아예 설정된 적이 없었다는 것도 발견 — 사용자 환경변수로 영구 설정.
- 실행 커맨드에서 `cmd.exe`로 절대경로 `cd`를 태우면 폴더명의 한글("공용")이 코드페이지 문제로 깨진다는 것도 확인 — PowerShell + 상대경로 조합으로 우회.

**이후 사용자가 명시적으로 지적**: "머지 전에 브랜치를 자꾸 main으로 돌리지 마라" — PR 작업이 끝나면 검토·머지 편의를 위해 그 브랜치를 그대로 둬야 하는데, 습관적으로 `git checkout main`을 했던 게 방해가 됐다. 이후 브랜치 전환은 명시적 지시가 있을 때만 하는 것으로 조정.

## 5. 환경 이슈 — 로컬 Gradle 테스트 러너

원인은 못 찾았고, 다음에 clov-api를 만지는 사람은 이 문제를 다시 마주칠 수 있다.

## 6. `web-design-repository PR #93` — 계약 오타 정정 (401→400)

**배경**: 3번(#169) 작업 중 CI 실패로 발견한 것 — `API-CONTRACT.md` §4-2·§14의 `OAUTH_CODE_INVALID`가 401로 적혀 있었는데 실제 구현은 처음부터 400이었다(기존 테스트도 이미 400을 기대하고 있었음 — 문서만 실제와 어긋나 있던 pre-existing 문제, 이번 세션에서 새로 만든 불일치 아님).

**변경**: exchange/consent/link-confirm 3곳 + §14 에러 코드 표까지 총 4곳을 400으로 정정. 왜 401이면 안 되는지(§4-4 `PASSWORD_RESET_TOKEN_INVALID`와 같은 이유 — 401이면 프론트 인터셉터가 `/auth/refresh`를 시도함, `client.js:57` 직접 확인)도 근거로 남겨서 나중에 누가 다시 401로 되돌리지 않게 함. 순수 문서 정정, 코드/동작 변경 없음.

- **머지는 항상 사용자가 직접**: 7개 PR 전부 본인이 머지 버튼을 눌렀다. `main`은 이번 작업일지 파일 하나(이 파일)만 예외적으로 직접 커밋했다 — 사용자가 명시적으로 "이건 바로 main에 머지하면 된다"고 지시.
