## A. 약관/마케팅 동의 저장

### A-1. 추천안 — `users`에 동의 시각 컬럼 3개 (MVP)

동의 유형이 3개로 고정이고, 필수 2종은 가입 시 항상 참이라 **"동의 시각"만 보존**하면 충분하다. 별도 테이블/조인 없이 코덱스가 #2/#6에서 바로 반영 가능.

**05-db `users` CREATE TABLE에 삽입** (`birthdate` 다음 줄):

```sql
  birthdate             DATE         NULL,
  terms_agreed_at       DATETIME     NULL COMMENT '✚ 서비스 이용약관 동의 시각(이메일 가입 필수)',
  privacy_agreed_at     DATETIME     NULL COMMENT '✚ 개인정보 처리방침 동의 시각(이메일 가입 필수)',
  marketing_agreed_at   DATETIME     NULL COMMENT '✚ 마케팅 수신 동의 시각(선택, NULL=미동의)',
  personal_invite_code  VARCHAR(20)  NOT NULL,
```

**이미 존재하는 개발 DB에는 ALTER로 추가**(⚠️ `DROP`/`TRUNCATE` 금지 — 공유 DB):

```sql
ALTER TABLE users
  ADD COLUMN terms_agreed_at     DATETIME NULL COMMENT '서비스 이용약관 동의 시각(이메일 가입 필수)'  AFTER birthdate,
  ADD COLUMN privacy_agreed_at   DATETIME NULL COMMENT '개인정보 처리방침 동의 시각(이메일 가입 필수)' AFTER terms_agreed_at,
  ADD COLUMN marketing_agreed_at DATETIME NULL COMMENT '마케팅 수신 동의 시각(선택, NULL=미동의)'      AFTER privacy_agreed_at;
```

**⚠️ 왜 NOT NULL이 아니라 NULL인가 (중요)**
- 소셜 콜백(`/login/oauth2/code/{provider}`)은 현재 **동의 단계 없이 `users` row를 생성**한다(계약 §4). 필수 동의를 `NOT NULL`로 걸면 **소셜 가입이 깨진다.**
- 따라서 DB는 `NULL` 허용, **이메일 가입 시 앱 레벨(@Valid)에서 필수 강제**한다.
- ↪️ 남는 공백: **소셜 최초 로그인 시 약관 동의 수집 흐름이 미정.** 이건 별건으로 분리(아래 "결정 포인트 3").

### A-2. 대안 — `user_consents` 테이블 (약관 개정 이력까지)

약관이 개정될 때 "어느 버전에 동의했는지"까지 남겨야 하면 테이블이 맞다. 조인·매퍼가 늘어 MVP엔 과함.

```sql
CREATE TABLE user_consents (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  user_id       BIGINT       NOT NULL,
  consent_type  VARCHAR(20)  NOT NULL COMMENT 'service/privacy/marketing',
  agreed        BOOLEAN      NOT NULL,
  version       VARCHAR(20)  NULL COMMENT '동의한 약관 버전',
  agreed_at     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_user_consent (user_id, consent_type),
  CONSTRAINT fk_user_consents_user FOREIGN KEY (user_id) REFERENCES users(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> **추천: A-1(컬럼 3개).** 약관 버전 관리가 당장 요구사항이 아니면 컬럼이 단순·안전하다.

## C. 계약 §4 요청·응답 JSON 스키마

> 규약: 응답 봉투 `{success,data}` / `{success,error{code,message}}` · **ID는 JSON에서 문자열** · **camelCase**(DB는 snake_case, `map-underscore-to-camel-case`).
> 아래 블록을 계약 §4 표 밑에 그대로 추가.

### C-1. 공통 — 사용자 객체 · 토큰 응답

```jsonc
// UserSummary — 인증 성공 시 함께 내려주는 최소 프로필
{
  "id": "1024",                       // BIGINT → 문자열 직렬화
  "email": "example@email.com",
  "nickname": "클로버",
  "profileImageUrl": null,
  "birthdate": "1998-03-21",          // 없으면 null
  "personalInviteCode": "CLV-7X2A9K"  // 서버 생성 (E)
}
```

### C-2. `POST /api/v1/auth/signup`

```jsonc
// 요청
{
  "email": "example@email.com",
  "password": "aB3!xyzq",            // 8~20자, 영문/숫자/특수문자 중 2종 이상 (D)
  "nickname": "클로버",
  "birthdate": "1998-03-21",         // 선택, 생략/null 허용
  "profileImageUrl": null,           // 선택 — 프로필 이미지 처리는 결정 포인트 2
  "agreements": {
    "service": true,                 // 필수 (false면 거부)
    "privacy": true,                 // 필수 (false면 거부)
    "marketing": false               // 선택
  }
}
// 응답 201 — 가입 즉시 로그인 상태(결정 포인트 1)
{
  "success": true,
  "data": {
    "accessToken": "eyJ...",
    "refreshToken": "eyJ...",
    "user": { /* UserSummary */ }
  }
}
```

### C-3. `POST /api/v1/auth/login`

```jsonc
// 요청
{ "email": "example@email.com", "password": "aB3!xyzq" }
// 응답 200
{
  "success": true,
  "data": {
    "accessToken": "eyJ...",
    "refreshToken": "eyJ...",
    "user": { /* UserSummary */ }
  }
}
```

### C-4. `POST /api/v1/auth/refresh`

```jsonc
// 요청 (전송 방식은 결정 포인트 4 — 여기서는 본문 방식)
{ "refreshToken": "eyJ..." }
// 응답 200 — 회전(rotate): 기존 refresh revoke, 신규 발급
{
  "success": true,
  "data": { "accessToken": "eyJ...", "refreshToken": "eyJ..." }
}
```

### C-5. `POST /api/v1/auth/logout`

```jsonc
// 요청
{ "refreshToken": "eyJ..." }
// 응답 200 — 해당 refresh revoked_at 기록
{ "success": true, "data": null }
```

### C-6. 인증 에러 코드 (계약 §14 목록에 편입)

| code | HTTP | 발생 |
|---|---|---|
| `VALIDATION_FAILED` | 400 | `@Valid` 실패(형식·필수 누락) |
| `TERMS_REQUIRED` | 400 | 필수 약관(service/privacy) 미동의 |
| `EMAIL_DUPLICATED` | 409 | signup 시 이메일 중복 |
| `INVALID_CREDENTIALS` | 401 | login 실패 — **이메일 존재 여부 노출 금지**(동일 메시지) |
| `INVALID_TOKEN` | 401 | refresh 토큰 위조/형식 오류 |
| `TOKEN_EXPIRED` | 401 | refresh 토큰 만료 또는 `revoked_at` 있음 |
| `OAUTH_EMAIL_REQUIRED` | 400 | 소셜 로그인인데 이메일 미수신(§5, `users.email` NOT NULL 방어) |

```jsonc
// 에러 응답 예
{ "success": false, "error": { "code": "INVALID_CREDENTIALS", "message": "이메일 또는 비밀번호가 올바르지 않습니다." } }
```

### C-7. 비밀번호 정책 (D — 계약 §4에 1줄 명시)

> 비밀번호는 **8~20자, 영문·숫자·특수문자 중 2종 이상 조합.** 백엔드 `@Valid`와 프론트 규칙을 동일하게 맞춘다. (화면 signup 규칙과 일치)

## 결정 포인트 (확정해야 반영 가능)

| # | 항목 | 선택지 | 초안 |
|---|---|---|---|
| 1 | **signup 응답** | ⓐ 토큰까지 발급(가입=자동로그인) / ⓑ 성공만 → 로그인 별도 | **ⓐ** (성공 화면이 바로 우정공간으로 가는 흐름과 정합) |
| 2 | **가입 시 프로필 이미지**(B) | ① 가입 땐 생략→기본값, 이후 프로필수정서 업로드 / ② 미인증 임시 업로드 경로 신설 | **①** (구현 단순, presign 인증 문제 회피) |
| 3 | **소셜 최초 로그인 약관 동의** | ⓐ 최초 로그인 후 동의 화면 1스텝 / ⓑ 소셜은 가입=약관 자동동의 간주 | 팀 결정 필요(개인정보 이슈) |
| 4 | **refresh 토큰 전송**(보안) | ⓐ 요청 본문 / ⓑ httpOnly 쿠키 | **ⓐ**(MVP). ❌ URL 쿼리스트링 금지(§5·OAuth 로그 유출) |
| 5 | **동의 저장 방식**(A) | A-1 컬럼 3개 / A-2 `user_consents` 테이블 | **A-1** |
| 6 | **초대코드 생성 규칙**(E) | 길이·문자셋·충돌 재시도 | 예: `CLV-` + Base32 6자, 충돌 시 재생성(UNIQUE) |
