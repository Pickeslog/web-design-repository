# 코덱스 — 백엔드 구현·검증

> `rg`·`git diff`·`apply_patch` 루틴이 몸에 배어 있어 실제 코드 작업·검증에 맞다.
> **한 방향(#2 → #3 → #4 → #6)으로만** 진행. 다른 슬라이스 동시 착수 금지.

## C-1. 환경·정합성 진단 (제일 먼저 · 코드 수정 없음)

```
clov-api에서 ./gradlew test를 돌려서 DB 연결까지 초록인지 확인해줘.
실패하면 원인을 아래 중 무엇인지 구분해서 알려줘. 코드는 아직 고치지 말고 진단만 해.
- Java 버전/JAVA_HOME 문제인지
- application-secret.yaml의 접속 URL이 st4_todo로 남아 있어서인지 (st4_clov여야 함)
- build.gradle 의존성 문제인지 (특히 jjwt 누락)
- 그 외
결과를 항목별로 짧게 보고해줘.
```

## C-2. API #2 착수 (C-1이 통과한 뒤에만)

```
이슈 #2([api] DB bootstrap 및 DDL 스키마 적용)를 읽고 작업해줘.
"반드시 지킬 것"을 그대로 지켜. 특히:
- DB는 이미 존재한다. 새로 만들지 말고 "붙는 경로 복원"이다.
- DROP DATABASE / DROP TABLE / TRUNCATE 절대 금지 (공유 DB — 전원 데이터 소실)
- 기준은 api-spec/05-db-unified-final.md
- 시크릿 값은 커밋/PR/이슈에 넣지 말고 application-secret.example.yaml은 값 없는 골격만
작업 후 git diff로 변경 범위가 이슈와 맞는지 확인하고, ./gradlew test 결과를 알려줘.
```

## C-3. 이후 순서 (참고 — 하나씩)

```
#2 머지 후 → #3(응답 봉투) → #4(Security+JWT, jjwt 0.12.6 추가) → #6(Auth 4종)
각 이슈의 "반드시 지킬 것"을 매번 다시 읽고 시작. 특히 #4는 role 컬럼/claim 금지.
```

# 클로드 코드 — 문서 정합성 감사

> 여러 문서를 동시에 놓고 모순 찾기에 강하다. 코드 구현보다 이쪽을 맡긴다.
> 코덱스가 밟을 지뢰를 앞에서 제거하는 역할.

## L-1. 계약 ↔ DB ↔ 화면 정합성 (로그인/회원가입 우선)

```
web-design-repository의 docs/API-CONTRACT.md와 api-spec/05-db-unified-final.md와
test-web-design의 화면 명세가 서로 어긋나는 곳을 찾아줘.
지금은 로그인·회원가입 흐름만 집중해서:
- 계약 §4의 요청/응답 필드
- DB users 테이블 컬럼
- 화면(01-auth/login.html·signup.html) 입력 폼
이 셋이 일치하는지, 빠지거나 이름이 다른 필드가 있는지 표로 정리해줘.
코드는 고치지 말고 발견만.
```

## L-2. 문서 충돌 정리 (이미 발견된 것 검증·확장)

```
work-logs/2026-07-20-레포진단-및-카카오-OAuth설정.md §2에
"문서 주장과 실제 레포 불일치 5건"이 정리돼 있어.
이게 지금도 유효한지 다시 확인하고, 특히:
- roadmap.md §7 / 팀-시작가이드.md §5는 "입장흐름·인증방식 결정 필요"라고 하는데
  API-CONTRACT.md는 이미 확정 선언했다. 이 충돌을 어떻게 정리할지 제안해줘.
바꿀 문서와 문구까지 구체적으로. 실제 수정은 하지 말고 제안만.
```

## L-3. OAuth 구현 전 사전 점검 (API #5 대비)

```
API #5(소셜 로그인 3사) 착수 전에, 계약 §4와
work-logs/2026-07-20-레포진단-및-카카오-OAuth설정.md §5를 대조해서
구현 시 걸릴 지점을 미리 목록으로 만들어줘. 특히:
- 소셜 콜백 후 프론트로 토큰 전달하는 방식이 계약에 명세돼 있는지 (없으면 결정 필요 항목)
- users.email이 NOT NULL인데 이메일 못 받는 케이스 처리
- 네이버 response 래핑, 카카오 client-secret ON
발견을 이슈 코멘트로 달 수 있게 정리해줘.
```
