## 2. 줄기 하나 — 스킨이 다섯에서 열둘로, 마스코트가 한 화면에서 네 화면으로

아침에 스킨은 5종이었고 마스코트는 **우정공간에서만** 보였다.

```
오전  오닉스 '블랙스타 공방'  ·  롭 '옐로우 크루'  ·  타코군 '수박껍질모자'
      마스코트를 추억피드·행운편지·일정계획에도
저녁  크로비 '마법학교 학생' · 크로비 '개발 경력자' · 김철수 '신입 개발자' · 롭 '탐험가'
```

| | 아침 | 저녁 |
|---|---|---|
| 스킨 | 5종 | **12종** |
| 스킨을 가진 마스코트 | 4/6 | **5/6** (버거노인만 없다) |
| 마스코트가 보이는 화면 | 1곳 | **4곳** |
| 등급 층 | COMMON 비어 있음 | **네 층 전부 채워짐** |
| 상점에서 살 수 있는 것 | 자리표시 12종 + 스킨 5종 | **전부 스킨** (자리표시 11종은 판매 종료, §9) |

**크로비가 3종으로 가장 많아졌다.** 하루에 스킨이 2.4배가 됐다.

**COMMON 층이 처음 열린 게 크다.** 900골드는 시작 골드 1,000 아래라 **가입 첫날 바로 살 수 있고**, 거기에 캐릭터가 둘(롭·타코군)이라 첫 스킨에 선택지가 생긴다.

### 등급마다 같은 값 쌍이 생겼다

```
COMMON      900  옐로우 크루 · 수박껍질모자
UNCOMMON  1,500  철골 작업반 · 블랙스타 공방
EPIC      6,000  마지막 신호병 · 오션 구조대
LEGENDARY 9,800  벚꽃 세트 · 아케이드 보스
```

어제 정한 규칙 — **등급도 같고 내용(상태 9종)도 같으면 값도 같게 둔다** — 이 그대로 네 번 적용됐다. 값을 가르는 두 축이 모두 같은데 다른 값을 붙이면 그게 근거 없는 숫자다.

COMMON만 예외적으로 **새 최고가**를 만들었다. 기존 두 줄(아이보리 500·클로버 배지 600)이 장식 하나짜리라 상태 9종 스킨과 내용이 다르기 때문이다. 선례도 있다 — ROV 조종사가 RARE 최고 2,400을, 마지막 신호병이 EPIC 최고 5,200을 넘었다.

## 3. ★★ 같은 결함에 반대 판정을 두 번 내렸고 둘 다 맞았다

오늘 가장 값진 것이다.

두 스킨에서 **똑같은 종류의 결함**이 나왔다. 배경 제거가 덜 끝나 캔버스 코너와 최하단 행에 고립 픽셀이 남아 있었다.

| | 알파 | bbox 하단 | 판정 |
|---|---|---|---|
| `rob/yellow-crew/angry.png` | **41** (코너), 1~8 (나머지) | **639** — 같은 폴더 다른 8장(471~539)에서 168px 벗어남 | **지웠다** |
| `tako-gun/watermelon` 9장 전부 | **3~8** | 594~626 — 정상 대역 | **안 지웠다** |

### 기준은 "잔여물이 있느냐"가 아니었다

```csharp
// scripts/mascot/SpriteTool.cs
private const int ALPHA_THRESHOLD = 8;
...
if (buf[row + x * 4 + 3] > ALPHA_THRESHOLD) {
```

**정규화 도구가 알파 8 이하를 이미 무시한다.** 그러니 판정은 이렇게 갈린다.

- 수박껍질모자의 알파 3~8 → **도구도 렌더도 못 본다.** 9장을 재인코딩하면 폴더가 300KB 넘게 커지는데 얻는 게 없다
- 옐로우 크루의 알파 41 → **임계값을 넘는다.** bbox가 캔버스 바닥까지 잡혀서, 이 상태로 정규화를 돌리면 면적 기준 배율 계산이 망가진다

> **판정 기준을 "결함이 있느냐"에 걸면 둘 다 지운다. "도구와 렌더가 그걸 보느냐"에 걸어야 둘이 갈린다.**
> 어제 정규화 판정을 `scale`이 아니라 `캔버스 균일성`에 건 것과 같은 계열이다 — **기준은 증상이 아니라 원인에 건다.**

### 순수 빨강이 단서였다

옐로우 크루의 잔여 픽셀 중 둘이 `RGB(255,0,0)`이었다. **노란 로봇·파란 멜빵·갈색 케이블에 순수 빨강이 있을 자리가 없다.** 크로마키 배경을 지운 흔적이다.

중간에 "크로마키 흔적" 자동 검출기를 만들어봤는데 **오닉스에서도 100건 넘게 잡혔다.** 반투명 아웃라인을 오탐한 것이라 버렸다. 검출기를 믿지 않고 **면별 분해(상/하/좌/우)로 돌아간 게 맞았다** — 케이블이 우측을 관통하는 것(정상)과 코너 잔여물(결함)이 그때 갈렸다.

### 이건 재발 중이다

스킨 **두 종 연속**으로 나왔고, `metadata.json`의 `states` 값이 **두 번 다 절대 경로**였다(기존 6종은 파일명만 쓴다). 매번 검사해서 잡는 것보다 **내보내기 쪽에서 끝내는 게 맞다.**

## 4. ★★ 알림 `type`을 무엇으로 가를지 정했다 — 그리고 첫 답을 뒤집었다

lami2342가 `clov-api#122`를 열었다. **나가기 확인창은 "남은 멤버에게 나갔다고 알림이 가요"라고 하는데 실제로는 안 간다.** 계약 §13 프로즈도 "입·퇴장"을 약속하는데 표에 행이 없었다.

`MEMBER_LEFT`를 신설하는 건 명확했다. 문제는 **어느 `type` 탭에 넣느냐**였다.

### 처음엔 JOIN이 맞아 보였다

짝인 `MEMBER_JOINED`가 JOIN에 있으니 대칭이 맞고, FRIEND에 넣으면 입장과 퇴장이 다른 탭으로 갈린다. 그렇게 정리해서 이슈에 올렸다.

### 코드를 보고 전제가 틀렸음을 알았다

```js
// Notifications.jsx
enabled: activeTab !== 'JOIN',                                       // :59  JOIN이면 알림 조회를 안 한다
const joinRequestsQuery = useQuery({ ... getJoinRequests(roomId) })  // :61  대신 가입신청 리소스
{tab.id === 'JOIN' && pendingRequests.length > 0 && ...}             // :130 뱃지도 신청 건수
{activeTab === 'JOIN' ? <JoinRequestList ... /> : ...}               // :136
```

탭 라벨도 `'가입 신청'`이다. **JOIN 탭은 알림 피드가 아니라 승인/거절하는 처리함이었다.**

그래서 두 가지가 뒤집혔다.

1. 내가 걱정한 **"JOIN_REQUEST 건수 희석"은 근거가 없었다** — 뱃지가 알림이 아니라 가입 신청 리소스를 센다
2. 대신 더 큰 문제가 있었다 — **JOIN에 넣으면 알림 목록 어디에도 안 뜬다**

### 그래서 기준을 다시 세웠다

계약 §13이 이미 **"`type` = 어느 탭에 보일지"** 라고 정의하고 있었다. 주제 분류가 아니다. 그러면 탭의 성격이 곧 기준이 된다.

> **알림은 주제축("멤버에 관한 것끼리 묶는다")이 아니라 행동축("처리할 게 있나")으로 먼저 가른다.**
> 처리함은 비워야 하는 통이라, 안 없어지는 정보성 항목이 섞이면 뱃지가 0이 되지 않고 그때부터 사용자가 뱃지를 무시한다.

| | 사용자가 할 일 | 통 |
|---|---|---|
| 가입 신청 | 승인/거절해야 함 | 처리함 |
| 입장·퇴장·추억·약속·레벨업 | 알기만 하면 됨 | 피드 |

`MEMBER_LEFT`는 **FRIEND**로 확정했다(`web-design-repository#50`).

### 원칙이 그 자리에서 확산됐다

같은 구조 때문에 **`JOIN_ACCEPTED`도 알림 화면에 안 뜬다**는 게 드러났다. 어제 `#113`으로 "승인됐는데 아무 소식이 없는" 빈자리를 채웠는데, **채운 알림이 정작 알림 화면에 없었다.** 빈자리가 반만 채워져 있던 것이다.

더 파보니 `type='JOIN'`은 알림 테이블에서 **사실상 죽은 카테고리**였다.

| subType | 성격 | 생산 | 알림 화면에 뜨나 |
|---|---|---|---|
| `JOIN_REQUEST` | 처리형 | **안 됨** | — |
| `MEMBER_JOINED` | 정보성 | 됨 | **안 뜸** |
| `JOIN_ACCEPTED` | 정보성 | 됨 | **안 뜸** |

**처리형은 안 만들어지고, 만들어지는 건 전부 정보성인데 볼 수가 없다.** `web-design#51`로 이슈를 떼고 lami2342에게 배정했고, 같은 날 `#52`로 계약이 정리됐다.

## 5. 리뷰 — 막은 것과 통과시킨 것

### 통과 — `#124`에서 위험한 자리 둘을 확인했다

lami2342가 `MEMBER_LEFT`를 구현하면서 **순환 의존**을 만났다(`RoomService → NotificationService → RoomService`). `NotificationService`가 `RoomService` 대신 `RoomMemberMapper`를 직접 받도록 끊었는데, 이건 **기존 API 두 개의 인가 판정이 바뀔 수 있는 자리**다.

- 복제한 `assertActiveMember`가 원본과 **같은 mapper·같은 조건·같은 에러코드**임을 대조했다
- 팬아웃이 `status='LEFT'` 갱신 **뒤에** 불리는데, `fanOutToActiveMembers`가 `status='ACTIVE'`와 `user_id != actorId` **양쪽으로 거른다** — 이중으로 안전하다

테스트가 **총 건수를 1로 못박은 게** 좋았다. 수신자 조건만 봤으면 "나간 사람에게도 한 건 더 갔다"를 못 잡는다.

### 막은 것 — `#243`의 `<ScrollRestoration />`

kimgyubi1234가 필름스트립 스크롤 버그를 고치면서 `router.jsx` 최상위에 `<ScrollRestoration />`을 "안전망으로" 넣었다.

**틀린 코드가 아니다.** 라우트 이동 시 스크롤이 남는 건 실제 문제고 이게 표준 해법이다. 다만 —

1. **원인은 이미 고쳐졌다** — 필름스트립 `scrollLeft` 수정으로 증상은 사라진다. 이건 그 위에 얹는 별개 개선이다
2. **적용 범위가 앱 전체다** — 프로젝트에 기존 사용이 0건이라 되돌아갈 기준선도 없다
3. **검증이 안 됐다** — 본인도 "로그인 화면이라 직접 확인 못 함"이라 적었다

> **한 PR에 원인 수정과 전역 정책 변경이 같이 있으면, 나중에 스크롤이 이상할 때 어느 쪽 탓인지 가릴 수 없다.**

상태 메시지 제한도 짚었다. 이슈는 "한글20/영어40 안내를 유지한다"고 했는데 가중치 로직을 걷어내 **한글 한도가 2배(20→40자)가 됐다.** 방향은 (A)가 낫다고 봤지만 — 실제로 기존은 **입력 한도(40자)와 저장 한도(가중치 40)가 어긋나** 한글 21자부터 저장 버튼이 죽던 상태였다 — **이슈가 유지하라고 한 것을 뒤집었으면 본문에 드러나야 한다.**

**리더 판단으로 그대로 머지됐다.** 두 항목은 현재 main에 있다.

### 변경 요청 후 승인 — `#52`

구조는 전부 맞았는데 본문 두 문장이 사실과 달랐다. 특히 이것 —

> 순서가 반대면 입장·수락 알림이 잠깐 "◯◯님의 행운편지"로 잘못 뜨는 회귀가 생긴다.

**`#242`가 머지되면서 `FEED_META.FRIEND`가 삭제돼 이미 틀린 말이 됐다.** 실제로는 `DEFAULT_META`("◯◯님의 새 소식")로 떨어진다 — 모호할 뿐 틀리지 않은 문구다.

계약은 SSOT라 **순서 압박이 실제보다 세게 적혀 있으면 나중 판단이 왜곡된다.** lami2342가 두 문장을 한 항목으로 합쳐서 고쳤는데, 원래 같은 이야기였던 걸 나눠 적었던 거라 **내 제안보다 나았다.**

### 저녁에 셋을 더 봤다

`#250`(프론트 문구 이동)·`#128`(백엔드 type 전환)은 승인했다. `#128`은 **`TYPE_JOIN` 생산자를 전수로 세어** 빠진 자리가 없음을 확인했고, 테스트가 **`type` 단언만 바꾸고 건수·수신자·actor는 그대로 둔 것**이 좋았다 — 같이 풀었으면 `#90`·`#113`에서 잡은 회귀를 못 잡는다.

**남은 하나가 `clov-api#92`인데, 이건 리뷰보다 그 앞의 진단이 컸다 → §8.**

## 6. 마스코트를 네 화면으로 — 라우터를 안 건드린 이유

캐릭터를 고르고 스킨을 사도 **볼 수 있는 자리가 우정공간 한 곳뿐**이었다.

방법이 둘이었다.

| | 얻는 것 | 치르는 것 |
|---|---|---|
| **화면별 마운트**(택함) | 3줄, 위험 없음 | 화면 이동 시 리마운트 |
| 레이아웃 라우트 | 마스코트 상태 유지 | `index` route 도입·경로 매칭 변화 |

**리마운트로 잃는 게 수면 20초·연타 1초·말풍선 1.8초짜리 짧은 타이머뿐이다.** 화면을 옮기는 순간 사용자 주의도 옮겨가서 체감이 거의 없다. 반면 라우트 계층 변경은 회귀 위험이 실재한다 — **같은 날 `#243`에서 `<ScrollRestoration />` 하나를 검증 부족으로 막았는데, 라우트 계층을 바꾸는 건 그보다 크다.**

### 함정 하나를 확인했다

`Letters`·`Schedule`은 루트에 라이트 팔레트를 `style`로 강제한다(다크 모드에서도 라이트로 렌더). 마스코트가 그 안에 들어가면 **CSS 커스텀 프로퍼티를 상속받는다** — `position: fixed`라도 변수는 시각적 박스가 아니라 DOM 트리를 타기 때문이다.

대조 결과 `Mascot.css`가 쓰는 변수는 **`--clov-mascot-size` 하나뿐**이고, 그건 `mascotSize.js`가 `:root`에 직접 세팅한다. 두 팔레트의 13개 변수와 안 겹치고 `:root` 값이라 페이지 래퍼가 덮을 수도 없다.

z-index도 안전했다 — 세 화면의 `position: fixed` 요소가 전부 모달(240~9600)이라 마스코트(40)가 뒤에 깔린다. **모달을 열면 가려지는 게 맞는 동작이다.**

## 7. 배포 — 일곱 번 다 인증 없이 증명했다

clov-web **5회**, clov-api **2회**. 인증이 걸린 화면을 못 보는 상태에서 **일곱 번 다 "올라갔다"를 눈이 아니라 응답으로 증명했다.**

| 회차 | 무엇 | 증명 방법 |
|---|---|---|
| web 1 | 스킨 3종 + lami·kimgyubi 수정 | `public/` 에셋 6개 GET — **바이트까지 디스크와 일치** |
| web 2 | 마스코트 4화면 + 티켓 UI | 로컬 `dist/assets/`의 **콘텐츠 해시 파일명**을 배포 도메인에 요청 → 200 |
| web 3 | `#250` 알림 문구 이동 | 배포된 번들을 받아 **바뀐 문자열을 직접 찾음** |
| web 4 | 스킨 4종 + 아이콘 수정 | 에셋 바이트 대조 + 번들에서 `ti-circle-off` 1건 · `ti-bubble` **0건** 확인 |
| web 5 | Signup Enter · OAuthRedirect 이식 | **운영 도메인을 브라우저로 직접 열었다** — 아래 참조 |
| api 1 | `#124` + `#127` + `#128` | `/api/v1/rooms` → **401**(502 아님) |
| api 2 | `#130` 카탈로그 status 필터 | 401까지 **17초** · CI에서 새 통합 테스트 통과 |

### 증명 방법을 한 단계 더 밀었다

1·2회차는 **파일이 올라갔다**까지였다. 3회차는 **그 파일 안에 오늘의 코드가 있다**를 봤다.

```
/assets/index-BOYC_Q_9.js   676,484B
  MEMBER_LEFT:{cls:`join`,icon:`ti-user-minus`,tail:`님이 나갔어요`,fallback:`멤버가 나갔어요`}
```

해시 대조는 **로컬에서 같은 빌드를 돌려야** 성립하는데, 번들에서 문자열을 찾는 건 **로컬 빌드 없이도 된다.** 배포본이 진짜인지 묻는 데는 이쪽이 더 직접적이다.

### ★★ 5회차에서 한 칸 더 갔다 — 운영 화면을 직접 봤다

`OAuthRedirect`는 **로그인 게이트 밖**이다. 그래서 배포된 도메인을 브라우저로 열어 **렌더된 결과를 직접 읽었다.**

```
https://clovlabcalss.store/oauth2/redirect?code=<아무 값>

.proto-oauthredirect   있음
emotion css-* 클래스   0개        ← 이식이 끝났다는 뜻
box-sizing             content-box  ← lami가 일부러 보존한 값 그대로
콘솔 에러              0건
화면                   "인증 시간이 만료되었어요. 다시 로그인해주세요."
```

**그 문구가 나온 게 덤으로 하나를 더 증명했다.** 오전에 `clov-web#247`을 닫으면서 *"`clov-api#127`의 401→400 변경이 문구는 그대로 두고 refresh 왕복만 없앤다"* 를 코드로만 판단했는데, **운영에서 실제로 그 문구가 나왔다.**

> **"로그인 뒤 화면을 못 본다"가 "아무것도 못 본다"는 아니다.** 인증 화면 넷(Login·Signup·JoinRoom·OAuthRedirect)은 게이트 밖이라 실제 렌더를 볼 수 있다. 오늘 `#259`(shake 애니메이션)도 그래서 재현으로 잡았다(§9).

`REACT_ENV_deploy-myeongjun` 시크릿이 없어 레포의 `.env.production`을 쓴다는 경고가 다섯 번 다 떴다 — **공용 도메인으로 나간다는 뜻이고 리더 배포에서는 의도한 동작이다.**

### ★ clov-api 배포를 하루 종일 미뤄서 502를 한 번만 겪었다

`#124`가 오전에 머지됐지만 **배포하지 않고 기다렸다.** `#127`·`#128`이 같은 날 들어올 게 보였기 때문이다.

```
01:43  #124 머지 (MEMBER_LEFT)      ← 배포 안 함
02:19  #127 머지 (OAuth 만료 오탐)   ← 배포 안 함
02:27  #128 머지 (type FRIEND)
02:29  배포 1회 — 세 개가 같이 나감
```

레포에 헬스체크가 없어 **배포마다 4분 30초쯤 502가 난다**(`clov-api#108`, 08-03 실측). 세 번 나눠 쐈으면 **13분 30초**를 죽었을 자리다.

> **머지는 배포가 아니다.** 이 간격이 있어야 묶을 수 있다. 헬스체크가 없는 레포에서는 **머지 즉시 배포가 오히려 손해다.**

배포 후 확인도 워크플로 초록불이 아니라 `curl`로 했다. **초록불은 "컨테이너가 떴다"까지고 "서비스 정상"이 아니다.** `/api/v1/rooms`가 401이면 인증 필터까지 살아 있다는 뜻이다.

## 8. ★★ 골드가 "안 들어오는" 게 아니라 "만든 적이 없었다"

하루 끝에 이 질문이 왔다.

> 새 D-day 만들기, 글쓰기 할 때마다 골드가 들어와야 하는데 지급이 안 되고 있는 것 같다. 돈이 들어와야 사용자가 상점을 쓸 수 있지 않겠나.

**버그로 접근했으면 `MemoryService`를 뒤졌을 것이다.** 먼저 확인한 건 지급 코드가 있느냐였다.

```
$ git grep -n "EARN_" origin/main -- src/main
(0건)
```

`WalletTransaction`에 있는 사유는 **`PURCHASE`와 `SIGNUP_GRANT` 둘뿐**이었다. 행동 지점 여섯 곳(`MemoryService` 2 · `PlanService` 2 · `MascotService` 1 · 이미지 보너스 1)이 전부 `expService.grant(...)`만 부른다 — **XP는 주는데 골드는 안 준다.**

| | main의 실제 동작 |
|---|---|
| 들어오는 길 | 가입 시 `SIGNUP_GRANT` 1,000 — **평생 한 번** |
| 나가는 길 | `PURCHASE` |
| 버는 길 | **없음** |

> **골드가 단방향이었다.** 1,000을 받아서 다 쓰면 그 계정은 상점이 영구히 닫힌다. 카탈로그는 71,660짜리인데 **평생 예산이 1,000이었다.**

### 왜 5일 동안 아무도 몰랐나 — 내 책임이다

지급 기능은 `clov-api#92`(chacha1650a)로 **07-30에 이미 올라와 있었다.** 5일 동안 열려 있었다.

어제 핸드오프에 *"`#92`가 07-30부터 정체. 크리티컬 패스"* 라고 적어놓고도 **막힌 이유를 안 봤다.** `BLOCKED`을 머지 충돌로 읽고 "작성자가 rebase할 차례"라고 미뤘다.

### ★ 그날 저녁에 그 진단도 틀렸다는 게 드러났다

리뷰에 *"승인이 없어서였다"* 라고 써서 chacha1650a에게 사과까지 했는데, 나중에 룰셋을 직접 열어보니 그것도 아니었다.

```json
// clov-api main 룰셋
"required_approving_review_count": 0,          ← 승인은 애초에 필요 없다
"required_review_thread_resolution": true,
"required_status_checks": [{ "context": "build" }]
```

`#92`는 **07-30에 이미 `build` pass**였고 미해결 리뷰 스레드도 **0개**였다.

> **GitHub은 이걸 한 번도 막은 적이 없다. 5일 내내 머지 가능했다.**

**결론은 더 나빠졌다.** 승인 게이트가 있었으면 "승인을 안 눌렀다"는 절차 누락인데, 게이트가 없었으니 **그냥 아무도 안 본 것**이다. 상태 문자열을 두 번 연속 추측으로 읽었다 — 처음엔 충돌로, 다음엔 승인 대기로. **둘 다 룰셋을 안 열어보고 낸 답이다.**

이 레포에서 PR이 실제로 막히는 조건은 둘뿐이다.

| | |
|---|---|
| `build` 체크 | 실패하거나 **아직 도는 중**이면 `BLOCKED` |
| 미해결 리뷰 스레드 | `required_review_thread_resolution: true`라 **스레드를 남겨두면 막힌다** |

두 번째가 실질적이다 — **인라인 코멘트로 스레드를 열면 고친 뒤 resolve까지 해야 머지된다.**

`#92`에 정정 코멘트를 달았다. **틀린 진단을 근거로 사과한 것을 그대로 두면, 다음 사람이 "승인 게이트가 있는 레포"로 읽는다.**

### 리뷰하면서 금액이 뒤집혀 있는 걸 봤다

구현을 맞추려고 계약 §15-4를 다시 읽다가 나왔다.

| 행동 | 필요한 것 | 07-31 값 |
|---|---|---:|
| 마스코트 교감 | **클릭 한 번** | **100** |
| 약속 연결 추억 | 약속 만들기 → 완료 → 글 작성 | **50** |

**가장 성의 없는 행동이 두 배를 벌고 있었다.** `CLAUDE.md`가 핵심 흐름을 *"약속 완료 후 추억 작성"* 이라고 못박아 두었는데, **골드가 그 루프를 밀지 않고 반대쪽을 밀고 있었다.**

07-31 값은 **획득 경로가 구현되기 전에 정한 탁상 수치**였다. 붙일 코드가 없으니 순서가 뒤집힌 걸 아무도 밟지 않았다.

### 계약 §15-4를 개정했다 (`web-design-repository#53`)

| | 개정 전(07-31) | 개정 후(08-04) |
|---|---:|---:|
| 마스코트 교감 | 100 × 3회 = 300 | **200 × 10회 = 2,000** |
| 약속 연결 추억 | 50 | **300** |
| 자유 추억 | **없음** | **200 × 3회 = 600** |
| 하루 총 상한 | 500 | **3,000** |
| 카탈로그 완주 | **143일** | **24일** |

금액을 **노력 순서**로 다시 세웠다 — 클릭 200 < 자유 글 200 < 약속 완주 300. 그리고 **표를 계약에 박아넣었다.** 새 사유를 넣을 때 자기 자리를 먼저 정하게 하려는 것이다. 금액이 노력 순서를 어기면 사용자가 가장 싼 경로만 반복한다.

### ★ 자유 추억은 사유를 따로 만들어야 했다

원래 `EARN_MEMORY` 하나로 합치려 했는데 못 합친다.

- 자유 추억은 **약속·완료·다른 참여자가 필요 없다** — 혼자 무한히 쓸 수 있다
- `MEMORY_ALREADY_WRITTEN`의 `UNIQUE(plan_id, writer_id)`도 **NULL은 중복을 허용**해서 안 막힌다
- 그래서 **하루 3회 캡**이 필요한데, **횟수는 사유별로 센다**(`countReasonToday`)

**사유를 합치면 그 3회 캡이 약속 추억까지 묶어버린다.** 하루에 약속을 다섯 개 완주해도 셋까지만 받는다. 그래서 `EARN_MEMORY_FREE`를 따로 냈다.

### 카탈로그 총액이 낡아 있었다

계약 §15-1의 `42,260 G`는 **스킨이 하나도 없던 07-30 값**이었다. 8월 초에 스킨 8종(29,400)이 들어와 실제로는 **71,660**이다 — 70% 커졌다.

이 값을 안 다시 세고 "며칠이면 다 산다"를 계산하면 그대로 틀린다. **세는 쿼리를 계약에 같이 넣었다.**

```sql
SELECT SUM(ROUND(price * (100 - discount_rate) / 100)) FROM shop_items;
```

### `#92` 리뷰 — 계약이 지목해서 금지한 실수가 그대로 있었다

```xml
<select id="sumEarnedToday" ...>
    ... WHERE reason IN ('EARN_MASCOT', 'EARN_MEMORY') ...
```

계약 §15-4에 **이 실수를 이름으로 지목한 경고**가 이미 있다 — *"합산 대상을 사유 이름으로 나열하면 새 사유가 조용히 캡 밖으로 빠진다. `EARN_` 접두사 전체를 대상으로 삼는다."*

**그리고 이 PR에서 바로 터진다.** `EARN_MEMORY_FREE`를 얹는 순간 자유 추억 골드가 **통째로 총 상한 밖에서 무한히 쌓인다.** 자바 쪽 Javadoc은 *"`EARN_*` 사유 합계만 센다"* 로 맞게 적혀 있는데 SQL이 그걸 안 지켰다.

> **주석이 맞고 쿼리가 틀리면 리뷰가 주석만 보고 통과시킨다.** 계약이 경고까지 써둬도 코드가 어기는 건 막지 못한다 — **경고를 검증 가능한 형태로 적어야 한다.** 그래서 계약의 경고 문구에 `reason LIKE 'EARN\_%'`를 같이 박았다.

캡 판정이 **행 잠금 밖**에 있는 것도 짚었다(`sumEarnedToday` → `if` → `findWalletForUpdate` 순서라 동시 요청 둘이 같은 누적치를 읽고 둘 다 통과한다). 요청 5건 중 ①②③은 필수, ④는 권장, ⑤는 테스트다.

**설계 자체는 좋았다.** `earnGold`가 실지급액을 반환해서 캡에 걸려도 화면이 거짓말을 안 하고, revive 분기가 `earnGold` 앞에서 early return해서 **삭제 후 재작성으로 다시 받는 경로가 없고**, `ClovTime.startOfTodayUtc()`가 KST 자정을 UTC로 환산한다(UTC 자정으로 잘랐으면 한국 사용자는 **오전 9시에 하루가 바뀐다**).

### 미결 — 약속(D-day) 생성에는 여전히 골드가 없다

질문에 *"새 D-day 만들기"* 가 있었는데 **계약에 `EARN_PLAN`이 없고 `#92`도 `PlanService`를 안 건드린다.**

## 9. ★★ 카탈로그 — 숫자를 세 번 틀리고, 상품 하나를 덮어쓰고, 열한 종을 내렸다

저녁에 스킨 4종을 등록하면서 시작됐는데, **계약에 적혀 있던 숫자를 확인하려다 세 겹이 연달아 드러났다.**

### ① 총액을 세 번 틀렸다 — 전부 "계산해서"

```
71,660   계산   시드 12종 42,260 + 스킨 8종 29,400
77,060   계산   위에 새 스킨 4종을 더함
71,860   실측   ← 앞의 둘이 얹혀 있던 시드 값이 틀렸다
34,800   실측   ← 셋째는 판매 종료분까지 세고 있었다
```

§15-1에 **"세는 쿼리는 아래와 같다"를 내가 직접 써놓고 한 번도 돌리지 않았다.** 두 번 다 앞 값에 더하기만 했다.

> **문서에 적힌 숫자는 계산으로 갱신하면 안 된다.** 앞 값이 틀렸으면 그 위에 얹은 값도 전부 틀린다. **재는 쿼리가 문서에 있으면 그건 "돌리라"는 뜻이다.**

### ② `code` 충돌로 기존 상품을 덮어썼다

실측이 예상과 어긋나서 **시드/스킨으로 쪼개 재봤다.** 그러자 원인이 바로 나왔다.

```
스킨 34,800   예상과 정확히 일치
시드 37,060   계약의 42,260보다 5,200 모자람
```

어제 가격표에 `EPIC 5,200 롭탐험가`가 있었다. 내가 새로 넣은 스킨의 `code`가 **그 시드 상품과 같았다.**

```sql
('COSTUME_ROB_EXPLORER', '롭 탐험가 코스튬', 'EPIC', 5200, ..., 100)   -- 07-29 시드
('COSTUME_ROB_EXPLORER', '탐험가 롭',        'UNCOMMON', 1500, ..., 230) -- 내 SQL
```

등록 SQL은 재실행 안전을 위해 `ON DUPLICATE KEY UPDATE`로 쓴다. **코드가 겹치면 새 행이 생기는 대신 기존 상품이 통째로 덮이고 에러는 안 난다.**

> **★ 내가 쓴 검증 쿼리로는 이걸 못 잡는다.** "4행 반환"은 **4개를 넣었을 때와 1개를 덮고 3개를 넣었을 때가 똑같다.** 전수 검사(스킨 12종)도 통과한다 — 덮인 쪽이 시드라 스킨 수는 맞기 때문이다.
>
> **넣기 전에 `code`가 이미 있는지 보는 것 말고는 막을 방법이 없다.** 계약에 그 쿼리를 박아뒀다.

**총액 하나만 쟀으면 원인을 못 짚었다.** 쪼개서 잰 덕에 "스킨은 맞는데 시드가 모자라다"가 나왔고 거기서 5,200이라는 숫자가 바로 걸렸다.

**리더 판단으로 덮어쓴 상태를 그대로 뒀다** — 덮인 시드가 SVG 한 장짜리 자리표시였고 그 자리를 상태 9종 스킨이 대신했으니 내용상 업그레이드다. 다만 **의도한 교체가 아니었다.**

### ③ 자리표시 11종을 내렸다 — `DELETE`가 아니라 `RETIRED`

시드 12종은 에셋 없이 이름과 가격만 있던 자리표시였다. 진짜 스킨이 12종 들어왔으니 비켜줄 때가 됐다.

**`DELETE`는 애초에 불가능했다.**

```
user_inventory_items.item_id        FK RESTRICT
user_preferences.equipped_item_id   FK RESTRICT
```

그리고 실제로 **6명이 갖고 있었다.** 뚫고 지웠으면 user 19가 그날 02:37에 12,000골드로 산 여름밤 스킨까지 전부 날아간다. 환불 로직도 없고 `wallet_transactions`의 구매 이력은 없는 상품을 가리킨 채 남는다.

`RETIRED`는 계약이 정의해둔 정식 수단이었다 — **목록에서 빠지고, 구매가 막히고, 산 사람은 그대로 갖고, 되돌리기가 한 줄이다.**

### ④ 그런데 `RETIRED`가 안 먹고 있었다

```xml
<!-- ShopMapper.findCatalog — status 조건이 없다 -->
WHERE (#{category} IS NULL OR i.category = #{category})
```

`ShopItem.isPurchasable()`은 `ACTIVE`만 허용하는데 **목록 쿼리만 그 기준을 안 봤다.** 내려도 화면에 그대로 뜨고 누르면 `ITEM_NOT_PURCHASABLE`로 떨어지는 **"보이는데 못 사는"** 상태다. 어제 핸드오프에 *"이슈로 안 만들었다"* 로 적혀 있던 항목이다.

**테스트가 이 버그를 통과시켜 온 이유가 있었다.** 셋업에 `TEST_RETIRED_SKIN`이 **이미 있었는데 구매 차단만 검증**하고 목록 쪽은 비어 있었다. 그 단언을 채웠다.

한 줄 고치고 배포한 뒤에야 SQL을 돌렸다. **순서가 반대였으면 고치려던 증상이 그대로 재현된다.**

### 결과

```
카탈로그   71,860  →  34,800   (판매 중인 것만)
완주       24일    →  약 12일
상품       23종    →  ACTIVE 12종 (전부 마스코트 스킨) + RETIRED 11종
```

**하루 상한 3,000은 안 건드렸다.** 오늘만 스킨이 8종 → 12종으로 늘었고, 반나절 만에 상한을 두 번 바꾸면 계약 이력이 흔들린다. **살 것이 늘어나는 속도가 상한을 따라잡는 쪽에 걸었다.**

```js
animation: ${rise} 0.6s ...                                    // 정상
animation: ${(p) => (p.$shake ? `${shakeInput} 0.4s ease` : 'none')};  // 터진다
```

## 11. 사고 하나 — 중단된 명령 뒤에 실행된 명령

```
git checkout main       → "Please commit your changes" 로 중단
git pull origin main    → 그대로 실행됨 (옛 브랜치에서!)
git checkout -b 새브랜치 → 그 위에서 생성
```

`&&`로 묶었는데 `git checkout`이 **실패 종료코드를 안 냈다.** 그래서 새 브랜치에 병합 커밋 3개가 딸려 붙었다.

`git diff origin/main HEAD`가 **비어 있어서** 내용은 같다는 걸 확인하고 `git reset --mixed origin/main`으로 포인터만 되돌렸다. 작업 트리는 안 건드렸다.

> **`git status`가 깨끗하지 않으면 `checkout`이 중단될 수 있다.** 체인 앞에 `git status --short`를 확인하거나, 브랜치를 만든 뒤 `git log origin/main..HEAD`가 비었는지 본다.

같은 계열로 `git add -A`가 **작업 중이던 새 스킨 폴더를 커밋에 끌어들인** 일도 있었다. `git reset --soft HEAD~1` + `restore --staged`로 뺐다. **AGENTS.md의 "Keep unrelated local changes out of the PR"이 이 자리다.**

- **★ 하나를 확인하러 갈 때 같은 종류 전체를 대조한다** — `ti-user-minus` 하나를 보러 갔다가 42종을 CDN 4,962종과 맞췄고, **찾던 것은 멀쩡했고 다른 게 걸렸다.** 비용이 같았다
- **★ 지우는 게 아니라 내리는 수단이 있는지 먼저 본다** — `DELETE`는 FK가 막았고 실제로 6명이 갖고 있었다. `RETIRED`는 계약이 이미 정의해둔 정식 수단이었는데 **정작 그게 동작을 안 하고 있었다**(§9). 되돌릴 수 있는 쪽을 고르면 판단이 싸진다
- **★★ "안 되는 기능"과 "만든 적 없는 기능"을 먼저 가른다** — "골드가 지급이 안 된다"를 버그로 읽으면 `MemoryService`를 뒤진다. `git grep EARN_ origin/main`이 **0건**이면 고칠 코드가 없는 것이다. **증상을 재현하기 전에 그 기능이 존재하는지 본다**
- **★★ `BLOCKED`의 뜻은 추측하지 말고 룰셋을 연다** — 같은 문자열을 하루에 두 번 다르게 추측했고 **둘 다 틀렸다**(충돌 → 승인 대기 → 실제로는 아무것도 안 막고 있었다). `gh api repos/OWNER/REPO/rules/branches/main` 한 줄이면 끝난다. 열린 PR은 **건수가 아니라 막힌 이유로** 센다 — 그런데 그 이유를 지어내면 세는 의미가 없다
- **★ 틀린 진단으로 사과하면 그 진단이 사실로 굳는다** — chacha1650a에게 "승인이 없어서 5일 걸렸다"고 사과했는데, 사과가 진단을 더 그럴듯하게 만든다. 정정 코멘트를 안 달았으면 다음 사람이 이 레포를 "승인 게이트가 있는 레포"로 읽는다

- **★ 계약의 경고는 검증 가능한 형태로 적는다** — §15-4가 "사유 이름을 나열하지 말라"고 경고했는데 SQL이 그대로 어겼다. 자바 주석은 맞게 적혀 있어서 **주석만 보면 통과한다.** 경고에 `reason LIKE 'EARN\_%'`를 같이 박아야 대조가 된다
- **문서에 박힌 총액·일수는 데이터가 늘면 조용히 낡는다** — 카탈로그 `42,260`은 스킨이 없던 값이라 실제(71,660)와 70% 벌어져 있었다. **숫자를 적을 때 세는 쿼리를 같이 적는다**
