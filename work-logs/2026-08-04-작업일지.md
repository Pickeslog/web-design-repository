## 2. 줄기 하나 — 스킨이 여섯에서 여덟로, 마스코트가 한 화면에서 네 화면으로

아침에 스킨은 5종이었고 마스코트는 **우정공간에서만** 보였다.

```
오닉스 '블랙스타 공방'(UNCOMMON)  →  롭 '옐로우 크루'(COMMON)  →  타코군 '수박껍질모자'(COMMON)
                                  →  마스코트를 추억피드·행운편지·일정계획에도
```

| | 아침 | 저녁 |
|---|---|---|
| 스킨 | 5종 | **8종** |
| 스킨을 가진 마스코트 | 4/6 | **5/6** (버거노인만 없다) |
| 마스코트가 보이는 화면 | 1곳 | **4곳** |
| 등급 층 | COMMON 비어 있음 | **네 층 전부 채워짐** |

**COMMON 층이 처음 열린 게 크다.** 900골드는 시작 골드 1,000 아래라 **가입 첫날 바로 살 수 있고**, 거기에 캐릭터가 둘(롭·타코군)이라 첫 스킨에 선택지가 생긴다.

### 등급마다 같은 값 쌍이 생겼다

```
COMMON      900  옐로우 크루 · 수박껍질모자
UNCOMMON  1,500  철골 작업반 · 블랙스타 공방
EPIC      6,000  마지막 신호병 · 오션 구조대
LEGENDARY 9,800  벚꽃 세트 · 아케이드 보스
```

어제 정한 규칙 — **등급도 같고 내용(상태 9종)도 같으면 값도 같게 둔다** — 이 그대로 네 번 적용됐다. 값을 가르는 두 축이 모두 같은데 다른 값을 붙이면 그게 근거 없는 숫자다.

COMMON만 예외적으로 **새 최고가**를 만들었다. 기존 두 줄(아이보리 500·클로버 배지 600)이 장식 하나짜리라 상태 9종 스킨과 내용이 다르기 때문이다. 선례도 있다 — ROV 조종사가 RARE 최고 2,400을, 마지막 신호병이 EPIC 최고 5,200을 넘었다.

## 3. ★★ 같은 결함에 반대 판정을 두 번 내렸고 둘 다 맞았다

오늘 가장 값진 것이다.

두 스킨에서 **똑같은 종류의 결함**이 나왔다. 배경 제거가 덜 끝나 캔버스 코너와 최하단 행에 고립 픽셀이 남아 있었다.

| | 알파 | bbox 하단 | 판정 |
|---|---|---|---|
| `rob/yellow-crew/angry.png` | **41** (코너), 1~8 (나머지) | **639** — 같은 폴더 다른 8장(471~539)에서 168px 벗어남 | **지웠다** |
| `tako-gun/watermelon` 9장 전부 | **3~8** | 594~626 — 정상 대역 | **안 지웠다** |

### 기준은 "잔여물이 있느냐"가 아니었다

```csharp
// scripts/mascot/SpriteTool.cs
private const int ALPHA_THRESHOLD = 8;
...
if (buf[row + x * 4 + 3] > ALPHA_THRESHOLD) {
```

**정규화 도구가 알파 8 이하를 이미 무시한다.** 그러니 판정은 이렇게 갈린다.

- 수박껍질모자의 알파 3~8 → **도구도 렌더도 못 본다.** 9장을 재인코딩하면 폴더가 300KB 넘게 커지는데 얻는 게 없다
- 옐로우 크루의 알파 41 → **임계값을 넘는다.** bbox가 캔버스 바닥까지 잡혀서, 이 상태로 정규화를 돌리면 면적 기준 배율 계산이 망가진다

> **판정 기준을 "결함이 있느냐"에 걸면 둘 다 지운다. "도구와 렌더가 그걸 보느냐"에 걸어야 둘이 갈린다.**
> 어제 정규화 판정을 `scale`이 아니라 `캔버스 균일성`에 건 것과 같은 계열이다 — **기준은 증상이 아니라 원인에 건다.**

### 순수 빨강이 단서였다

옐로우 크루의 잔여 픽셀 중 둘이 `RGB(255,0,0)`이었다. **노란 로봇·파란 멜빵·갈색 케이블에 순수 빨강이 있을 자리가 없다.** 크로마키 배경을 지운 흔적이다.

중간에 "크로마키 흔적" 자동 검출기를 만들어봤는데 **오닉스에서도 100건 넘게 잡혔다.** 반투명 아웃라인을 오탐한 것이라 버렸다. 검출기를 믿지 않고 **면별 분해(상/하/좌/우)로 돌아간 게 맞았다** — 케이블이 우측을 관통하는 것(정상)과 코너 잔여물(결함)이 그때 갈렸다.

### 이건 재발 중이다

스킨 **두 종 연속**으로 나왔고, `metadata.json`의 `states` 값이 **두 번 다 절대 경로**였다(기존 6종은 파일명만 쓴다). 매번 검사해서 잡는 것보다 **내보내기 쪽에서 끝내는 게 맞다.**

## 4. ★★ 알림 `type`을 무엇으로 가를지 정했다 — 그리고 첫 답을 뒤집었다

lami2342가 `clov-api#122`를 열었다. **나가기 확인창은 "남은 멤버에게 나갔다고 알림이 가요"라고 하는데 실제로는 안 간다.** 계약 §13 프로즈도 "입·퇴장"을 약속하는데 표에 행이 없었다.

`MEMBER_LEFT`를 신설하는 건 명확했다. 문제는 **어느 `type` 탭에 넣느냐**였다.

### 처음엔 JOIN이 맞아 보였다

짝인 `MEMBER_JOINED`가 JOIN에 있으니 대칭이 맞고, FRIEND에 넣으면 입장과 퇴장이 다른 탭으로 갈린다. 그렇게 정리해서 이슈에 올렸다.

### 코드를 보고 전제가 틀렸음을 알았다

```js
// Notifications.jsx
enabled: activeTab !== 'JOIN',                                       // :59  JOIN이면 알림 조회를 안 한다
const joinRequestsQuery = useQuery({ ... getJoinRequests(roomId) })  // :61  대신 가입신청 리소스
{tab.id === 'JOIN' && pendingRequests.length > 0 && ...}             // :130 뱃지도 신청 건수
{activeTab === 'JOIN' ? <JoinRequestList ... /> : ...}               // :136
```

탭 라벨도 `'가입 신청'`이다. **JOIN 탭은 알림 피드가 아니라 승인/거절하는 처리함이었다.**

그래서 두 가지가 뒤집혔다.

1. 내가 걱정한 **"JOIN_REQUEST 건수 희석"은 근거가 없었다** — 뱃지가 알림이 아니라 가입 신청 리소스를 센다
2. 대신 더 큰 문제가 있었다 — **JOIN에 넣으면 알림 목록 어디에도 안 뜬다**

### 그래서 기준을 다시 세웠다

계약 §13이 이미 **"`type` = 어느 탭에 보일지"** 라고 정의하고 있었다. 주제 분류가 아니다. 그러면 탭의 성격이 곧 기준이 된다.

> **알림은 주제축("멤버에 관한 것끼리 묶는다")이 아니라 행동축("처리할 게 있나")으로 먼저 가른다.**
> 처리함은 비워야 하는 통이라, 안 없어지는 정보성 항목이 섞이면 뱃지가 0이 되지 않고 그때부터 사용자가 뱃지를 무시한다.

| | 사용자가 할 일 | 통 |
|---|---|---|
| 가입 신청 | 승인/거절해야 함 | 처리함 |
| 입장·퇴장·추억·약속·레벨업 | 알기만 하면 됨 | 피드 |

`MEMBER_LEFT`는 **FRIEND**로 확정했다(`web-design-repository#50`).

### 원칙이 그 자리에서 확산됐다

같은 구조 때문에 **`JOIN_ACCEPTED`도 알림 화면에 안 뜬다**는 게 드러났다. 어제 `#113`으로 "승인됐는데 아무 소식이 없는" 빈자리를 채웠는데, **채운 알림이 정작 알림 화면에 없었다.** 빈자리가 반만 채워져 있던 것이다.

더 파보니 `type='JOIN'`은 알림 테이블에서 **사실상 죽은 카테고리**였다.

| subType | 성격 | 생산 | 알림 화면에 뜨나 |
|---|---|---|---|
| `JOIN_REQUEST` | 처리형 | **안 됨** | — |
| `MEMBER_JOINED` | 정보성 | 됨 | **안 뜸** |
| `JOIN_ACCEPTED` | 정보성 | 됨 | **안 뜸** |

**처리형은 안 만들어지고, 만들어지는 건 전부 정보성인데 볼 수가 없다.** `web-design#51`로 이슈를 떼고 lami2342에게 배정했고, 같은 날 `#52`로 계약이 정리됐다.

## 5. 리뷰 — 막은 것과 통과시킨 것

### 통과 — `#124`에서 위험한 자리 둘을 확인했다

lami2342가 `MEMBER_LEFT`를 구현하면서 **순환 의존**을 만났다(`RoomService → NotificationService → RoomService`). `NotificationService`가 `RoomService` 대신 `RoomMemberMapper`를 직접 받도록 끊었는데, 이건 **기존 API 두 개의 인가 판정이 바뀔 수 있는 자리**다.

- 복제한 `assertActiveMember`가 원본과 **같은 mapper·같은 조건·같은 에러코드**임을 대조했다
- 팬아웃이 `status='LEFT'` 갱신 **뒤에** 불리는데, `fanOutToActiveMembers`가 `status='ACTIVE'`와 `user_id != actorId` **양쪽으로 거른다** — 이중으로 안전하다

테스트가 **총 건수를 1로 못박은 게** 좋았다. 수신자 조건만 봤으면 "나간 사람에게도 한 건 더 갔다"를 못 잡는다.

### 막은 것 — `#243`의 `<ScrollRestoration />`

kimgyubi1234가 필름스트립 스크롤 버그를 고치면서 `router.jsx` 최상위에 `<ScrollRestoration />`을 "안전망으로" 넣었다.

**틀린 코드가 아니다.** 라우트 이동 시 스크롤이 남는 건 실제 문제고 이게 표준 해법이다. 다만 —

1. **원인은 이미 고쳐졌다** — 필름스트립 `scrollLeft` 수정으로 증상은 사라진다. 이건 그 위에 얹는 별개 개선이다
2. **적용 범위가 앱 전체다** — 프로젝트에 기존 사용이 0건이라 되돌아갈 기준선도 없다
3. **검증이 안 됐다** — 본인도 "로그인 화면이라 직접 확인 못 함"이라 적었다

> **한 PR에 원인 수정과 전역 정책 변경이 같이 있으면, 나중에 스크롤이 이상할 때 어느 쪽 탓인지 가릴 수 없다.**

상태 메시지 제한도 짚었다. 이슈는 "한글20/영어40 안내를 유지한다"고 했는데 가중치 로직을 걷어내 **한글 한도가 2배(20→40자)가 됐다.** 방향은 (A)가 낫다고 봤지만 — 실제로 기존은 **입력 한도(40자)와 저장 한도(가중치 40)가 어긋나** 한글 21자부터 저장 버튼이 죽던 상태였다 — **이슈가 유지하라고 한 것을 뒤집었으면 본문에 드러나야 한다.**

**리더 판단으로 그대로 머지됐다.** 두 항목은 현재 main에 있다.

### 변경 요청 후 승인 — `#52`

구조는 전부 맞았는데 본문 두 문장이 사실과 달랐다. 특히 이것 —

## 6. 마스코트를 네 화면으로 — 라우터를 안 건드린 이유

캐릭터를 고르고 스킨을 사도 **볼 수 있는 자리가 우정공간 한 곳뿐**이었다.

방법이 둘이었다.

| | 얻는 것 | 치르는 것 |
|---|---|---|
| **화면별 마운트**(택함) | 3줄, 위험 없음 | 화면 이동 시 리마운트 |
| 레이아웃 라우트 | 마스코트 상태 유지 | `index` route 도입·경로 매칭 변화 |

**리마운트로 잃는 게 수면 20초·연타 1초·말풍선 1.8초짜리 짧은 타이머뿐이다.** 화면을 옮기는 순간 사용자 주의도 옮겨가서 체감이 거의 없다. 반면 라우트 계층 변경은 회귀 위험이 실재한다 — **같은 날 `#243`에서 `<ScrollRestoration />` 하나를 검증 부족으로 막았는데, 라우트 계층을 바꾸는 건 그보다 크다.**

### 함정 하나를 확인했다

`Letters`·`Schedule`은 루트에 라이트 팔레트를 `style`로 강제한다(다크 모드에서도 라이트로 렌더). 마스코트가 그 안에 들어가면 **CSS 커스텀 프로퍼티를 상속받는다** — `position: fixed`라도 변수는 시각적 박스가 아니라 DOM 트리를 타기 때문이다.

대조 결과 `Mascot.css`가 쓰는 변수는 **`--clov-mascot-size` 하나뿐**이고, 그건 `mascotSize.js`가 `:root`에 직접 세팅한다. 두 팔레트의 13개 변수와 안 겹치고 `:root` 값이라 페이지 래퍼가 덮을 수도 없다.

z-index도 안전했다 — 세 화면의 `position: fixed` 요소가 전부 모달(240~9600)이라 마스코트(40)가 뒤에 깔린다. **모달을 열면 가려지는 게 맞는 동작이다.**

## 7. 배포 — 네 번 다 인증 없이 증명했다

clov-web **3회**, clov-api **1회**. 인증이 걸린 화면을 못 보는 상태에서 **네 번 다 "올라갔다"를 눈이 아니라 응답으로 증명했다.**

| 회차 | 무엇 | 증명 방법 |
|---|---|---|
| web 1 | 스킨 3종 + lami·kimgyubi 수정 | `public/` 에셋 6개 GET — **바이트까지 디스크와 일치** |
| web 2 | 마스코트 4화면 + 티켓 UI | 로컬 `dist/assets/`의 **콘텐츠 해시 파일명**을 배포 도메인에 요청 → 200 |
| web 3 | `#250` 알림 문구 이동 | 배포된 번들을 받아 **바뀐 문자열을 직접 찾음** |
| api 1 | `#124` + `#127` + `#128` | `/api/v1/rooms` → **401**(502 아님) |

### 증명 방법을 한 단계 더 밀었다

1·2회차는 **파일이 올라갔다**까지였다. 3회차는 **그 파일 안에 오늘의 코드가 있다**를 봤다.

```
/assets/index-BOYC_Q_9.js   676,484B
  MEMBER_LEFT:{cls:`join`,icon:`ti-user-minus`,tail:`님이 나갔어요`,fallback:`멤버가 나갔어요`}
```

해시 대조는 **로컬에서 같은 빌드를 돌려야** 성립하는데, 번들에서 문자열을 찾는 건 **로컬 빌드 없이도 된다.** 배포본이 진짜인지 묻는 데는 이쪽이 더 직접적이다.

`REACT_ENV_deploy-myeongjun` 시크릿이 없어 레포의 `.env.production`을 쓴다는 경고가 세 번 다 떴다 — **공용 도메인으로 나간다는 뜻이고 리더 배포에서는 의도한 동작이다.**

### ★ clov-api 배포를 하루 종일 미뤄서 502를 한 번만 겪었다

`#124`가 오전에 머지됐지만 **배포하지 않고 기다렸다.** `#127`·`#128`이 같은 날 들어올 게 보였기 때문이다.

```
01:43  #124 머지 (MEMBER_LEFT)      ← 배포 안 함
02:19  #127 머지 (OAuth 만료 오탐)   ← 배포 안 함
02:27  #128 머지 (type FRIEND)
02:29  배포 1회 — 세 개가 같이 나감
```

레포에 헬스체크가 없어 **배포마다 4분 30초쯤 502가 난다**(`clov-api#108`, 08-03 실측). 세 번 나눠 쐈으면 **13분 30초**를 죽었을 자리다.

> **머지는 배포가 아니다.** 이 간격이 있어야 묶을 수 있다. 헬스체크가 없는 레포에서는 **머지 즉시 배포가 오히려 손해다.**

배포 후 확인도 워크플로 초록불이 아니라 `curl`로 했다. **초록불은 "컨테이너가 떴다"까지고 "서비스 정상"이 아니다.** `/api/v1/rooms`가 401이면 인증 필터까지 살아 있다는 뜻이다.

## 9. 사고 하나 — 중단된 명령 뒤에 실행된 명령

```
git checkout main       → "Please commit your changes" 로 중단
git pull origin main    → 그대로 실행됨 (옛 브랜치에서!)
git checkout -b 새브랜치 → 그 위에서 생성
```

`&&`로 묶었는데 `git checkout`이 **실패 종료코드를 안 냈다.** 그래서 새 브랜치에 병합 커밋 3개가 딸려 붙었다.

`git diff origin/main HEAD`가 **비어 있어서** 내용은 같다는 걸 확인하고 `git reset --mixed origin/main`으로 포인터만 되돌렸다. 작업 트리는 안 건드렸다.

> **`git status`가 깨끗하지 않으면 `checkout`이 중단될 수 있다.** 체인 앞에 `git status --short`를 확인하거나, 브랜치를 만든 뒤 `git log origin/main..HEAD`가 비었는지 본다.

같은 계열로 `git add -A`가 **작업 중이던 새 스킨 폴더를 커밋에 끌어들인** 일도 있었다. `git reset --soft HEAD~1` + `restore --staged`로 뺐다. **AGENTS.md의 "Keep unrelated local changes out of the PR"이 이 자리다.**

- **★★ "안 되는 기능"과 "만든 적 없는 기능"을 먼저 가른다** — "골드가 지급이 안 된다"를 버그로 읽으면 `MemoryService`를 뒤진다. `git grep EARN_ origin/main`이 **0건**이면 고칠 코드가 없는 것이다. **증상을 재현하기 전에 그 기능이 존재하는지 본다**
- **★★ `BLOCKED`은 충돌일 수도 승인 대기일 수도 있다** — 충돌이면 작성자가 움직여야 하고 승인 대기면 내가 움직여야 한다. **같은 글자를 잘못 읽어 5일을 세웠다.** 열린 PR은 **건수가 아니라 막힌 이유로** 센다. 충돌은 시끄럽고 승인 대기는 조용하다
- **★ 보상 금액은 노력 순서를 따른다** — 클릭 한 번이 100인데 약속 완주가 50이면, 서비스가 뭘 핵심 흐름이라 부르든 사용자는 클릭만 한다. **새 사유를 넣을 때 노력 순서표에 자기 자리부터 정한다**
- **★ 계약의 경고는 검증 가능한 형태로 적는다** — §15-4가 "사유 이름을 나열하지 말라"고 경고했는데 SQL이 그대로 어겼다. 자바 주석은 맞게 적혀 있어서 **주석만 보면 통과한다.** 경고에 `reason LIKE 'EARN\_%'`를 같이 박아야 대조가 된다
- **문서에 박힌 총액·일수는 데이터가 늘면 조용히 낡는다** — 카탈로그 `42,260`은 스킨이 없던 값이라 실제(71,660)와 70% 벌어져 있었다. **숫자를 적을 때 세는 쿼리를 같이 적는다**
- **머지 즉시 배포가 손해일 수 있다** — 헬스체크 없는 레포는 배포마다 4분 30초 502다. `#124`를 오전에 머지하고 저녁까지 참아 `#127`·`#128`과 묶었다. **세 번 쐈으면 13분 30초였다**
- **★ 판정 기준을 "결함이 있느냐"가 아니라 "그걸 보는 쪽이 있느냐"에 건다** — 같은 잔여물을 한 번은 지우고 한 번은 안 지웠는데 둘 다 맞았다. 기준이 `ALPHA_THRESHOLD=8`이었기 때문이다
- **★ 알림·카테고리는 주제축이 아니라 행동축으로 먼저 가른다** — "처리할 게 있나"가 "무엇에 관한 것인가"보다 먼저다. 처리함에 정보성 항목이 섞이면 뱃지가 0이 되지 않고, 그때부터 뱃지가 무시된다
- **★ 자기 권고를 코드로 검증한다** — 대칭성만 보고 JOIN이 맞다고 했는데, `Notifications.jsx` 네 줄을 읽고 전제가 틀렸음을 알았다. **판단 근거가 "그럴듯함"이면 코드를 열어본다**
- **자동 검출기가 오탐하면 버리고 손으로 돌아간다** — 크로마키 검출기가 오닉스에서 100건 넘게 잡길래 버리고 면별 분해로 갔다. 그때 케이블(정상)과 코너 잔여물(결함)이 갈렸다
- **한 PR에 원인 수정과 전역 정책 변경을 같이 넣지 않는다** — 나중에 문제가 생겼을 때 어느 쪽 탓인지 못 가린다
- **틀려진 주석·문서는 코드처럼 지운다** — `#241`이 "일부러 지정하지 않는다"는 옛 주석을 같이 지웠고, `#52`가 "탭이 갈리는 것은 알고 내린 결정"을 지웠다. 남겨두면 다음 사람이 "의도된 것"으로 읽는다
- **계약 문서의 부정확한 문장은 판단을 왜곡한다** — "행운편지로 뜬다"가 실제보다 심각하게 적혀 있었다. 순서 압박이 과장되면 배포 계획이 필요 이상으로 조여진다
- **`&&` 체인 앞의 명령이 중단돼도 뒤가 실행될 수 있다** — `git checkout`이 실패 종료코드를 안 냈다. 브랜치를 만들면 `git log origin/main..HEAD`로 확인한다
- **배포 반영은 인증 없이 증명된다 — 방법이 둘이다** — ① 로컬 `dist/assets/`의 해시 파일명이 배포 도메인에서 200 ② **배포된 번들을 받아 바뀐 문자열을 직접 찾기.** ②는 로컬 빌드가 필요 없고 "그 파일 안에 오늘 코드가 있다"까지 본다
